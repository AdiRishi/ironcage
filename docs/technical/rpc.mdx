Use the starter's native Worker RPC integration. The server implementation defines each method once, and Alchemy derives the callable client. Shared schemas define payloads where consumers need them. This page allocates behavior without prescribing a second handwritten interface for every future operation.

## Boundary rules

The web Worker authenticates browser requests and injects owner context. Private processor calls use their accepted import identity. The analyst receives read-only financial capabilities. Service bindings are private, and the API still checks ownership and permitted operations. A narrower TypeScript type alone does not authorize a caller.

Browser server functions validate input using the same contracts as the API. File bodies use authenticated streaming handlers where RPC is unsuitable. Responses expose only fields the screen or tool needs, including evidence references but excluding storage keys, raw account identifiers, credentials, and authentication metadata.

## Stage 1

| Operation group         | Observable interface                                                                                                                                                 |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Accounts and settings   | Read and update implemented account metadata and display preferences.                                                                                                |
| Upload                  | Register verified bytes, identify an existing source, and start processing or return an actionable start failure.                                                    |
| Import status           | List uploads and return the current file summary, reviews, or failure. Retry can rerun processing.                                                                   |
| Transactions            | List filtered bank postings and retrieve one posting with its supporting rows and sources.                                                                           |
| Review                  | Show ambiguous account, value, or duplicate evidence. Accept a specific resolution and rerun validation.                                                             |
| Evidence                | Stream an authorized source or show its extracted row data.                                                                                                          |
| Publication             | The processor submits parsed observations. The API validates and matches against current records, then commits accepted postings and review dispositions atomically. |
| Financial command retry | The same command ID retrieves the committed result after a lost response.                                                                                            |

Transaction reads require no interpretation joins in this stage. Publication is one domain operation; callers do not coordinate table-level writes or chunk-by-chunk financial commits.

## Stage 2

Extend upload and evidence handling to PDF. Add source removal, on-demand data export, and basic model usage/settings reads. Removal deletes original bytes while retaining accepted transactions and extracted evidence. Reupload can restore source access. An export failure offers another export attempt.

## Stage 3

Add reference-data management, interpretation reads, categorization actions, splits, movement and credit links, rules, correction history, and undo. Broad or financial changes have an impact preview and version-checked acceptance. Single-record category changes can use the ordinary edit form directly.

A processor classification is a suggestion until the API applies it under the same override and ownership rules as the UI. AI failure creates review information, not a failed bank import. A user can request categorization of existing postings without reuploading them.

## Stage 4

Add financial summaries, comparisons, contribution queries, and saved-query management. Reads return consistent totals and coverage for their resolved query. Drill-down refreshes the displayed total and contributions together if data changed. Saved definitions run on open or explicit refresh.

## Stage 5

Add commitment management, recurrence suggestions, occurrence decisions, ordinary-cost calculation, and forecast/scenario queries. All calculations use the shared deterministic financial functions. Saving assumptions requires an authenticated user action.

## Stage 6

Use the SDK's conversation transport, persistence, cancellation, and reconnect behavior. Financial tools reuse existing read operations with trusted owner context. Suggestions link to existing edit controls or show an explicit confirmation card that calls the ordinary user command. Natural-language text alone never calls a financial mutation.

Notes are explicit user-managed records. Starting a fresh conversation loads the current notes. There is no separate intent-extraction or application-run supervisor interface.

## Stage 7

Add finding and intention reads and user actions, inbox state, and reminder preferences. A bounded scan recomputes current findings and intention progress. Failure can be retried from the owning screen. In-app notification identity prevents unchanged results appearing as new.

## Errors and status

[Shared contracts](/technical/contracts#failures) defines user-facing errors. Import status and platform execution state must agree when displayed; if execution stopped before writing an application summary, the status read can report the platform failure and offer retry. No dispatcher recovery service is required to make a failure visible.

Use public operations for integration tests. Derive method names, input types, and output types from implemented code when producing more detailed API reference material.
