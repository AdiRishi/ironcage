The financial API exports the methods below through the starter's native Worker RPC adapter, except the explicitly identified content streams. Each RPC takes `{context: CallerContext, input: Input}` and returns an Effect success value or a tagged failure. The adapter derives the callable client from the server implementation. Content streams use private service-binding HTTP handlers with the same ownership rules.

`CallerContext`, `Command`, `CommandReceipt`, `Page`, `FinancialQuery`, and failures are defined in [Shared contracts](/technical/contracts). Browser server functions and AI tools omit context from their public arguments and supply it from trusted execution state.

## DTO projections

`Dto<table>` means the corresponding row in [Database schema](/technical/database-schema), with snake_case columns encoded as camelCase. IDs, timestamps, dates, amounts, and JSON payloads use the shared codecs. The projection excludes `ownerId`, `objectKey`, `uploadKey`, `authSubject`, `identityHash`, `payloadHash`, `leaseToken`, and deployment credentials. Nullable SQL values remain null. Other listed columns, including id, version, and timestamps where present, are included.

This rule defines a separate concrete schema for each exposed table. It is not permission to send arbitrary database rows. Tables not named in an output below are not exposed through a generic entity endpoint. `TransactionDetail` contains `posting: Dto<postings>`, `event: Dto<financial_events>`, `allocations: Dto<allocations>[]`, `counterparts: Dto<postings>[]`, `credits: Dto<cost_credits>[]`, `feeAssociations: Dto<fee_associations>[]`, `evidence: EvidenceRef[]`, `reviews: Dto<review_items>[]`, and `basis`.

`JobView` is `{id, version, kind, state: JobState, attempt, executionGeneration, deadline, cancelRequestedAt, createdAt, updatedAt}`. `ImportBatchView` contains `{id, items: {id, sourceId, filename, uploadStatus, job: JobView | null}[], totals: {files, acceptedPostings, matchedObservations, unresolvedObservations, failedFiles}}`. Counts are derived from committed records and observation dispositions.

## Financial mutations

These methods accept `Command<Input>` and return `CommandReceipt<Output>`. They allow user actors. Agent access is limited by the action authorization contract in [AI functionality](/technical/ai-functionality#mutation-authority).

### saveAccount

Input inside Command: `{accountId: Id<"account"> | null, expectedVersion: Version | null, label, currency, institution, periods: {startDate, endDate, role, offsetLoanId}[]}`

Output and invariants: `Dto<accounts>`. Null ID creates with null expectedVersion. Updates require a version. Currency cannot change after accepted postings exist.

### saveCategory

Input inside Command: `{categoryId: Id<"category"> | null, expectedVersion: Version | null, slug, label, parentId, archived}`

Output and invariants: `Dto<categories>`. Prevents hierarchy cycles and preserves referenced IDs.

### saveTag

Input inside Command: `{tagId: Id<"tag"> | null, expectedVersion: Version | null, label, archived}`

Output and invariants: `Dto<tags>`

### saveMerchant

Input inside Command: `{merchantId: Id<"merchant"> | null, expectedVersion: Version | null, label, service, aliases: string[]}`

Output and invariants: `Dto<merchants>`. Alias conflicts return InvalidInput.

### correctEvent

Input inside Command: `{eventId, expectedVersion, change: EventChange, reason: string | null}`

Output and invariants: `{event: Dto<financial_events>, correctionId}`. Amount conservation and credit eligibility are rechecked.

### linkCostCredit

Input inside Command: `{creditAllocationId, expectedCreditVersion, targets: {costAllocationId, expectedVersion, amountMinor}[]}`

Output and invariants: `{creditLinks: Dto<cost_credits>[], correctionId}`. Positive targets, matching currency, no clipping of excess.

### unlinkCostCredit

Input inside Command: `{creditLinkId, expectedCreditVersion, expectedCostVersion}`

Output and invariants: `{correctionId}`

### linkMovements

Input inside Command: `{kind: "transfer" | "cardSettlement" | "loanPayment" | "borrowing", movement: MovementLink, postingIds: Id<"posting">[], expectedEventVersions: {eventId, version}[]}`

Output and invariants: `{event: Dto<financial_events>, correctionId}`. Requires one or two postings consistent with MovementLink. A single posting requires explicit user confirmation of both owned endpoints. Attaching the missing counterpart preserves the existing confirmed event ID. Other merges replace memberships atomically and supersede replaced events.

### setFeeAssociation

Allowed actors: user; job actors may create or update proposed associations only

Input inside Command: `{feeEventId, expectedFeeVersion, purchaseEventId: Id<"event"> | null, status: "proposed" | "confirmed", evidence: EvidenceRef[]}`

Output and invariants: `{association: Dto<fee_associations> | null, correctionId}`. Null purchaseEventId removes an association and is user-only. The command validates event roles and currency, preserves amounts and dates, and cannot overwrite a user-confirmed association from a job. Job callers also supply executionGeneration.

### undoCorrection

Input inside Command: `{correctionId, expectedTargetVersions: {entityKind, id, version}[]}`

Output and invariants: `{correctionId: Id<"correction">}` for the new inverse change. Rejects when newer changes make the inverse invalid.

### savePersonalEvent

Input inside Command: `{personalEventId: Id<"personalEvent"> | null, expectedVersion: Version | null, label, period: Range | null, excludeFromOrdinary: boolean, note: string | null, allocationIds: Id<"allocation">[]}`

Output and invariants: `Dto<personal_events>`. Explicit membership includes advance bookings.

### saveContext

Input inside Command: `{contextId: Id<"context"> | null, expectedVersion: Version | null, kind, text, accountIds, merchantIds, effectivePeriod: Range | null, evidence: EvidenceRef[]}`

Output and invariants: `Dto<personal_context>` in confirmed state. Text maximum 4,000 characters.

### removeContext

Input inside Command: `{contextId, expectedVersion}`

Output and invariants: `{contextId, status: "removed"}`

### saveCommitment

Input inside Command: `{commitmentId: Id<"commitment"> | null, expectedVersion: Version | null, label, merchantId, status, effectiveFrom: CalendarDate, schedule: ScheduleDefinition}`

Output and invariants: `{commitment: Dto<commitments>, segment: Dto<commitment_segments>}`. Closes the previous effective segment.

`EventChange` is one of the following closed variants:

```ts
type EventChange =
  | { kind: "merchant"; merchantId: Id<"merchant"> | null }
  | {
      kind: "allocations";
      allocations: {
        id: Id<"allocation"> | null;
        role: AllocationRole;
        amountMinor: Minor;
        categoryId: Id<"category"> | null;
        tagIds: Id<"tag">[];
        personalEventIds: Id<"personalEvent">[];
      }[];
    }
  | { kind: "role"; eventKind: EventKind; allocations: AllocationInput[] }
  | { kind: "purchaseDate"; date: CalendarDate; evidence: EvidenceRef[] };
```

`AllocationInput` is the allocation object in the allocations variant. Existing IDs preserve credit links. Removing or reducing an allocation with linked credits requires an explicit compatible relink in a separate prepared change. Bank amounts, source dates, and posting identity are not fields of `EventChange`.

### setOccurrenceOverride

Allowed actors: user

Input inside Command: `{commitmentId, expectedCommitmentVersion, nominalDate: CalendarDate, scheduledDate: CalendarDate, servicePeriod: Range | null, status: "expected" | "skipped"}`

Output and invariants: `Dto<commitment_occurrences>`. NominalDate identifies an occurrence in an effective segment. The command changes its date or service period without changing segment membership. A matched occurrence must be unmatched first. User-supplied service periods are recorded as confirmed in the correction.

### setOccurrenceMatch

Allowed actors: user

Input inside Command: `{commitmentId, nominalDate, expectedCommitmentVersion, eventId: Id<"event"> | null, expectedEventVersion: Version | null}`

Output and invariants: `Dto<commitment_occurrences>`. An explicit match validates account, currency, and role and records user authority for date or amount exceptions. Null eventId unmatches the current event and excludes it from automatic rematching. Match changes advance the revision and refresh affected estimates.

## Previews, rules, and review resolution

`RulePredicate` contains optional exact merchantId, accountId, role, normalized description prefix up to 100 characters, and amount range. At least one field is required. Fields combine with AND. `ClassificationAction` contains categoryId and optional merchantId and tagIds. Rules do not change financial roles, bank values, refunds, or movement relationships.

`ChangeImpact` contains `{recordCount, affectedEventIds, measures: {metric: FinancialQuery["metric"], period: Range, accountIds: Id<"account">[], currency: Currency, before: Money | null, after: Money | null, coverageBefore: CoverageSummary, coverageAfter: CoverageSummary}[], reviewCount, warnings: string[]}`. Preview measures always use total normalization. Costs, income, cash balance change, and the net loan repayment effect appear when affected. The stored preview includes the exact command input and full affected set even when the UI pages it.

`PreviewInput` is a closed union of `{kind: "eventChange", change: PreparedEventChange}`, `{kind: "rule", rule: RulePreviewInput}`, `{kind: "roleRule", rule: RoleRuleInput}`, and `{kind: "sourceRemoval", sourceId, expectedVersion}`. RulePreviewInput is the previewRule input below.

PreparedEventChange is a discriminated union with operation equal to correctEvent, linkMovements, linkCostCredit, unlinkCostCredit, or undoCorrection. Each variant contains input with the exact input schema of that operation. It cannot pair one operation name with another operation's payload.

Direct correctEvent calls support single-event merchant changes, categories, tags, and evidenced purchase-date changes. Allocation edits through this path preserve IDs, roles, and amounts. Financial-role changes, splits, movement links, credit links, and undo affecting those fields enter through acceptEventChange. The method schemas above describe their shared internal operations, not alternate public routes around preview acceptance. Movement event kinds are constructed through linkMovements, not a role-only change.

`RoleRulePredicate` is `{match: {kind: "description", normalizedExact: string} | {kind: "counterpartyReference", reference: string}, expectedSign: "debit" | "credit"}`. `RoleRuleInput` contains `{ruleId: Id<"roleRule"> | null, expectedVersion: Version | null, accountId, predicate: RoleRulePredicate, role: "purchase" | "income" | "financingCost", effectiveStart: CalendarDate, effectiveEnd: CalendarDate | null, applyHistory: boolean}`.

Success: `CommandReceipt<{correctionId, affectedEventIds}>`. Reloads the stored input and checks expiry, revision, target versions, and authorization before committing once. A changed input needs a new preview.

Success: `{previewId, revision, expiresAt, impact: ChangeImpact}`

Allowed actors: user

Success: `CommandReceipt<{rule: Dto<role_rules>, jobId: Id<"job"> | null}>`. Saves the scoped user confirmation and optionally dispatches historical application.

### listRoleRules

### applyRule

Input: `Command<{previewId, expectedRevision}>`

Success: `CommandReceipt<{rule: Dto<classification_rules>, jobId: Id<"job"> | null}>`. Saves the rule, then applies a large historical set in bounded version-checked job groups.

Success: `CommandReceipt<Dto<classification_rules>>`. Does not undo historical decisions.

### listRules

Input: `{page: PageRequest}`

Success: `Page<Dto<classification_rules>>`

### resolveReview

Input: `Command<{reviewId, expectedVersion, resolution: ReviewResolution}>`

Success: `CommandReceipt<{review: Dto<review_items>, correctionId: Id<"correction"> | null}>`

`ReviewOption` contains `{id: string, label: string, resolution: ReviewResolution}`. Resolution variants are `chooseOption {optionId}`, `mapAccount {accountId}`, `matchPosting {postingId}`, `distinctPosting {}`, `useObservation {observationId}`, `classify {change: EventChange}`, `acceptChange {previewId, expectedRevision}`, `explain {text}`, and `dismiss {reason}`. chooseOption is resolved to a stored non-chooseOption value. The issue kind determines the allowed variants. Free-text explanations can resolve context questions but cannot establish unreadable amounts or duplicate identity without further evidence.

Review resolution locks the review subject, checks its version, applies the selected financial command, and marks the review resolved in the same transaction. Classify permits only direct correctEvent changes. AcceptChange checks a stored event-change preview and resolves the review atomically for role, allocation-amount, or relationship changes. Dismiss leaves unresolved financial values outside confirmed totals. Agent callers can propose review options but cannot dismiss unresolved evidence automatically.

## Processor-only RPC

Only job actors can call these methods, and each input jobId must match the caller. Every job-actor mutation, including shared model-call and artifact operations, also carries executionGeneration, checked against the current job before a new effect. Mutations return stored idempotent step outcomes keyed by jobId and stepKey. Completed compatible step outcomes can be reused by a later generation after this check.

### getJobInput

Input: `{jobId}`

Success: `JobInput`

### beginExtraction

Input: `{jobId, stepKey}`

Success: `{extractionId, replayed: boolean}`. Uses the accepted import job's source, extractor version, and input hash. Reuses an existing compatible extraction.

### stageInspection

Input: `{jobId, stepKey, extractionId, inspection: SourceInspection}`

Success: `{extractionId, segmentKeys: string[]}`. Validates source ownership and locator bounds. A completed inspection is reused on replay; changed extraction output needs a new extractor version or input hash.

### getExtraction

Input: `{jobId, extractionId, segmentKey: string | null, page: PageRequest}`

Success: `{inspection: SourceInspection | null, observations: Page<{observation: Dto<observations>, disposition: Dto<observation_dispositions> | null}>}`. The job must own this extraction. Inspection segments retain account-mapping reviews until evidence or a user answer establishes the account.

### captureReconciliation

Input: `{jobId, stepKey, extractionId, segmentKey, accountId, period: Range}`

Success: `{artifactId, revision, contentHash}`. Stores ReconciliationInput at one read snapshot after checking the segment's established account mapping. ReadArtifact supplies the immutable input. Publication uses its actual revision and repeats matching on a revision conflict.

### finalizeExtraction

Input: `{jobId, stepKey, extractionId, expectedRevision}`

Success: `{revision, sourceCoverage: SourceCoverage[], reviewIds}`. Checks all staged segment rows and dispositions, writes supported coverage and statement summaries, and sets extraction status. Segment failures produce specific reviews. Only changed financial coverage advances the revision. The same receipt is returned on replay.

### captureSnapshot

Input: `{jobId, stepKey, definition: AnalysisDefinition | null}`

Success: `{snapshotId, revision, definition: AnalysisDefinition, manifest: SnapshotManifest}`. Analysis jobs pass null: the API resolves their accepted definition and basis. Refresh and interpretation jobs supply a resolved definition within their accepted account and event scope. Extraction includes the supporting postings and interpretation records required by that work. The API captures rows and contextGeneration together, then persists the snapshot and step outcome. Retries reuse the same resolved dates and data.

### commitRoles

Input: `{jobId, stepKey, expectedRevision, decisions: RoleDecision[]}`

Success: `{revision, appliedEventIds, reviewIds}`. Revalidates source markers or user-accepted role rules.

### stageObservations

Input: `{jobId, stepKey, extractionId, segmentKey, observations: ParsedObservation[]}`

Success: `{stagedCount, observationIds}`

### publishPostingGroup

Input: `{jobId, stepKey, expectedRevision, group: PostingPublication}`

Success: `{revision, acceptedPostingIds, matchedObservationIds, reviewIds}`

### commitInterpretations

Input: `{jobId, stepKey, expectedRevision, decisions: InterpretationDecision[]}`

Success: `{revision, appliedEventIds, reviewIds}`

### commitOccurrenceMatches

Input: `{jobId, stepKey, expectedRevision, matches: {commitmentId, nominalDate, expectedCommitmentVersion, eventId, expectedEventVersion}[]}`

Success: `{revision, matchedOccurrenceIds, reviewIds}`. Rechecks the occurrence-matching policy against current records, including uniqueness and explicit exclusions. It preserves valid user matches and records ambiguous candidates for review. Groups contain at most 200 matches. Event and schedule mutations also invalidate incompatible existing matches in their financial transaction.

### applyRuleGroup

Input: `{jobId, stepKey, expectedRevision, events: {eventId, expectedVersion}[]}`

Success: `{revision, appliedEventIds, reviewIds}`. Loads the rule and preview from the accepted applyRule job. At most 200 events must belong to that preview's affected set. The command preserves individual corrections and reports changed targets as conflicts.

### publishRefresh

Input: `{jobId, stepKey, expectedRevision, commitments: CommitmentProposal[], insights: InsightPublication[], intentions: {intentionId, expectedVersion, resultId}[]}`

Success: `{commitmentIds, insightIds, intentionIds, publication: "current" | "historical"}`. A group contains at most 200 entries. New proposals and derived pointers do not advance the financial revision. Stale results remain historical and enqueue a current refresh. Accepted schedules and dismissed unchanged findings retain their user state.

CommitmentProposal is `{detectorKey, label, merchantId, effectiveFrom, schedule: ScheduleDefinition, evidence: EvidenceRef[]}`. DetectorKey hashes the policy version, series identity, cadence, and first evidenced occurrence. The API upserts that proposed commitment and never overwrites an accepted schedule. InsightPublication is `{fingerprint, detector, resultId, impact: Money, rank: number}`. The API checks result ownership, revision, currency, detector thresholds, and rank before publication. Intention result publication checks the saved intention version and the resolved current period. Each result retains its resolved queries and evidence.

### publishAnalysis

Input: `{jobId, stepKey, snapshotId, definitionHash, result: AnalysisResultData, evidence: EvidenceRef[]}`

Success: `{resultId, publication: "current" | "historical"}`

### checkpointJob

Input: `{jobId, stepKey, expectedVersion, state: JobState}`

Success: `JobView`

Artifact transfer uses authenticated private HTTP streams. A worker does not receive production SQL credentials or arbitrary R2 access from these calls. The payload schemas and step identities are in [Import and job protocols](/technical/import-protocol).

## Export and maintenance RPC

These API methods allow only the owning export, backup, or source-removal job as stated. They use jobId, stepKey, and executionGeneration fencing like other processor mutations. The API owns source and backup storage operations.

### readSource

Allowed actors: user, owning job, or agent with source evidence in its snapshot

Input: `{sourceId}` through streaming HTTP

Success: the available source's content stream. Import jobs can read their accepted source. Export and backup jobs can read sources in their frozen export manifest. The handler derives the owner from trusted caller context and never accepts an object key.

### prepareExport

Allowed actors: owning export or portable-backup job

Input: `{jobId, stepKey}`

Success: `{artifactId, manifest: ExportManifest}`. Captures canonical entities and the manifest at one REPEATABLE READ snapshot. ExportManifest contains `{schemaVersion: 1, revision, contextGeneration: ContextGeneration, capturedAt, schemaMigrationVersion, rowCounts: {table, count}[], recordArtifactId, sourceIds, artifactIds, conversations: {conversationId, throughSequence, submissionIds, completedAnswerIds}[]}`. IDs identify records represented by the captured database state. Include flags come from the accepted job. Source objects are pinned until package verification finishes.

### getExportScope

Allowed actors: owning export or portable-backup job, including the trusted analyst export adapter acting for that job

Input: `{jobId, conversationId}`

Success: `{ownerId, throughSequence, submissionIds, completedAnswerIds}` from the prepared export. Rejects conversations and job kinds outside that manifest. This private response supplies routing identity to the analyst and is not a browser DTO.

### completeExport

Allowed actors: owning export or portable-backup job

Input: `{jobId, stepKey, artifactId, conversationArtifactIds: Id<"artifact">[]}`

Success: `{artifactId, completedAt}`. Verifies the package against the frozen manifest, including hashes, entity counts, and conversation reconciliation records. Portable backups additionally copy and verify referenced bytes in backup storage before publishing the retained manifest. User downloads expire after seven days; backups use Operations retention.

### runDatabaseBackup

Allowed actors: owning database-backup job

Input: `{jobId, stepKey}`

Success: `{artifactId, completedAt}`. The API runs the fixed pg_dump task in its maintenance Container with the dedicated backup connection, streams its output to backup storage, and verifies the artifact before recording completion. This operation has no generated-code input. Its runtime and retention are defined in Operations.

### completeSourceRemoval

Allowed actors: owning removeSource job

Input: `{jobId, stepKey}`

Success: `{sourceId, affectedPostingIds, affectedResultIds, withdrawalCorrectionId}`. Deletes only the object recorded for the accepted removal version and commits removed status after successful deletion. Missing bytes on replay are compatible with completion. A newer source version cannot become a deletion target.

### exportConversation

Owner: analyst Worker, exposed only through the processor's private export binding

Allowed actors: owning export or portable-backup job

Input: `{jobId, executionGeneration, stepKey, conversationId}`

Success: `{artifactId, throughSequence, pendingRunIds}`. The analyst validates getExportScope through the API, routes to the owner-bound conversation, and exports the longest canonical message prefix represented by the accepted submissions and completed answers in that scope. Incomplete database/message pairs enter pendingRunIds rather than introducing references absent from the backup. Before streaming, the analyst freezes the prefix's last message ID in application-owned Durable Object state under jobId and stepKey. Retries retain that prefix even if later messages become available. Message export uses the SDK's supported message interface. The analyst registers and uploads the export artifact under the requesting job through the API; the processor receives no general conversation or writable storage capability. Replays return the recorded artifact.

These methods are private to agent actors, with runId matching `CallerContext`. `acceptRun` is called by the authenticated conversation ingress with user context, before an agent context exists.

### listConversations

### startChildRun

### captureRunSnapshot

## Private content streams

These paths exist only on the API service binding. A runtime adapter constructs the `X-Ironcage-Context` header from its trusted CallerContext, encoded as base64url JSON. It replaces any incoming header instead of forwarding browser input. The API decodes the header and applies the same actor and ownership checks as RPC. Job uploads also carry their current execution generation.

| Path                                      | Method              | Authorization                                                                        |
| ----------------------------------------- | ------------------- | ------------------------------------------------------------------------------------ |
| `/internal/sources/:sourceId/content`     | GET, optional Range | readSource scope and available source status.                                        |
| `/internal/artifacts/:artifactId/content` | GET                 | readArtifact scope.                                                                  |
| `/internal/artifacts/:artifactId/content` | PUT raw bytes       | Unexpired artifact_uploads grant for the calling job or run, matching size and hash. |

RegisterArtifact returns the private PUT path. Browser downloads use the authenticated public web routes below; the web adapter supplies user context on the private hop. No source or artifact route accepts a client-selected object key.

## Browser HTTP and conversation boundaries

| Route                                | Method and body                                              | Result                                                                                                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/imports/:itemId/content`       | PUT raw bytes, declared Content-Type, `Idempotency-Key` UUID | 202 `{sourceId, jobId: Id<"job"> \| null, repeatedSource, restoredSource, withdrawalCorrectionId: Id<"correction"> \| null}`. The server verifies bytes, hashes content, and registers the source. |

| `/api/artifacts/:artifactId/content` | GET                                                          | Authenticated artifact stream.                                                                                                                                                                     |
| `/api/analyst/:conversationId/*`     | SDK HTTP, streaming, and WebSocket protocol                  | Authenticated routing to the owner-bound AIChatAgent through its cross-script Durable Object namespace binding. SDK message frames are not replaced by a custom chat protocol.                     |

Financial screen reads and commands use typed TanStack Start server functions that call the RPC methods. The upload path expires after one hour before upload begins. Limits are 100 files per batch, 33,554,432 bytes per file, displayed as 32 MiB, and 500 PDF pages per file. Larger limits require configuration and resource validation, not silent truncation. The importer must accommodate every supplied file.

Browser mutations validate origin and session before forwarding. The web Worker owns the HTTP and WebSocket ingress and binds directly to the analyst-owned Durable Object namespace. The analyst Worker exports the class and owns migrations; no intermediate analyst HTTP proxy is deployed. Routing translates the app path to the SDK route and exposes only the analyst namespace. Deployment tests cover authentication, owner-derived instance names, upgrades, streaming, and reconnects. Each conversation identity is derived from the authenticated owner and its conversation UUID. A browser cannot route itself to another owner's Durable Object by changing the URL.

## Worked correction exchange

The fictional request changes one purchase to the strata category. The UUIDs and amounts are fictional.

```json
{
  "schemaVersion": 1,
  "commandId": "00000000-0000-4000-8000-000000000001",
  "input": {
    "eventId": "00000000-0000-4000-8000-000000000002",
    "expectedVersion": 3,
    "change": {
      "kind": "allocations",
      "allocations": [
        {
          "id": "00000000-0000-4000-8000-000000000003",
          "role": "cost",
          "amountMinor": "125000",
          "categoryId": "00000000-0000-4000-8000-000000000004",
          "tagIds": [],
          "personalEventIds": []
        }
      ]
    },
    "reason": "Quarterly strata levy"
  }
}
```

Success contains the same commandId, the committed timestamp, the new dataset revision, event version 4, correctionId, and invalidations for the affected date range. Repeating the request returns that exact receipt. Sending expectedVersion 3 under a new command ID returns `VersionConflict` once version 4 exists.

A stale version is represented at the browser boundary as HTTP 409:

```json
{
  "schemaVersion": 1,
  "error": {
    "_tag": "VersionConflict",
    "message": "This event changed since you opened it.",
    "details": {
      "entityKind": "event",
      "id": "00000000-0000-4000-8000-000000000002",
      "expectedVersion": 3,
      "currentVersion": 4
    }
  },
  "requestId": "00000000-0000-4000-8000-000000000005"
}
```

The native RPC caller receives the corresponding tagged `VersionConflict` value. The HTTP envelope belongs only to the browser adapter.
