# AI

Every line of AI code lives in `ironcage-agents`, a Flue application ([D10](./00-decisions.md#d10)). The engine never calls a model; it reads validated rows that agents produced earlier. This chapter specifies the Flue application's shape, the AI Gateway configuration, the capability runtime end to end, the registry and model configuration, scorecards and demotion, and the design-time agents.

The one-sentence contract, repeated from the [overview](./01-overview.md) because everything here serves it: **agents produce data; the engine validates, clamps, and decides what that data is allowed to mean.**

## The Flue application

One Flue agent per capability, plus the design-time agents. A Flue agent is a function composing hooks (`useModel`, `useTool`, `useSkill`, …); Flue generates a Durable Object class per agent, and each run/conversation is an instance holding its own transcript — Flue's machinery, holding conversations only, never engine state ([Topology](./02-topology.md)).

- **Simple capabilities stay simple**: the regime assessment is an agent whose whole body is "given this context, produce this structured assessment" — no tools, no loop. It lives in Flue anyway so that growth (skills, follow-up reasoning, context documents) never requires migration — the recorded rationale of [D10](./00-decisions.md#d10).
- **Scheduling** is the agents Worker's own: cron triggers dispatch signal messages to the right agent on each capability's cadence. The engine is not the scheduler and does not wait — it reads whatever the last run persisted.
- **Context access** is exclusively the read-only `AgentReadApi` on core ([D24](./00-decisions.md#d24)): candles, positions, mandate text, scorecards, recorded events. What an agent read is part of its decision record.
- **Output delivery** is exclusively the decision-records Queue ([D25](./00-decisions.md#d25)). An agent has no other write path into the system.
- **Versions are pinned** (Flue, Pi, providers), upgraded deliberately — the same posture as Effect ([D1](./00-decisions.md#d1)).

## AI Gateway

All model traffic routes through AI Gateway ([D11](./00-decisions.md#d11)). Because Flue's default providers ship directly to the vendor, the agents Worker **registers gateway-fronted providers at startup** — same provider IDs, base URLs pointed at our gateway — so every `useModel('anthropic/…')` in any agent resolves through the gateway without per-agent care. This registration is treated as part of the platform seam, tested by an integration check that fails the build if any configured provider resolves to a vendor-direct URL.

Per-call request metadata carries the capability name and run ID, which is what makes AI Gateway's cost accounting _per-capability_ — the number Portfolio's cost display and the weekly review's "is the AI worth it?" verdict read. Gateway-level spend caps back the per-capability budgets; hitting one is a failed run (visible, safe-defaulted), never a silent degradation.

## The capability runtime

The full path of one run-time capability tick, using the regime assessment as the worked example:

1. **Dispatch.** The agents Worker's cron fires on the capability's cadence and dispatches the agent with the tick's identity: capability, config version, cadence timestamp. Dispatch is idempotent on that identity — a duplicate cron firing re-enters the same run, not a second one.
2. **Context.** The agent pulls what its registry entry declares it consumes — via `AgentReadApi` only. For the regime assessment: recent candles per instrument, current positions, the calendar/news inputs its config names.
3. **Inference.** The agent asks its configured model for the structured output — per instrument, the named axes on the quantized ladder, each with rationale and cited sources. Model and parameters come from the capability's versioned configuration, not from code.
4. **Wire validation.** The agent validates the model's answer against the output schema at its own boundary (Flue's schema layer — wire-level, [D10](./00-decisions.md#d10)). A model answer that won't parse after the configured retries makes this a **failed run**: the failure itself is the output.
5. **Delivery.** The agent enqueues one message: the capability output (or the failure), the decision record (what was asked, what data mattered, what was decided, why, model, timing, gateway log IDs), and the run identity. At-least-once delivery; the message ID is the run ID.
6. **Authoritative validation and write.** Core's queue consumer decodes the message with the Effect Schema from `packages/contracts` — the authoritative validation, regardless of what the agent already checked. In one transaction it writes the `capability_outputs` row (with `valid_until` precomputed from the registry's staleness window), the `decision_records` row, and the feed event (`notice` for a material change, `warning` for a failed run). Duplicate run IDs are dropped harmlessly.
7. **Consumption.** The next sleeve tick reads the latest valid output ([Engine](./04-engine.md) step 4). Stale, absent, or failed → the safe default. Nothing about a failed AI run can delay, block, or alter the tick's schedule.

The engine-side guarantee this sequence produces: **the model's words never touch the engine — only rows that survived two validations and carry their own provenance.**

## The registry and configuration

The capability registry ([Sleeves](../product/02-sleeves.md)) is **typed code in `packages/domain`**: each entry declares its identity and safety class, what it consumes, its output Schema, the consuming engine component, cadence, staleness window, safe default, baseline definition, and default demotion rule. Being code, registry changes are reviewed and versioned like engine changes — which is exactly the discipline the product demands for new capabilities.

Two things are data, not code:

- **Per-sleeve parameters** live in the mandate (which capabilities a sleeve holds, their thresholds, the combiner choice).
- **Model selection** — provider, model, inference parameters per capability — is versioned configuration in Postgres ([D11](./00-decisions.md#d11)), read at dispatch, recorded on every decision record. Changing a model is a recorded configuration act, and scorecards are attributable to the configuration that produced them.

## Scorecards, baselines, demotion

Capabilities follow evidence, mechanically:

- **The counterfactual is computed by the engine, not the AI.** Every tick, alongside the real evaluation, the sleeve actor evaluates what it would have done with the capability at its safe default (the registry's declared baseline), runs both through the same simulated-fill machinery as dry run, and accrues the deltas — P&L, drawdown, costs — as scorecard rows ([Data](./03-data.md)). The AI is never asked to grade itself.
- **Demotion is automatic.** The registry's demotion rule (tightenable per mandate) is evaluated on schedule against the scorecard. Breach → the capability is **suspended**: its outputs are ignored (safe default applies), a `critical` feed event fires, and the suspension lands in Overview's attention items. Suspension is cage-side state — the agent may keep running and writing rows; the engine stops listening.
- **Reinstatement is a ceremony**, from the scorecard evidence, recorded like every other decision.

Design-time capabilities carry the analogous scorecard over their proposals — submitted, passed gates, survived live, value added — computed from the proposals table, not self-reported.

## Observers and the categorization agent

Observer capabilities (calibration audit, allocation memo, red-team scenarios, report generation) run the same runtime with two differences: their cadence is slower, and their output is a document or recommendation rather than an engine input — delivered through the same queue, stored as reports ([Data](./03-data.md)) with bodies in R2, zero execution risk by construction since no engine component consumes them as behavior.

The Money view's categorization is a capability like any other: dispatched after an import with the uncategorized rows as context, returning per-transaction category + confidence; core applies high-confidence assignments, queues the rest for review, and every assignment's decision record links from the transaction. Corrections create rules ([Money](../product/05-money.md)) — and rules short-circuit the agent entirely: a rule-matched transaction never reaches a model.

## Design-time agents

The proposal-producing agents — parameter tuning, strategy variants — and the operator's research agent:

- **Workspace**: design-time agents may hold a Computer workspace ([D16](./00-decisions.md#d16)) — files, git, code execution on the Worker-based backends — with reference data mounted read-only from R2. Run-time capabilities never have one.
- **Output**: a proposal bundle — the mandate diff or strategy variant, its rationale, and its supporting analysis — committed to Artifacts ([D13](./00-decisions.md#d13)), then registered via the queue as a `proposals` row. The commit is the immutable fact; the gate pipeline ([Workbench](./07-workbench.md)) takes it from there. An agent cannot advance its own proposal's state — only the pipeline and the operator do.
- **Trial discipline**: concurrent trials are capped and every backtest increments the trial count ([Workbench](./07-workbench.md)) — the multiplicity bookkeeping that keeps a prolific proposer from laundering luck into evidence is enforced where trials run, not where they're proposed.
- **Conversation**: the operator can talk to the research agent from the Workbench UI (`@flue/react` through the app proxy, [App](./09-app.md)). Conversations are Flue's DO transcripts — debugging-grade record ([D12](./00-decisions.md#d12)); anything that matters graduates to a proposal or a decision record.

## Failure posture

The agents Worker is designed to be losable. If it is down, misconfigured, out of budget, or shipping garbage: capability outputs go stale on schedule, the engine degrades every consumer to its safe default, vitals show the failed runs, and trading continues — more cautiously than before, by construction. There is no AI failure mode that makes the system _bolder_, and none that makes it stop being auditable. The worst case the architecture permits is a fully clockwork Ironcage with a red "AI runs" vital — which is a bad week, not an incident.
