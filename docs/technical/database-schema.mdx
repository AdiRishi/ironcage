Migrations under `workers/api/migrations/` and their inferred schemas own exact columns and indexes once implemented. The record groups below define required meaning and relationships. Add tables and fields with their owning [stage](/technical/stage-boundaries), using the smallest relational design that supports its queries.

## Conventions

Records have stable IDs and authenticated ownership. Mutable records have versions and timestamps. Foreign keys preserve evidence and financial relationships; owner-scoped links cannot cross owners. Booked money uses BIGINT with an explicit currency, dates use DATE, and timestamps use TIMESTAMPTZ. Index source identity, posting account/date queries, and actual relationship lookups.

Use relational columns for financial identity, money, dates, and queryable relationships. JSON is appropriate for literal parser fields, review details, saved query definitions, and SDK-independent notes. It does not replace constraints on money or ownership.

## Stage 1: sources and bank postings

| Record           | Required data and constraints                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner            | Authenticated subject. The application has one authorized user.                                                                                                                       |
| Account          | Stable bank identity, label, currency, and evidenced account role. Masked suffix alone is insufficient identity. Effective role changes retain earlier periods.                       |
| Source file      | Owner, verified hash, filename, media type, byte count, private object reference, and availability. Owner plus hash is unique.                                                        |
| Import           | Source, selected account when needed, parser version, platform execution reference, status, summary, and failure or review information. A batch groups independently processed files. |
| Observation      | Source, parser version, stable row/page locator, literal fields, normalized candidate, and disposition. Repeated processing of the same source row cannot publish another occurrence. |
| Posting          | Account, currency, signed booked amount, posting date, optional evidenced purchase/value dates, description, and optional original money.                                             |
| Posting evidence | Observation-to-posting relationship and the evidence for an exact, identifier, or user-confirmed match. One observation supports at most one posting.                                 |
| Coverage         | Source/account interval, stated and observed coverage, balance anchors and supplied totals, and whether reconciliation established completeness.                                      |
| Review item      | Specific source rows, issue, candidate decisions, and user resolution. Repeated processing preserves accepted matches and distinct-purchase decisions.                                |
| Command receipt  | Owner and command ID are unique. Stores input identity and committed financial response.                                                                                              |
| Settings         | Timezone, reporting currency, and implemented user preferences.                                                                                                                       |

An import can store its summary and review details without separate job-step, extraction-dispatch, or artifact registries. Choose separate observation or coverage tables where querying requires them. Do not create interpretation records in stage 1.

Within one source's extraction, two transaction occurrences cannot share one posting. The same posting can have evidence from several overlapping files. The publication transaction enforces this rule alongside the unique source and observation constraints.

## Stage 2: document evidence and data controls

PDF observations use page locators and the same posting model. Source removal retains postings and their extracted evidence, while marking the original file unavailable. Reuploading verified identical bytes restores source access without creating new postings.

Exports read implemented financial records and evidence relationships. Temporary download metadata is sufficient for an export that needs background processing. AI usage records store task, model, timestamp, reported tokens, and reported or estimated cost when available. Failed calls may have unknown usage, which remains labelled unknown.

## Stage 3: interpretation

| Record                                 | Required relationship                                                                                                             |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Financial event and posting membership | Groups a purchase, movement, credit, financing cost, or unresolved interpretation. A posting belongs to at most one active event. |
| Allocation                             | Nonnegative part of an event, with role and cost category where applicable. Allocations sum exactly to event magnitude.           |
| Reference data                         | Editable categories, merchants and aliases, tags, and personal events. Renaming preserves identity.                               |
| Credit link                            | Applied amount from refund/reimbursement allocation to cost allocation, in one currency and within both remaining amounts.        |
| Fee association                        | Evidence that a separate fee relates to a purchase. The fee keeps its own amount and date.                                        |
| Correction                             | Prior and accepted interpretation, actor, time, and scope. User overrides survive later classification.                           |
| Rule                                   | User-accepted conditions, action, and historical or future scope. Conflicts require review.                                       |

Tags and personal-event membership can overlap. Event posting links and allocation conservation change atomically. Transfers use the amount moved once, even when both account postings are present. Interest is never moved into a repayment event to make its dates agree.

Stage 3 introduces these records through a migration and an explicit interpretation action for existing postings. Uninterpreted history remains visible without placeholder allocations. Accepted bank-field corrections require replacement evidence; category edits cannot change bank-booked amounts.

## Stage 4: saved queries

A saved analysis contains a name, query definition, and fixed or relative date selection. Ordinary calculation results are returned on demand. There is no mandatory snapshot store, current-result pointer, result-history table, or refresh queue.

## Stage 5: commitments and scenarios

Commitments store confirmed amount, cadence, account, effective dates, and optional service periods. Amount or account changes preserve earlier schedule segments. Explicit occurrence matches link a payment once, and user exclusions prevent a rejected match from immediately returning. Proposed schedules stay distinguishable from confirmed schedules.

Scenarios store named assumptions and overrides. They do not alter bank records or baseline commitments. Estimates are computed when viewed.

## Stage 6: conversations and notes

AIChatAgent owns canonical conversation messages in its own storage. The API stores explicit personal notes with their applicable account or period when supplied. Financial records do not require parallel AI run, step, intent, or authorization tables. The SDK owns conversation execution and streaming.

## Stage 7: findings and intentions

Findings store the detector, subject, comparison period, evidence, and user state. Stable identity prevents duplicate findings. Intentions store the chosen baseline, measure, start date, and explicit related-cost assumptions. Inbox records reference existing findings or actions and retain read/dismissed state. Reminder preferences belong to settings.

## Transaction example

A reimbursement command checks its receipt and current allocation versions under the financial write lock. A 30000-minor-unit cost linked to a 20000-minor-unit reimbursement leaves 10000. A second request to apply another 20000 rejects the excess instead of clipping it. The link, correction, and command receipt commit together; a failed check changes none of them.

The complete concurrency rule is in [Financial records and metrics](/technical/financial-model#persistence-and-concurrency).
