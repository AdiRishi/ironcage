This is the target schema for migrations under `workers/api/migrations/`. Names in this page are SQL names. The [shared contracts](/technical/contracts) define encoded values and the [financial model](/technical/financial-model) defines accounting meaning.

## Conventions

Unless stated otherwise, every table has `id UUID PRIMARY KEY`, `owner_id UUID NOT NULL REFERENCES owners(id)`, and `created_at TIMESTAMPTZ NOT NULL`. Mutable tables also have `version INTEGER NOT NULL DEFAULT 1 CHECK (version > 0)` and `updated_at TIMESTAMPTZ NOT NULL`. Version increases once per committed modification.

The listings below show additional columns. `?` means nullable. All other columns are `NOT NULL`. `FK(table)` means UUID referencing that table. `enum(...)` is text with a `CHECK` constraint. `json(Type)` means JSONB validated against the named versioned application schema. Every entity has `UNIQUE(owner_id, id)`, and foreign keys between owner-scoped records include owner_id to prevent cross-owner relationships. Creation and update timestamps come from the database clock.

Every foreign-key column has an index unless already covered by an index with that leading column. Destructive cascades are limited to disposable staging records. Canonical records, corrections, evidence, and command receipts use explicit deletion commands.

| `cost_credits`      | `credit_allocation_id FK(allocations)`, `cost_allocation_id FK(allocations)`, `amount_minor BIGINT`                                                                                                                                                                                                                                                                              | Positive amount. Unique pair. Credit role is refund or reimbursement. Totals cannot exceed either the credit allocation or remaining eligible cost. Same currency required.                                                   |

One transfer event can contain both bank postings. The event magnitude is the transferred amount, not the sum of both absolute posting amounts. Refunds are separate events joined to costs through cost_credits. They never overwrite the original purchase.

A loan payment with separately evidenced interest can contain payment, counterpart, and interest postings. Its allocations partition the payment into cost and principal. An interest posting already included there cannot create a second financing-cost event. Exact construction rules and the mortgage example are in [Calculation rules](/technical/calculation-rules#financial-event-construction).

Within one extraction, two observations cannot map to the same posting. Owner-locked publication enforces this multiplicity constraint and consistency between posting_sources and observation_dispositions. Matching one posting from different files is permitted.

Changing a posting's amount or date requires a source-resolution command with replacement evidence. Ordinary category corrections cannot edit bank-booked fields. An update preserves its previous encoded entity in the audit record and marks dependent results affected.

## Transaction example

For a reimbursement link, the transaction locks dataset_heads, checks command_receipts, then loads the credit allocation and target cost allocations. It verifies their versions, currency, and remaining eligible amounts. The transaction inserts cost_credits, records corrections, increments the revision, creates refresh jobs and dispatch records, and stores the receipt before commit. Any failed validation leaves every table unchanged.

The test fixture has a cost of `30000` AUD minor units and a credit of `20000`. Linking that credit produces net cost `10000`. A concurrent second attempt to apply another `20000` credit can apply at most the remaining `10000`, and therefore rejects the requested amount rather than silently clipping it.
