Stage 1 supports CSV and OFX. Stage 2 adds PDF and validates the full supplied corpus. Import succeeds independently of interpretation, which begins in stage 3. [Import protocol](/technical/import-protocol) defines normalization, matching, and safe publication.

## Actual CommBank files

The actual files are in `fixtures/commbank/`, which is Git-ignored and local only. Read `fixtures/README.md` and inspect those files when implementing parser behavior. Preserve the originals and keep private contents out of tracked fixtures, build output, and ordinary logs.

The README inside that directory describes the previous application. Its pairing requirements and import order are historical context, not requirements for this implementation. CSV and OFX must each work independently.

The September 2026 corpus contains 26 CSV, 26 OFX, and 47 PDF files, approximately 45 MiB in total. The largest file is approximately 2.6 MiB. These sizes support starting with per-file processing; measure decoded rows and runtime use before selecting resource limits.

## Parsing libraries

| Format | Starting point                                                                            | Application responsibility                                                                                                  |
| ------ | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| CSV    | csv-parse, already used in this repository.                                               | CommBank column meanings, exact amounts, dates, signs, and locators.                                                        |
| OFX    | Evaluate a maintained parser such as [ofx-js](https://github.com/bradenmacdonald/ofx-js). | Preserve literal values and support the supplied OFX 1.02 SGML, encoding, account metadata, dates, and empty or reused IDs. |
| PDF    | [unpdf](https://github.com/unjs/unpdf), using its serverless PDF.js build.                | Group positioned text into CommBank statement rows and validate their meaning.                                              |

A candidate OFX library is not accepted until it handles the actual fixtures without losing exact monetary strings or source evidence. If it needs an adapter, keep that adapter focused on the demonstrated gap. A generic XML parser alone cannot parse SGML with omitted leaf closing tags.

Use the library's normal parser API for files that fit memory. Streaming or another runtime is a response to measured resource limits, not an initial architecture requirement.

## PDF library selection

The evaluated baseline is unpdf 1.8.1 with bundled PDF.js 6.1.200. The September 2026 comparison covered five PDFs, 25 pages, and 303 manually verified transaction rows. A layout decoder and visually established card-decimal repair matched all transaction dates and signed amounts and all 258 available running balances. Native Python extraction did not improve those results.

That sample supports the library choice but does not establish full-corpus completion. Check every supplied PDF in stage 2. Keep raw strings and positions, including when applying a verified layout repair. Do not infer missing decimals solely to force a balance to agree.

An unresolved page is shown for user inspection. If actual documents require model extraction, use one supported document-input path and validate its output. Do not require a rendering Container, OCR pipeline, or provider fallback chain in advance. A reproducible decoder defect remains implementation work; a specific unreadable or conflicting fact can require a user decision.

## Upload and recording flow

1. Verify and retain the uploaded bytes. Identify an existing source by owner and hash.
2. Resolve the account using source metadata or a user choice. A filename or masked suffix alone is insufficient evidence.
3. Parse the file using the selected library and source profile.
4. Validate amounts, dates, signs, and supplied balances. Match against current accepted postings using the deterministic protocol.
5. Atomically publish the file's accepted records, evidence, reviews, coverage, and summary.
6. Show the transaction list and any specific decisions the user still needs to make.

Coverage distinguishes requested export dates, observed rows, stated intervals, and reconciled history. A matching pair of balance anchors can establish a period with no transactions. Missing records are never represented as zero spending.

## Human review and repeat actions

The review UI shows the source row, uncertainty, and candidate choices. It supports confirming an account, resolving source conflicts, matching an existing posting, or declaring a distinct purchase. Reprocessing preserves those decisions. Dismissing an unreadable amount does not make it valid.

A failed file can be retried or uploaded again. Other files complete independently. The importer may repeat parsing, but source and observation identities prevent repeated financial publication. Sources and bank postings remain usable even when categorization is unavailable.
