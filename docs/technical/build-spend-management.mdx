Use this guide when asked to build Ironcage. The repository contains the project requirements and design. You do not need the discovery conversation or the author's working notes.

## Establish the full scope

Read the [vision](/vision), every feature page linked from [Product](/product), and the [acceptance scenarios](/product/acceptance). Then read the [technical design](/technical) and its references.

Create a work plan that accounts for every specified behavior. Link each part to its product contract, implementation owner, and verification evidence. Include settings, review, recovery, and background refresh alongside the main financial views.

Use acceptance scenarios as concrete examples of the contract. The feature pages also contain requirements. Completion means the whole spend-management scope works together.

## Apply the design to the repository

Inspect the existing code and dependency versions before editing. Keep its strong typing, Effect service composition, Alchemy infrastructure ownership, and Worker RPC conventions. Replace sample application behavior with the financial application described in [Architecture](/technical/architecture).

Inspect the [actual CommBank files](/technical/ingestion#actual-commbank-files) in `fixtures/commbank/` when developing import and financial-data behavior. Use their contents to verify assumptions about formats, account identifiers, overlaps, and coverage.

Use [Monorepo and ownership](/technical/monorepo) for workspace responsibilities, package exports, infrastructure ownership, and import rules. Adapt private files when existing shared logic provides a better home. Preserve public contracts and service responsibilities, and record any necessary design change in the affected page.

## Resolve engineering choices

Use the selected frameworks and the project-specific policies in these docs. Consult official documentation and matching package source for third-party API usage, supported limits, and integration details.

Use the [decision ownership and status](/technical#design-status) policy. Implement the shared contracts, schema, RPC, and processing references together. If implementation evidence exposes a contradiction or missing contract, resolve it on the owning reference page before adding dependent behavior. Product behavior and financial invariants remain the acceptance boundary.

Choose compatible library versions and model IDs using the documented evaluation gates. Tune versioned thresholds only with recorded evidence, and update the affected specification before changing its contract. Internal function decomposition and framework API syntax remain implementation choices.

Verify authenticated analyst namespace routing, direct outbox-to-Workflow dispatch, source extraction, and the Effect Postgres connection through Hyperdrive early. Include atomic financial publication, stable snapshots, and recovery after a lost commit response. Keep the resulting checks with their owning modules.

Use concrete review items for missing financial facts. For example, an unknown account relationship remains unresolved until evidence or the user's answer establishes it. Continue implementing the surrounding behavior without inventing personal context.

If an external credential, deployment identity, or private source is unavailable, implement and verify the available paths with representative fixtures. Record the exact external check that remains. Distinguish that limitation from a completed live integration.

## Connect every product flow

Build in dependency order, with connected behavior at each step:

1. Implement the Postgres schema and transaction protocol in the [financial model](/technical/financial-model), then the [ingestion pipeline](/technical/ingestion). Establish canonical history, source evidence, review, corrections, and retry behavior.
2. Connect the [workspace](/product/workspace) and [transactions](/product/transactions) through the shared financial API. Verify that a correction updates every affected view coherently.
3. Implement [trends](/product/trends), [commitments and forecasts](/product/commitments-and-forecasts), and saved analyses using the shared [calculation services](/technical/analytics).
4. Connect the [analyst and memory](/product/analyst-and-memory) to those services through the [agent runtime](/technical/ai-analyst). Include clarification, reconnection, cancellation, and reproducible computational investigations.
5. Complete [insights and follow-through](/product/insights-and-follow-through), settings, exports, and source removal. Verify refresh and invalidation after new records, corrections, and context changes.

Apply the [frontend requirements](/technical/frontend) and [operating policy](/technical/operations) throughout this work. The sequence resolves dependencies. All steps belong to the requested product.

## Establish completion

Run the checks defined in [Verification](/technical/verification). Map each product requirement to working behavior and evidence. Record model evaluation results, forecast comparisons, and any remaining external checks with enough context to repeat them.

Account for every supplied CSV, OFX, and PDF file during private-corpus validation. Distinguish accepted records, matched observations, and specific unresolved evidence. Fix parser or reconciliation defects rather than treating a general review state as successful ingestion.

Exercise the connected experience on desktop and mobile. Verify imports through evidence-backed answers, corrections through refreshed results, and interruptions through truthful recovery states. Verify access and restoration using the operating policy.

Replace obsolete sample routes and behavior as their product replacements land. Update documentation that no longer matches the implemented design. Finish with a completion report that identifies the verified scope, evidence locations, and any work still outstanding.
