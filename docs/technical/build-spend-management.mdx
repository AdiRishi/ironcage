---
title: Build one stage
description: Select a bounded deliverable, build its frontend and backend, verify it, and stop.
---

Start with [Delivery stages](/stages). Unless the task names another stage, the implementation target is [stage 1](/stages/record-transactions). The references describe the eventual product; they do not authorize implementing later stages.

## Establish the selected scope

Read the selected stage's outcome, user flows, backend responsibilities, exclusions, reading path, and completion evidence. Inspect the repository to establish what already works. For a later stage, verify the prerequisites and identify any missing earlier behavior before proceeding. A stage listing is not an implementation status report.

Read the product and technical sections named by that stage. [Stage boundaries](/technical/stage-boundaries) assigns shared records, interfaces, jobs, and controls to their introduction stages. [Product acceptance](/product/acceptance) assigns concrete scenarios. Build a short work plan for that scope with frontend, backend, integration, and verification work attached to each user outcome.

Stage pages own delivery scope. Product pages own behavior, and technical references own contracts and invariants. Resolve a missing dependency in the owning stage and affected reference before adding dependent behavior. Do not pull an entire later feature into scope because a shared page mentions it.

## Apply the architecture

Use the existing strong types, Effect service composition, Alchemy infrastructure ownership, and Worker RPC conventions. Read [Architecture](/technical/architecture) for the system split and [Monorepo and ownership](/technical/monorepo) for module and resource ownership. Create only the resources and exports required by the selected stage.

Implement the stage projections in [Stage boundaries](/technical/stage-boundaries#contract-evolution). Preserve source identity and financial invariants while evolving schemas through explicit migrations. Later fields and behaviors need no placeholder handlers, disabled controls, unused tables, or runtime stage flags.

For imports, inspect the [actual CommBank files](/technical/ingestion#actual-commbank-files) in `fixtures/commbank/`. Stage 1 validates CSV and OFX; stage 2 expands validation to the full corpus. Preserve private contents outside tracked fixtures and published artifacts.

Use the [decision ownership policy](/technical#design-status). Consult matching installed source and official third-party documentation when implementing APIs. Record evaluated policy/model versions on their owning references. Correct a failed evaluation candidate rather than weakening financial invariants.

## Build the browser experience with the backend

Each stage is a complete application increment. Connect its real persistence and processing to its user flows. Include navigation, required settings, evidence, review, progress, errors, cancellation and recovery where applicable. Apply [Frontend](/technical/frontend) and [Operations](/technical/operations) for the selected stage.

Verify the stage's critical runtime integrations early. Stage 1 includes Postgres through Hyperdrive, authenticated storage access, direct outbox dispatch, atomic publication, and recovery after a lost commit response. PDF/model checks arrive in stage 2; analyst namespace routing and conversation continuity arrive in stage 6.

Missing financial facts become specific review items. Continue independent work without inventing personal context. If credentials, a deployment identity, or private files are unavailable, implement and verify available paths with representative fixtures and record the exact external check that remains outstanding.

The written flows specify information and actions. Visual composition and branding remain open to a separate design task. A functional frontend is still required for stage completion.

## Verify and stop

Run [Verification](/technical/verification) for the selected stage and regression checks for earlier behavior. Exercise the connected frontend on desktop, mobile, and with a keyboard. Validate data, source evidence, and recovery through the same operations the user invokes.

Stage 1 accounts for every supplied CSV/OFX; stage 2 accounts for every supplied file. Distinguish accepted records, matched observations, and specific unresolved evidence. A parser defect or general review state is not successful ingestion.

Replace obsolete sample behavior as its stage replacement lands. Update affected references and record completion evidence, policy evaluations, and specific unverified external checks. A completion report names the stage and its remaining work. Stop after the selected stage; later stages require a new task or explicit scope extension.
