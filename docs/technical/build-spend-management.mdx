---
title: Build one stage
description: Select a deliverable, build its connected frontend and backend, verify it, and stop.
---

Start with [Delivery stages](/stages). Stage 1 is the default unless the task names another stage. Inspect the repository to establish what already works; the documentation describes intended behavior, not implementation status.

## Establish scope

Read the selected stage's flows, prerequisites, reading path, and completion evidence. Use [Stage boundaries](/technical/stage-boundaries) for shared behavior and [Acceptance scenarios](/product/acceptance) for concrete outcomes. Build a short plan around connected user journeys, including UI, persistence, integration, and verification.

Later references do not authorize later features. Introduce schema fields and operations with the behavior that needs them. Earlier postings require no future interpretation placeholders.

## Choose the smallest working implementation

Use the existing Effect, Alchemy, Worker RPC, and frontend conventions. [Architecture](/technical/architecture) defines the system split and [Monorepo](/technical/monorepo) defines ownership.

Look for an existing library or platform feature before adding custom logic. Check installed source and official documentation for APIs. If a library leaves a demonstrated gap, implement the narrow bank or product behavior it lacks. Keep exact financial rules in shared code used by the API and all result consumers.

A failed action may require retry, reupload, or human review. Preserve accepted data and make repeated financial writes safe. Normal SDK/platform retries are sufficient unless actual use demonstrates otherwise. Do not add a custom recovery path merely because an operation can fail.

For imports, inspect the [actual CommBank files](/technical/ingestion#actual-commbank-files). Stage 1 covers CSV and OFX; stage 2 covers all files. Retain private contents outside tracked fixtures and published artifacts. Measure the corpus before adding concurrency, chunking, or another runtime.

## Build the full user journey

Connect each flow to real persistence and processing. Show empty, processing, review, failed, and completed states as needed. A user must be able to resolve a specific ambiguity or repeat a failed action from its owning screen.

Verify critical runtime connections early: authenticated upload, Postgres through Hyperdrive, private evidence access, and safe financial publication in stage 1. Add deployed PDF/model checks only when used, and SDK conversation routing in stage 6. [Operations](/technical/operations) owns private access and managed backups.

Visual composition, colors, and typography remain open to a separate design task. A functional, responsive, keyboard-accessible frontend is still part of this implementation. [Frontend](/technical/frontend) defines query and interaction behavior.

## Verify and stop

Run [Verification](/technical/verification) for the selected stage and earlier regressions. Demonstrate the browser flow and inspect its stored financial outcome. Use independently known amounts and real input structures.

Account for every supplied file within the selected formats. Specific missing or conflicting evidence can remain reviewable. Parser defects or a blanket unresolved state are not completion.

Run the required repository and documentation checks for changed files. Report the stage, verified outcomes, and specific external checks still unavailable. Do not claim full completion with a required check outstanding. Stop after the selected stage.
