[Stage pages](/stages) own deliverables and stopping points. Product references own user behavior. Technical references own financial meaning and implementation constraints. This page allocates shared behavior without prescribing all future table columns or RPC signatures.

## Contract evolution

Implement the selected stage and preserve earlier outcomes. Add fields, tables, and operations only when their owning behavior is implemented. Boundary types are inferred from implementation schemas; RPC methods are inferred from the server. A migration can introduce a later relationship without manufacturing placeholder data earlier.

Each stage includes its frontend, backend, integration, and verification. Use libraries and platform capabilities first. Failure can require user action; accepted financial data must remain consistent and safe to retry.

## Stage 1

Owns accounts, verified sources, import status, observations, postings, evidence links, coverage, source review, display preferences, and financial command receipts. The UI contains upload, status, transaction list/detail, account controls, and review. Its home page leads to upload and history.

Read the CSV/OFX portions of Ingestion and Import protocol. Use exact values and ownership from Shared contracts and the financial write rule. Events, allocations, categories, model calls, saved queries, and AI runs do not exist. Source access and managed database backups protect the first private records.

## Stage 2

Adds PDF page evidence, full-corpus reconciliation, on-demand financial export, original-file removal, and provider/usage settings only if document models are used. Reuse stage 1 posting and review operations. Source removal retains recorded transactions and extracted evidence; there is no withdrawal or restoration-undo action.

The PDF library is selected; any additional model/document runtime must address an actual supplied file. A failed model-assisted extraction can require human review. Classification is still absent.

## Stage 3

Introduces interpretation events and allocations, categories, merchants, tags, personal events, role/rule decisions, movement and credit links, splits, correction history, and undo. The transaction UI grows semantic fields and filters. Details and previews gain financial measures.

Existing postings can be interpreted through an explicit action without reupload. Uninterpreted records remain visible. Suggestions are reviewable individually or in bulk; users can categorize without AI. Preserve source values and accepted corrections.

## Stage 4

Adds historical overview, comparison queries, contributors, frequency/average-payment views, and saved query definitions. Reuse stage 3 measures. Calculate on open or explicit refresh and invalidate visible frontend queries after writes. Relative date selection resolves at read time. There is no required snapshot store or automatic saved-analysis refresh.

## Stage 5

Adds schedules, effective changes, occurrence matching, ordinary costs, deterministic 30/90-day cost outlooks, a known-payment cash calendar, and saved scenarios. Financial values remain separate from estimates. Forecast assumptions cannot edit actual history. Statistical forecasts and future balance simulation are outside this stage.

## Stage 6

Adds AIChatAgent, authenticated conversation routing, bounded read-only financial tools, explicit notes, and confirmation actions through the existing UI commands. The SDK owns messages and streaming. A failed answer can require a new request. Note changes lead to a fresh conversation so the prior transcript is not reused.

No parallel AI-run schema, text-edit intent service, child-agent execution, arbitrary computation service, or coordinated chat/database restore is required.

## Stage 7

Adds deterministic finding scans, user finding state, intentions, an in-app inbox, and reminder preferences. A normal scheduled handler can invoke the same bounded scan used by the UI. Scans preserve dismissed state and avoid duplicate notifications. Failure offers retry without a dependency-refresh coordinator.

## Shared controls

Financial exports begin in stage 2 and include new financial/domain records as they arrive. They are data downloads, not synchronized system backups. Provider backup configuration remains an operating concern. Original-file removal retains records at every stage, so it does not introduce later financial-impact or result-history protocols.

Stage 1 review concerns source facts and identity. Stage 3 adds interpretation review. Stage 6 suggestions use those existing controls. Stage 7 inbox entries link to owning views rather than introducing another state machine for the same action.
