The [delivery stages](/stages) control implementation scope. This reference allocates the shared technical design to those stages. A stage number means the first stage that requires the behavior; later stages preserve it and implement only their named additions. Deployment environments such as local, staging, and production are independent of delivery stage numbers.

## Contract evolution

The schema and RPC references describe the eventual contracts. Implement a complete, typed projection for the selected stage, using the explicit allocations below. Add later fields, union variants, foreign keys, methods, and infrastructure when their owning stage is implemented. Do not implement a full union with unsupported branches or create future tables just to satisfy a future foreign key.

Keep canonical entity IDs, exact money/date codecs, source locators, ownership, versions, and receipt semantics stable. Migrations add later fields and relations without reimporting history or replacing IDs. Persisted payloads, receipts, snapshots, and exports retain their schema version; a later incompatible shape needs versioned decoding or migration. Derive each stage's real consumer types from its implemented boundary schemas.

A field whose behavior belongs to a later stage is omitted from the current schema and DTO. It is not an empty result claiming that behavior ran. Fields already meaningful in the current stage keep their documented nullability. A later consumer cannot make an earlier import depend on classification, analysis, or conversation availability.

[Upload and record transactions](/stages/record-transactions) owns the following initial contract.

No AI package or analyst runtime.                                                                                                                                                                                                                           |

Accounts have source-backed or user-confirmed account roles and periods so signs and identity are correct. Offset-to-loan relationships are added in stage 3. Account type does not classify postings.

Every accepted posting belongs to one unresolved event, with one unresolved allocation equal to its magnitude. Event kinds and allocation roles contain only unresolved at this stage. Merchant/category/tag/personal-event references, fee associations, credit relationships, and movement links arrive in stage 3. The current TransactionDetail contains posting, event, unresolved allocations, observation evidence, reviews, and basis. TransactionFilter contains currency, period, amount, original-description search, accountIds, and import reviewStates. Semantic filters and detail collections arrive in stage 3.

Corrections initially audit source-evidence resolution. Review kinds are accountMapping, unreadableValue, duplicate, and sourceConflict. Resolution supports stored choices, mapAccount, matchPosting, distinctPosting, useObservation, and dismiss under their existing evidence rules. Unknown role alone creates no interpretation job or role-review workload before stage 3.

SourceCoverage, live pagination, revision fencing, and reconciliation artifacts are required now. Persisted interpretation snapshots and the snapshots table arrive in stage 3; public snapshot-based analysis reads arrive in stage 4. Backup/export capture has its own immutable ExportManifest and record artifact. Dataset contextGeneration stays at its documented initial value until stage 6; its presence does not require context tables.

Settings initially contains timezone and currency. AI policy fields arrive in stage 2, and importReminderDays arrives in stage 7. Jobs gain budget_job_id and model accounting in stage 2. The current backup manifest enumerates every implemented table and required source/artifact object, with no conversation fields or analyst binding. Restore verifies this implemented dataset, receipts, source links, and dispatch reconciliation.

## Stage 2

[Historical imports](/stages/historical-imports) adds PDF media, page locators, document rendering and extraction, and their validation gates to the existing import contract. It retains unresolved financial events.

| Area             | Additions                                                                                                                                                               |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime/package  | Processor document-rendering Container, shared AI execution package and AI Gateway. Document is the only model role.                                                    |
| Tables           | change_previews for source removal and withdrawal undo; model_calls and usage_attempts for document jobs.                                                               |
| Model RPC        | getUsage, openModelCall, completeModelCall, reserveUsage, settleUsage for the owning job. Shared artifact transfer already exists.                                      |
| Data-control RPC | startExport, previewSourceRemoval, removeSource, completeSourceRemoval; previewEventChange, acceptEventChange, and undoCorrection restricted to source-withdrawal undo. |
| Jobs             | User export and removeSource. Backup and export internals from stage 1 are reused.                                                                                      |
| Frontend         | PDF evidence/review, user export and removal/restore flows, document provider/privacy disclosure, usage and limit settings.                                             |

Source-removal ChangeImpact contains affected records, evidence warnings, and review counts. Its measures field is introduced in stage 3 with the financial calculations. Withdrawal undo restores only eligible source-backed postings and their unresolved events. Other event edits and rule previews are not accepted in stage 2.

User exports include all currently implemented records and optional source files. includeConversations and conversation manifest entries arrive in stage 6. Removal tracks affected result IDs only from stage 4, when analysis results exist. Each new stage extends export/restore and removal invalidation to its records as part of that stage's completion.

UsagePolicy initially includes monthlyLimitMicroUsd, importJobLimitMicroUsd, and maxConcurrentModelCalls, plus schema/version fields. Analyst run limits and maxSteps arrive in stage 6. Model roles, inputs, outputs, and actor scopes contain only implemented variants. Document work uses the owning job; it needs no ai_runs or analyst authorization tables.

## Stage 3

[Interpretation and corrections](/stages/interpret-transactions) adds financial meaning above the same postings.

| Area                     | Additions                                                                                                                                                                                                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tables                   | snapshots for interpretation, categories, merchants, merchant_aliases, tags, personal_events, fee_associations, allocation_tags, allocation_events, cost_credits, role_rules, classification_rules; extend events, allocations, corrections, and previews for interpretation. |
| Reference reads/commands | getReferenceData, saveCategory, saveTag, saveMerchant, savePersonalEvent; extend saveAccount with evidenced relationships.                                                                                                                                                    |
| Financial commands       | correctEvent, linkCostCredit, unlinkCostCredit, linkMovements, setFeeAssociation; extend previewEventChange, acceptEventChange, undoCorrection, and resolveReview to semantic edits.                                                                                          |
| Rules                    | previewRoleRule, acceptRoleRule, listRoleRules, setRoleRuleEnabled, previewRule, applyRule, setRuleEnabled, listRules.                                                                                                                                                        |
| Processing               | captureSnapshot for interpretation, commitRoles, commitInterpretations, applyRuleGroup; interpret and applyRule jobs. Interpretation model role and evaluation.                                                                                                               |
| Frontend                 | Complete interpretation detail, semantic search/filters/review, linked movement/credit evidence, splits, previews, correction history, rule and reference-data controls.                                                                                                      |

All financial event kinds, allocation roles, category/merchant relations, and movement/credit collections become available. Personal events hold dates and transaction associations; exclude_from_ordinary arrives in stage 5. General personal_context and its effect on classification arrive in stage 6; stage 3 InterpretationInput omits that context field.

Financial-role rules, conservation, metric arithmetic, and CoverageSummary needed by ChangeImpact belong here. This includes cash and loan-period calculations and the difference between unknown roles and unclassified costs. Interpretation capture uses the financial definition and query fields needed to select its accepted account, period, and event scope, with no comparison or grouping. Its manifest stores the selected rows and evidence; it produces no comparison result. General FinancialQuery comparison endpoints and historical result machinery arrive in stage 4. A correction preview computes its bounded before/after impact directly in the API without requiring saved analyses.

Posting publication now dispatches interpretation. Installing stage 3 durably schedules pre-existing unresolved events for interpretation with stable job identities, preserving source decisions and user corrections. Work with no original source-processing budget uses the standalone interpretation policy. The migration/backfill has visible progress and retry behavior. It does not reupload or reparse sources solely to classify history.

## Stage 4

[Historical exploration](/stages/explore-spending) owns comparisons and persistent analysis results.

| Area                | Additions                                                                                                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tables              | saved_analyses and analysis_results; extend interpretation snapshots to financial analyses.                                                                                 |
| Reads               | getCoverage, getOverview, queryFinancials, getAnalysisResult, listContributions, listEvidence, listSavedAnalyses.                                                           |
| Commands/processing | startAnalysis, saveAnalysis, refreshAnalysis, captureSnapshot for financial analyses, and publishAnalysis.                                                                  |
| Contracts/jobs      | FinancialQuery actual-history measures, comparison results, ResultSelection, allocation/posting contributions, fixed/relative saved definitions; analysis and refresh jobs. |
| Frontend            | Historical overview, Trends, evidence drilldowns, saved-analysis controls, immutable result history, pending refresh.                                                       |

getOverview initially contains basis, sourceCoverage, and metrics. Upcoming schedules arrive in stage 5 and insightIds in stage 7. ordinaryMonthlyCost, ordinaryBasis, and estimate contributions arrive in stage 5. Forecast/scenario definitions and results arrive in stage 5; computation arrives in stage 6. No future result variant is accepted in stage 4.

Refresh coordinates saved-analysis jobs through startAnalysis and refreshAnalysis, with results committed through publishAnalysis. publishRefresh is introduced in stage 5 for commitment proposals and extended in stage 7 for insights and intentions. Imports and corrections dispatch refresh only for existing consumers. The scheduler now refreshes relative saved analyses when their dates change.

## Reference and verification ownership

[Product acceptance](/product/acceptance) assigns every scenario to its introduction stage. Within a shared feature page, its delivery table allocates the detailed behaviors. Technical sections inherit the corresponding contract allocation above; shared correctness rules apply whenever the operation exists.

Stage 1 validates all supplied CSV/OFX. Stage 2 expands that gate to all supplied formats. Stage 3 adds role and category evaluation, stage 4 comparison/snapshot checks, stage 5 forecast evaluation, stage 6 analyst/routing/computation checks, and stage 7 detector and follow-through checks. Every stage verifies its browser flows, data controls, and recovery and keeps earlier regression coverage.
