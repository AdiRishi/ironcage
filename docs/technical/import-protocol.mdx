Stages 1 and 2 record bank data. Stage 3 adds independent interpretation. [Ingestion](/technical/ingestion) owns library choices and the actual corpus context. [Financial writes](/technical/financial-model#persistence-and-concurrency) owns transaction safety.

## Extraction output

Each observation retains the source ID, parser version, row or page locator, literal fields, normalized candidate, and validation issues. CSV locators identify the starting physical line. OFX locators identify the statement and transaction ordinal. PDF locators identify page and row, with a bounding box when available. All displayed ordinals are one-based.

A candidate contains posting date, optional purchase/value dates, signed booked amount, currency, description, optional balance/original money, and the account identity evidence. Unreadable required values remain unavailable and identify a specific review issue. Optional original money requires both supplied currency and amount. It never replaces the booked money in totals.

Statement metadata retains stated periods, balance anchors with their actual dates, and any supplied debit/credit totals. An end-of-day anchor corresponds to the next day's start. A timestamped ledger balance establishes a daily boundary only when its relation to that day's postings is known.

## CSV normalization

The CommBank CSV parser expects four headerless columns: DD/MM/YYYY posting date, signed decimal amount, description, and optional balance. It supports UTF-8 BOMs, quoted commas, escaped quotes, and multiline quoted fields. A row number refers to its starting physical line.

Decimal parsing removes permitted thousands separators only after CSV decoding, validates the currency exponent, and constructs integer minor units without floating-point multiplication. Blank balances remain null. A description's value date is stored separately. An explicitly labelled purchase date can populate purchaseDate.

Deposit amounts represent changes in assets. Card and loan adapters normalize statements to liability-negative balances and corresponding signed deltas. Sign rules are selected from the source layout and verified against statement totals, not inferred from a model's expense category. Reversals preserve their bank sign.

## OFX normalization

The adapter detects the OFX header and message structure from content. The private corpus uses OFX 1.02 SGML with `OFXHEADER:100`, `ENCODING:USASCII`, and `CHARSET:1252`. Its leaf values can omit closing tags. A generic XML parser alone does not handle that format. Encoding follows the declared header, and unsupported or malformed input becomes a specific import issue. OFX XML uses a separate decoding path when supplied. External entity and network resolution are disabled.

Each statement envelope supplies account candidates and `CURDEF`. Account identity uses the institution and account identifiers, scoped to the owner. The supplied card uses CCACCTFROM. The supplied home loan uses BANKACCTFROM with ACCTTYPE CREDITLINE. These are source-profile facts, not a general rule that every bank envelope is a deposit account.

Each `STMTTRN` produces an observation. `TRNAMT` uses exact decimal parsing and the established account sign convention. `DTPOSTED` supplies the posting date. The supplied exports use date-only `YYYYMMDD` values, which remain calendar dates. Timestamp variants retain their original representation and explicit offset during decoding. Offset-free timestamps, including the supplied 14-digit DTASOF values, use GMT as OFX specifies. Display timezone does not change that interpretation. A bank-specific deviation requires a separately evidenced and versioned profile. [OFX date defaults, section 3.2.8.2](https://financialdataexchange.org/wp-content/uploads/2025/12/OFX-2.2.pdf)

The initial CommBank export profile preserves CSV Value Date and OFX DTUSER separately and uses postingDate when there is no independently evidenced purchaseDate. Agreement between these fields does not itself promote them. A later profile may recognize a purchase-date marker only for its evaluated transaction layout and established purchase role. CommBank describes value date as a possible date of the underlying deposit or withdrawal, which does not make it a purchase date for every movement. [CommBank transaction, savings and investment account terms, notes to table 3.1.2](https://www.commbank.com.au/personal/apply-online/download-printed-forms/SavingsInvestment_ADB2852.pdf)

`NAME` and `MEMO` retain their literal values. The candidate description joins nonempty values with a space, omitting a duplicate when both are equal. `TRNTYPE` is bank metadata, not an expense category. `FITID`, correction references, and correction actions remain source fields. A bank correction creates a source-conflict review and requires the existing evidence-resolution command before changing accepted history.

The matching adapter trims FITID and treats missing, empty, or whitespace-only values as absent. Raw evidence keeps the original value. An absent ID supplies no match or conflict evidence and uses the remaining deterministic matching evidence. The supplied card and loan envelopes include empty FITIDs.

`DTSTART` and `DTEND` describe the reported download window, not proof of complete coverage. `LEDGERBAL` supplies a balance anchor at `DTASOF` after sign normalization. `AVAILBAL` is retained as available-balance metadata and does not replace the ledger anchor. A closing balance alone does not establish an opening balance or prove that all movements were exported.

Each file has its own source identity and parser version. Companion CSV files can add descriptions, balances, or corroboration after reconciliation. Neither file format has unconditional precedence over contradictory evidence. File naming and upload order cannot establish a match.

The OFX standard scopes transaction IDs to the institution and account. The importer also checks value consistency because exports can reuse an ID. [OFX specification, section 3.2.3](https://financialdataexchange.org/wp-content/uploads/2025/12/OFX-2.2.pdf)

## PDF extraction and checks

Use positioned PDF text and a CommBank layout adapter. Keep table rows distinct from headings, rewards, totals, and notices. A visually verified layout rule can repair a known extraction defect. A matching total alone never justifies inventing a decimal separator.

When a supplied page cannot be decoded reliably, show it for review or use one bounded document-model call if that capability is needed and enabled. The same deterministic amount, date, sign, and reconciliation checks apply to its output. [Document extraction](/technical/ai-functionality#document-extraction) defines the model boundary.

## Duplicate matching

File identity and posting identity are separate. Owner plus verified file hash prevents repeat uploads creating another source. An observation can support one posting, and two real occurrences in one file remain distinct.

Match only within the same account and booked currency. Accepted user matches and distinct-purchase decisions take precedence. Conflicting amounts or supplied balances require review.

1. Reuse an existing source-observation link when the parsed bank values agree. A changed parser cannot silently replace accepted financial fields.
2. Match a nonempty bank ID only when its account, amount, date, and other supplied evidence agree and identify one occurrence. Reused IDs cannot collapse distinct rows.
3. Match exact normalized descriptions, signed amounts, and dates when corroborated by balances, independently matched neighbors, or a complete overlapping occurrence group. Normalization may standardize whitespace and punctuation while retaining numerical references and service distinctions.
4. Preserve the multiplicity of identical purchases. An incomplete overlap with indistinguishable candidates goes to review. A plausible duplicate cannot silently enter history as a new purchase.
5. An established observation with no plausible existing match becomes a new posting. Record the method and evidence for every accepted match.

Date-only proximity and equal amount can identify review candidates, but cannot prove a duplicate. Apply an offset only for an evidenced source date convention. Cross-format ambiguity is a user decision, not a requirement for fuzzy scores or graph optimization.

Evaluate all actual format pairs and report how many rows require review and why. Fix parser defects and missed deterministic matches. Add a more sophisticated matcher only if the observed workload needs it, using a maintained matching library where appropriate. There is no arbitrary automatic-resolution quota.

## Reconciliation and publication

Opening balance plus signed movements equals closing balance exactly in minor units. Where running balances exist, validate each adjacent movement. Supplied statement totals provide additional checks. Missing anchors permit established rows with partial coverage; they do not establish reconciled coverage.

Parse and prepare observations outside the financial transaction. The API then acquires the financial write lock, reads current matching evidence, validates the decisions, and commits accepted postings, evidence links, review dispositions, coverage, and the import summary in one transaction per file. Valid rows may be accepted while specific uncertain rows remain outside totals, but all those dispositions publish together. A statement discrepancy blocks records whose values or identity it puts in doubt.

There are no partially published groups within that transaction. Technical failure rolls it back. Other files in the batch are independent and can complete. No network calls, model calls, or R2 transfers occur inside the transaction. Measure transaction duration on the real corpus before introducing chunked publication.

Unique source and observation identities plus serialized matching protect simultaneous overlapping imports. Repeated publication returns the accepted outcome. A parser change that alters an accepted row creates a source-conflict review; it cannot overwrite user corrections or create a second bank posting.

## Processing status and retry

Use Cloudflare Workflows for meaningful extraction and publication steps. Persist a small import status: processing, needs review, complete, or failed, with its platform execution reference and summary. The status endpoint can consult the platform if work stopped before the summary was written.

If startup fails, show failure and offer retry. A retry starts processing again or uses the platform's normal retry action. It may repeat extraction. Keep any successfully uploaded source so the user can retry without choosing the file again, while also accepting a reupload safely. A partially uploaded file can require reupload.

The same command ID resolves a lost publication response. A new upload action is protected independently by source hash and observation links. Concurrent or late attempts cannot duplicate accepted rows or override an accepted source correction. No custom dispatch leases, step receipts, or execution-generation supervisor is required.

Review is application data. The user resolves the specific issue and requests another validation attempt; the Workflow need not remain suspended throughout that conversation. Refreshing the page restores the stored summary or current platform status.

## Financial-role establishment

Stage 3 reads already recorded postings. Explicit user decisions and accepted rules come first. A verified source marker may establish a purchase, interest, or fee role. Generic debit/credit labels, account names, and merchant guesses do not prove purpose.

Transfers, repayments, borrowing, and credit relationships require corroborated evidence or user confirmation under [Calculation rules](/technical/calculation-rules#financial-event-construction). Unknown roles remain reviewable. An established cost with no category contributes as unclassified. Categorization failure does not change import status or bank values.

Interpretation runs on explicit request, including for history recorded before stage 3. A successful new import can offer that action. There is no durable obligation to launch every later consumer automatically.

## Source removal

Stage 2 deletes original bytes only, with a confirmation naming affected records. Postings and extracted evidence remain. Reuploading verified identical bytes restores source access and reuses existing observation relationships. [Operations](/technical/operations#exports-and-removal) owns storage behavior.
