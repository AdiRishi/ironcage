Stage 1 imports CSV and OFX. Stage 2 adds PDF. Import never depends on interpretation; a posting needs no category.

## Libraries

| Format | Library                                                                                      | Application code                                                                    |
| ------ | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| CSV    | `csv-parse`, already installed.                                                              | CommBank column meanings, exact amounts, dates, value-date suffix, locators.        |
| OFX    | Evaluate `ofx-js` against the corpus first. Adapt or replace it only for a demonstrated gap. | Envelope selection by account kind, entity decoding, empty `FITID`, GMT timestamps. |
| PDF    | `unpdf` with its bundled PDF.js build. Evaluated at 1.8.1.                                   | Grouping positioned text into CommBank statement rows and validating them. Stage 2. |

Files fit in memory; the corpus's largest file is 2.6 MiB. Use the library's normal parse API.

## Flow

1. The API hashes the upload, stores the bytes in R2 under `sources/<sha256>/<uploadId>` with a fresh upload ID, and finds or creates the source file. An existing source with its bytes available returns its latest import without new work.
2. The API creates the import in `processing` and starts an `ImportWorkflow` instance with the import ID.
3. The Workflow reads the bytes, parses them with the source profile for the format, and produces observations plus statement metadata.
4. The Workflow calls `publishImport`. The API resolves the account, matches observations against current postings, reconciles balances, and commits postings, coverage, review items, and the summary in one transaction.
5. The UI shows the summary and any review items. Resolving an item reruns step 4 for that import.

Steps 1 to 3 run outside any database transaction. Step 4 is one transaction under the write lock. A Workflow that fails in step 3 or 4 reports `failed`; retry starts a new instance on the same bytes.

## Observations

```ts
type Locator =
  | { kind: "csvLine"; line: number }
  | { kind: "ofxTransaction"; statement: number; ordinal: number }
  | { kind: "pdfRow"; page: number; row: number; bbox?: [number, number, number, number] };

type Candidate = {
  postedOn: CalendarDate;
  valueOn: CalendarDate | null;
  amount: Money;
  description: string;
  balance: Money | null;
  bankId: string | null;
  originalMoney: Money | null;
};

type Issue = {
  code: "unreadableAmount" | "unreadableDate" | "unknownAccount" | "unsupportedLayout";
  literal: string;
};
```

`locator_key` is the locator serialized as text, for example `csvLine:12`. Ordinals are one-based. `raw` keeps every literal field. A row whose required value cannot be read has no candidate and an issue, and becomes a `value` review item.

## CommBank CSV

Four unquoted or quoted fields, no header: `DD/MM/YYYY`, signed decimal amount, description, running balance or empty. Rows are newest first. Decode with `csv-parse` using `bom: true` and `relax_quotes: false`.

- Amount text like `-12.50` or `+1234.56` converts to minor units by splitting on the decimal point. Two decimal places for AUD.
- A description ending in `Value Date: DD/MM/YYYY` populates `valueOn` and is stripped from `candidate.description`. `raw` keeps the full text.
- The balance, when present, is the account balance after this row. Store it as `candidate.balance`.
- Fragments like `Card xx1234` or `USD 12.34` stay in the description. `USD 12.34` also populates `originalMoney` when a currency code and amount are both present.
- The CSV carries no account identity. The upload must name the account.

## CommBank OFX

OFX 1.02 SGML. The header block declares `ENCODING:USASCII` and `CHARSET:1252`; decode bytes as Windows-1252. Leaf elements have no closing tag. Decode SGML entities in leaf values: `&amp;`, `&lt;`, `&gt;`. Disable any external entity or network resolution.

| Account kind | Message set          | Statement wrapper                              | Account element                                              |
| ------------ | -------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| deposit      | `BANKMSGSRSV1`       | `STMTTRNRS` / `STMTRS`                         | `BANKACCTFROM` with `BANKID`, `ACCTID`, `ACCTTYPE` `SAVINGS` |
| card         | `CREDITCARDMSGSRSV1` | `CCSTMTTRNRS` / `CCSTMTRS`                     | `CCACCTFROM` with `ACCTID`                                   |
| loan         | `BANKMSGSRSV1`       | `STMTTRNRS`, opens `CCSTMTRS`, closes `STMTRS` | `BANKACCTFROM` with `ACCTTYPE` `CREDITLINE`                  |

Account identity is `(BANKID, ACCTID)` for deposit and loan and `(null, ACCTID)` for card. The first import of an unknown identity creates the account with the kind implied by the table. The parser tolerates the loan's mismatched wrapper tags by matching on element names, not on balanced pairs.

- Each `STMTTRN` is one observation. `TRNAMT` converts exactly. `DTPOSTED` is eight digits and is a calendar date. `DTUSER` populates `valueOn` when it differs from `DTPOSTED`.
- `MEMO` is the description, with the same value-date suffix rule as CSV. `NAME` is absent in the corpus; if present, join `NAME` and `MEMO` with a space, omitting a duplicate.
- `FITID` populates `bankId` after trimming. Empty means null. The deposit accounts have IDs on every row; card and loan have none.
- `TRNTYPE` is stored in `raw` and used for nothing else.
- `LEDGERBAL` supplies a balance anchor at `DTASOF`. `DTASOF` is fourteen digits without an offset, which the OFX specification defines as GMT; convert to a calendar date in GMT, not in the display timezone. An end-of-day ledger balance anchors the start of the next day. `AVAILBAL` is stored in statement metadata and not used as an anchor.
- `DTSTART` and `DTEND` are the requested download window and become `stated_start` and `stated_end`. They do not prove coverage.

## Normalization for matching

`normalizedDescription` is the candidate description with entities decoded, whitespace collapsed to single spaces, and leading and trailing whitespace removed. Nothing else is altered; numbers, card fragments, and service names stay so that distinct services remain distinct.

The match key is `(accountId, currency, postedOn, amountMinor)`. Description and running balance corroborate a match; they are not part of the key, because a PDF statement words the same posting differently from a CSV export.

## Matching

Matching runs inside the publication transaction with the write lock held. It sees every committed posting. It relies on one property of CommBank exports: a file contains every posting of its account for every date it covers. Statement periods and export windows are whole days.

For each observation `O` of file `F`, in file order:

1. **Same file, same row.** If an observation with `(F, O.locatorKey)` already exists and supports posting `P`: when `O.candidate` equals `P`'s booked fields, reuse the link. When it differs, create a `source_conflict` review item and leave `P` unchanged. Stop.
2. **Bank ID.** If `O.bankId` is present, find postings on the same account supported by an observation with the same `bankId`. Exactly one with equal amount and posted date is a match with method `bankId`. One with a different amount or date is a `value` review item. None continues to step 3.
3. **Group.** Let `G` be the observations of `F` with `O`'s match key that are still unmatched in this run, and `E` the existing postings with that key on the account not yet matched by an observation of `F` in this run.
   - `E` empty: every member of `G` becomes a new posting. Method `new`.
   - `|E| = |G|`: pair equal normalized descriptions, using equal running balances to disambiguate repeated descriptions before assigning any pairs. Then pair remaining rows by equal running balance. When both sides supply balances, conflicting balances never form an automatic pair. If rows remain on both sides, pair them in file order only when the remaining rows are indistinguishable from one another within `G` and within `E`: equal normalized descriptions and, where supplied, equal running balances on each side. Two identical coffees without balances in both files match as two postings and either pairing is correct. Remaining rows that are distinguishable become one `duplicate` review item, because an equal count proves how many postings exist but not which row supports which. Method `group`.
   - Otherwise: pair a member of `G` with a member of `E` only when they are the single pair in `G × E` that shares a normalized description or a running balance. Method `corroborated`. Whatever remains on both sides becomes one `duplicate` review item listing the rows and the postings. The user matches specific pairs or declares distinct postings.

Record `match_method` and `match_evidence` on every observation. A user decision from a review item is method `user` and wins over every automatic step on reruns.

Amount and a nearby date never match on their own, and there is no similarity score. On the corpus, every CSV row matches its OFX pair at step 3 with equal descriptions, and the deposit accounts also match at step 2. Statement rows inside a structured window match at step 3 by count, with running balances corroborating on deposit and loan statements.

## Reconciliation and coverage

For each file and account, publication computes a coverage row.

- `observed_start` and `observed_end` are the earliest and latest posted dates in the file.
- `stated_start` and `stated_end` come from OFX `DTSTART` and `DTEND` or a PDF statement period. CSV has none.
- The closing anchor is the OFX `LEDGERBAL`, the newest CSV running balance, or a PDF closing balance. The opening anchor is a PDF opening balance or, for a CSV with balances, the oldest balance minus its row's amount.
- `reconciled` is true when both anchors exist and opening plus the sum of movements between them equals closing exactly. Where every row has a running balance, each adjacent pair must also agree. PDF debit and credit totals are extra checks when printed.

A file with anchors that do not reconcile publishes nothing and creates a `value` review item naming the discrepancy. A file without an opening anchor publishes its rows with `reconciled` false. Missing anchors are missing evidence, not zero activity. Two anchors on consecutive dates with no rows between them establish an empty reconciled interval.

## Publication transaction

1. Take the write lock. Derive the publication command ID from the import ID, the parser version, and a hash of the observation set, and look up its receipt. A repeat returns the stored summary whatever the import's status is now. Otherwise confirm the import is `processing`.
2. Resolve the account: from the OFX envelope, from the upload's `accountId`, or by creating an `account` review item when neither exists.
3. Upsert observations by `(source_file_id, locator_key)`.
4. Run matching. Collect new postings, links, and review items.
5. Reconcile and compute the coverage row.
6. Insert postings, set `posting_id`, `match_method`, and `match_evidence` on observations, upsert coverage, insert review items, write the summary, set the status, and write the receipt. Commit.

The receipt key includes the parser version and the observation set, so a retry after a parser fix is a new publication rather than a conflict. Step 3 and matching step 1 are what make that new publication safe. A republish triggered by `resolveReview` runs under that command's own receipt, not the publication receipt.

Every row's disposition is in one transaction: accepted rows are committed together with the review items for the uncertain ones. A technical failure rolls the whole file back. Other files in the same upload are independent. No network call happens inside the transaction. Measure the transaction on the largest corpus file before considering anything more complicated.

## Review resolutions

| Kind              | Question                                                     | Resolutions                                                                                         |
| ----------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `account`         | Which account does this file belong to?                      | Choose an account, or create one.                                                                   |
| `value`           | A required value is unreadable, or anchors do not reconcile. | Accept a decoded value shown beside the literal text, or leave the row out and note why.            |
| `duplicate`       | Which existing posting, if any, does this row represent?     | Match a listed posting, or declare a distinct posting.                                              |
| `source_conflict` | The parser now reads an accepted row differently.            | Keep the accepted posting, or accept the new reading as a bank-field correction with this evidence. |

Resolving applies the decision to the observations, then reruns steps 4 to 6 of publication for the import under the same lock. Decisions persist on the observations, so a later reparse reproduces them.

## PDF statements

Stage 2. Use `unpdf` to get positioned text, then a CommBank layout adapter per account kind groups text into transaction rows and separates them from headings, reward summaries, totals, and notices. Locators are page and row with the bounding box.

The September 2026 evaluation of five statements, 25 pages, and 303 manually checked rows matched every date and signed amount and all 258 printed running balances after one visually verified repair for card rows whose decimal point the text layer drops. Keep the raw strings and positions when applying a repair. A repair is a documented rule for a known layout defect, never an inference that makes a total balance.

Statement metadata carries the printed period, opening and closing balances, and debit and credit totals. Statements also print zero-amount notice rows, such as a fee waived; keep them in `raw` and do not turn them into postings.

A page the adapter cannot decode is shown to the user for a `value` review with the page image. If a supplied statement needs it, one document-model call per page is available under [AI](/technical/ai#document-extraction), with the same candidate validation as every other parser. A reproducible decoder defect is a code fix, not a review item.

Statement history before the structured exports becomes new postings. Statement rows inside a structured window match existing postings at step 3 by account, date, amount, and count, with running balances corroborating on deposit and loan statements. A day where the statement and the export disagree on how many postings share an amount is a `duplicate` review item. Stage 2's completion evidence counts how many rows reach review and why.

## Source removal

Stage 2. `removeSourceBytes` carries `commandId`, `sourceFileId`, and `expectedVersion`. Inside the transaction it checks the version, sets `bytes_available` false, and bumps the version. The command receipt's `result` stores `{ sourceFileId, objectKey, affectedPostingCount }`, capturing the current `object_key`. Postings, observations, coverage, and review history stay. The confirmation lists the postings the file supports and says only the original bytes go.

After the transaction, the handler deletes the receipt's `objectKey` from R2 and returns the affected posting count. A repeated command with the same input reads its receipt before checking the version and attempts that same delete again. An already absent object counts as success. A storage failure returns `unavailable`; the UI offers Retry with the same command ID and input. The receipt preserves the deletion key without a new table or a scheduled cleanup job.

Reuploading identical bytes writes a new object under a new upload ID, points `object_key` at it, sets `bytes_available` true, and bumps the version; matching step 1 reuses every link, so no posting is created. A new removal command with a stale version changes nothing. A repeated removal command or a delete already in flight targets only the key in its receipt, so the replacement is never removed.
