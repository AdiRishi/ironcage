Models appear in three places: document extraction for a PDF page the parser cannot decode in stage 2, category suggestions in stage 3, and the analyst in stage 6. Stages 1 and 2 record postings with no model at all.

## Configuration and limits

One configured model per task, called through the AI SDK and the existing provider integration. Prompts and output schemas live beside the feature that uses them. Each call has an input limit, an output limit, and for the analyst a tool-step limit. The SDK's transient retry is enough; an exhausted retry, invalid structured output, or an unavailable provider becomes an `unavailable` failure or a review item the user can act on.

Every call writes a usage record: task, model, time, reported tokens, and reported or estimated cost. A failed call with no report stores unknown usage. Settings shows the provider, what data each task sends, the usage total, and an on/off switch. A usage warning threshold blocks new calls once observed usage reaches it; delayed reports and concurrent calls can overshoot it, and the settings text says so.

Logs carry operation IDs and timings, never prompts, completions, or statement text.

## Document extraction

Stage 2. The parser runs first. When a page cannot be decoded, and the user has enabled document models, send that page through the SDK's document input and ask for structured output of transaction rows with page locators. The result goes through the same candidate validation, reconciliation, and matching as parser output. A response that fails validation leaves the page in `value` review with the page shown. Any extra rendering dependency is added only when a real page needs it.

## Classification

Stage 3. Input: the posting description, the established financial role, the account kind, the merchant if known, and the current category tree. Output: a category ID or an explicit "needs review", with a one-line reason, as structured output validated against the current categories.

Precedence from [Financial model](/technical/financial-model#precedence) applies: a correction or accepted rule on the event wins, and a suggestion never touches a booked field. Suggestions are shown for single or bulk acceptance. The user can categorize manually at any time, and an uncategorized cost still counts as spending. An unknown financial role stays unresolved rather than being inferred from a category.

Evaluate a model change on representative corpus cases and synthetic fixtures: useful suggestions, wrong categories, ambiguous descriptions, and preservation of corrections.

## Analyst

Stage 6. One `AIChatAgent` Durable Object instance, named for the single user, reached through the web Worker. The web Worker validates the Access session and forwards HTTP and WebSocket traffic over the private namespace binding with the verified identity attached; the agent rejects any connection without it.

The SDK owns messages, persistence, streaming, reconnection, and cancellation. The application supplies tools, prompt context, and result components. One answer runs at a time per conversation; the user can stop it and ask again. A failed answer is shown as failed and can be resubmitted, which may repeat tool calls.

### Tools

All tools are read-only and call existing API operations with the trusted identity.

| Tool           | Reads                                                       |
| -------------- | ----------------------------------------------------------- |
| `getPostings`  | Filtered postings with observations and source links.       |
| `getEvent`     | A financial event with allocations, links, and corrections. |
| `compare`      | A stage 4 comparison result.                                |
| `contributors` | Contributor rows for a comparison.                          |
| `commitments`  | Schedules and upcoming occurrences.                         |
| `forecast`     | A stage 5 forecast or scenario result.                      |
| `notes`        | Current notes relevant to the question's scope.             |

Every tool result carries the calculation time, scope, coverage, and record references. The model narrates those results; it never computes a total itself. A question the tools cannot answer gets an explanation of what is missing.

### Suggested changes

The analyst can propose a correction. The proposal renders as a link to the existing edit control or as a confirmation card that calls the ordinary command with the current expected versions. Text in a bank description, a note, or a model response has no authority; only the user's click does.

### Notes

Notes are explicit records the user creates, edits, and removes, each optionally scoped to an account or period. A fresh conversation loads the current notes. After a note changes, the UI starts a new conversation for further questions and leaves the old one read-only, so a removed fact does not come back through the old transcript. The confirmation dialog says this before the change.

Account kinds, offset relationships, rules, and personal events stay in their own records. Casual conversation never becomes a stored fact.

### Evaluation

Ask questions with independently verified API results and compare the numbers. Check that source links resolve, that scope and coverage are stated, and that a description containing an instruction is treated as data. Exercise stop, provider failure, and reconnect through the real SDK integration.
