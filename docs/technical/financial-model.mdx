This page holds the rules every stage shares. Stage pages own their tables and operations. [Calculation rules](/technical/calculation-rules) owns arithmetic.

## Values

| Value        | Contract                                                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ID           | UUID generated by the API, branded by record kind in TypeScript.                                                                                                |
| Money        | `{ currency, minor }`. `minor` is a signed integer of minor units: `bigint` in code, `BIGINT` in Postgres, a decimal string in JSON. Never a JavaScript number. |
| DecimalMoney | `{ currency, value }` with `value` a decimal string. Used only for per-day averages and other non-booked quantities.                                            |
| CalendarDate | `YYYY-MM-DD` string in code and JSON, `DATE` in Postgres. Decoded without passing through a local-midnight `Date`.                                              |
| Instant      | ISO 8601 UTC string in JSON, `TIMESTAMPTZ` in Postgres.                                                                                                         |
| Period       | `{ start, endExclusive }` of calendar dates.                                                                                                                    |
| Version      | Integer incremented on every write to a mutable record. Commands carry the version they expect.                                                                 |

Parsing converts decimal text straight to minor units using the currency's exponent. Aggregates in SQL use `SUM` over `BIGINT` or `NUMERIC`. Fractional intermediate values stay exact as rationals or decimals until the output boundary named by the calculation. An amount that a source does not supply is absent, never zero.

Boundary schemas validate imported bytes, browser input, stored JSON payloads on read, and model output. Everything inside the API trusts decoded types.

## Identity

- A source file is its SHA-256. Same bytes, same file, whatever the name.
- An observation is its source file plus locator key. Reparsing a file yields the same observation IDs for the same rows.
- A posting is created once by publication and never recreated by reparsing. Observations point at postings; postings do not point at observations.
- A financial event is created by interpretation in stage 3 and keeps its ID when its allocations or links change.
- Reference data such as categories keeps its ID through renames.

## Write protocol

Every write of financial records is a command with a client-generated `commandId`. The API runs each command like this:

1. Open a database transaction and take the transaction-level advisory lock `pg_advisory_xact_lock(1)`. One user, one lock; writes are short and serialized.
2. Look up `command_receipts` by `commandId`. If the input hash matches, return the stored result. If it differs, fail with `conflict`.
3. Read the records the command touches. Compare each `expectedVersion`. Any mismatch fails with `stale` and changes nothing.
4. Validate business preconditions against current records: allocation conservation, remaining credit, matching decisions.
5. Write the change, its correction history where the stage has one, and the receipt. Commit.

Parsing, model calls, and uploads to R2 happen before the transaction opens. Source removal deletes from R2 after the transaction, using the key saved in its receipt. A repeat completes that delete before returning, as defined in [Source removal](/technical/import-protocol#source-removal). A client that loses the response repeats the same command with the same ID and gets the first result. A network error alone does not prove the write rolled back.

Import publication follows the same shape. Its receipt key is the import ID, the parser version, and a hash of the observation set, so a retry of the same parse returns the stored summary and a retry after a parser fix is a new publication. The receipt lookup runs before any check on the import's status.

## Reads

Reads that return related totals, such as a headline and its contributors, run in one transaction with `REPEATABLE READ` so the parts agree. Lists use a cursor made of the sort key and ID of the last row. The cursor is validated as input; changing filters resets it. Hyperdrive caching is off so a read after a commit sees the commit.

## Postings

A posting records what the bank booked: account, currency, signed booked amount, posted date, optional value date, description, and optional original-currency money. Booked amounts are asset-positive: a deposit account balance is positive when the user has money, and a card or loan balance is negative when the user owes money. A purchase on any account is negative; a repayment into a card or loan is positive.

Historical totals use the booked AUD amount. Original-currency money is display information and its own supporting observation. Separate fee postings stay separate postings.

Posted date is the date basis for account views. Value date is stored beside it and never used as a purchase date on its own.

## Financial events

From stage 3, a financial event groups one or two postings into one economic event and divides its magnitude into allocations. [Calculation rules](/technical/calculation-rules#financial-event-construction) lists the event kinds with their posting membership and reporting account.

Rules that hold at every write:

- A posting belongs to at most one active event.
- Allocations of an event are nonnegative and sum exactly to the event's magnitude. Splitting a purchase into three allocations of 4000, 3500, and 2500 minor units for a 10000 purchase is valid; 4000, 3500, and 2600 is rejected.
- A transfer, card settlement, loan payment, or borrowing uses the amount moved once, even when both account postings are present. It creates neither income nor cost.
- A credit link applies part of a refund or reimbursement allocation to a cost allocation in the same currency. The applied amount cannot exceed the remaining unapplied credit or the remaining uncredited cost. A 30000 cost with a 20000 credit applied has 10000 remaining; a further 20000 application fails rather than clipping to 10000.
- Interest and fees are financing-cost events with their own dates. Linking a repayment never moves an interest posting's date. Net principal reduction is a period measure computed from both, not an allocation of a repayment to an interest date.
- Corrections change interpretation, never a booked amount. Changing a bank field requires replacement source evidence and goes through source review.
- A confirmed movement can have one posting and a confirmed external endpoint. Its role is known and its counterpart evidence is visibly incomplete. Attaching the counterpart later keeps the event ID.

## Precedence

When several sources of interpretation disagree, the order is:

1. A correction on the specific event.
2. A user-accepted rule. Two rules matching the same event with different actions create an interpretation review.
3. A role established by a verified source marker, such as a CommBank interest or fee description.
4. A model suggestion, which is a proposal until the user accepts it.

Reprocessing a source or rerunning classification cannot overwrite anything above the level it operates at.

## Measures

| Measure                                 | Definition                                                                                                     |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Gross costs                             | Sum of purchase and financing-cost allocations before credit links.                                            |
| Net personal costs                      | Gross costs minus credit-linked refunds and reimbursements. "Spending" on product pages means this.            |
| Income                                  | Sum of income allocations. Excludes borrowing, transfers, refunds, and reimbursements.                         |
| Surplus after costs                     | Income minus net personal costs on the selected date basis.                                                    |
| Surplus rate                            | Surplus divided by income when income is positive. Otherwise unavailable.                                      |
| Cash balance change                     | Closing minus opening balance across selected deposit accounts. Requires both anchors.                         |
| Net principal reduction from repayments | Loan-side repayments minus interest and fees charged in the period. Requires full loan coverage of the period. |
| Purchase count                          | Distinct purchase events, including fully refunded ones.                                                       |
| Ordinary monthly cost                   | Variable baseline plus monthly allocation of confirmed commitments, minus excluded personal events. Stage 5.   |

Every result names its measure, period, date basis, accounts, currency, calculation time, and coverage. Coverage reports observed dates, reconciled intervals, missing accounts or periods, and counts and amounts of unresolved events. A result with unresolved events that could change it says so beside the number. Surplus is not available cash.

## Failures

Commands and reads fail with one of these kinds so the UI can act on them.

| Kind          | Meaning                                                            | UI action                                         |
| ------------- | ------------------------------------------------------------------ | ------------------------------------------------- |
| `invalid`     | Input failed its schema.                                           | Show the field error, keep the input.             |
| `notFound`    | A referenced record does not exist.                                | Return to the list.                               |
| `stale`       | An expected version no longer matches.                             | Show current records, keep the input, ask again.  |
| `conflict`    | Command ID reused with different input, or a uniqueness violation. | Show the stored result or the conflicting record. |
| `needsReview` | The write created or requires a review item.                       | Link to the review item.                          |
| `unavailable` | Database, storage, Workflow, or model call failed.                 | Offer retry with the same command ID.             |
