Operational requirements arrive with their owning [stage](/technical/stage-boundaries). Stages 1 and 2 need private uploads, a reliable financial database, basic logs, and safe user retries. Stage 6 adds conversation access. Stage 7 adds scheduled in-app reminders.

## Application domain and access

The production application uses `wealth.arishi.dev` under the existing `arishi.dev` domain. The web service's Alchemy module owns its routing. Configure the staging hostname, Access login provider, and allowed user identity before that environment goes live.

Cloudflare Access protects the application. The web Worker validates token signature, issuer, audience, and expiry. The same authentication covers downloads, server functions, and analyst HTTP/WebSocket traffic. [Access token validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)

The server supplies owner identity. Internal Workers have private bindings and no public domains. Local development can use a local identity only in the local environment. Browser mutation handlers verify origin and authentication. Model output and source text cannot grant authority.

## Database and runtime

Use PlanetScale Postgres through the API's Hyperdrive binding, with query caching disabled for financial reads. Follow the existing Effect SQL and Alchemy composition. Transactions use one connection for their entire lifetime. Local and CI databases use the same major version and migrations as production.

Use separate application and migration roles, TLS, and deployment secrets. Production, staging, and tests use separate data stores. Confirm available region, capacity, and cost when provisioning rather than prescribing a production tier before measuring the workload.

Imports use Cloudflare Workflows with a few meaningful steps. Use built-in bounded retries for transient errors and a visible failure after exhaustion. User retries may rerun work. Input size, execution time, and model output limits protect actual runtime boundaries. Measure the supplied corpus before adding chunked publication, another execution service, or a PDF rendering runtime.

## Sources, backups, and retention

Keep original source files private in R2 until the user removes them. Preserve extracted bank evidence and accepted corrections in Postgres. Enable managed database backups, configure their retention, and verify one restore into an isolated environment before relying on the app for private records. PlanetScale provides database backups and point-in-time recovery. [Back up and restore](https://planetscale.com/docs/postgres/backups)

Database backups do not contain R2 bytes. Keep an independent copy of original statements, either in the user's source archive or a separate backup location. Before the first private deployment, record the chosen database retention and original-file copy arrangement. Reupload can restore original evidence, but cannot reconstruct lost user corrections, so database backups remain required.

Use the provider's recovery tools and a short operator restore procedure. Application screens need retention disclosures, not a backup management product. Conversation history uses the SDK's storage lifecycle; exact coordinated restoration of chat, financial data, and source files is outside the current product guarantee.

Temporary upload and export files have a configured expiry. Cleanup targets temporary storage only and cannot delete accepted source evidence. Disclose the actual configured retention. Source or note deletion does not claim immediate removal from retained backups.

## Exports and removal

Stage 2 provides on-demand financial data export with source files as a selectable addition. The package names its format, included records, and export time. It is a data download, not a synchronized cross-store restore image. Re-export after failure.

Source removal deletes original file bytes and retains accepted transactions, extracted fields, and evidence relationships. The confirmation explains that outcome and identifies affected records. The detail then marks the original file unavailable. Reuploading identical bytes restores its source identity. Deleting financial history is a separate future product decision.

Storage operations target the specific object selected by the action. A stale deletion must not delete a later replacement upload. Keep the source's availability truthful and offer retry if byte deletion fails. No source withdrawal, cascading result refresh, or withdrawal-undo protocol is required.

## Model access and usage

Use the configured model through the existing provider/Gateway integration. Name the provider and disclose what data is sent. Gateway routing does not imply that inference stays within Cloudflare. Send only records needed by the task. Exclude prompts, completions, account identifiers, and private statement contents from routine logs and tracked fixtures.

[AI functionality](/technical/ai-functionality) defines output validation, limits, and human review. Show reported usage or labelled estimates when available. Usage warnings are not an exact billing ceiling. The user can disable model calls while continuing to upload structured data and use recorded history.

## Scheduled work

No import recovery or saved-analysis refresh scheduler is required. Saved views calculate on demand. Stage 7 can use a normal scheduled handler for bounded finding scans, intention reviews, and configured import reminders. A failed scan is visible and can be rerun; the next scheduled scan also reads current data. Stable finding and notification identities avoid duplicates.

## Observability and deployment

Log operation/import IDs, timing, platform execution references, and safe error codes. Owning screens show failed imports and model review states. Ordinary provider logs and database metrics are enough to investigate failures; no general operations console is required.

Alchemy owns the resource graph, and service modules own their resources. Versioned migrations create an empty database and upgrade existing records. Use a verified backup and coordinated deployment for a change that cannot preserve old readers. Before private deployment, verify authentication, private evidence access, a repeated import, a lost financial-write response, and the chosen restore procedure. Add analyst routing checks in stage 6.
