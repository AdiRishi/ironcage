Stage 2 can use a document model when actual PDFs require it. Stage 3 adds category suggestions. Stage 6 adds the conversational analyst. Stages 1 and 2 record postings without needing classification. [Stage boundaries](/technical/stage-boundaries) owns feature scope.

## Models and limits

Choose one configured model per task and use the existing AI SDK/provider integration. Keep prompts and output schemas beside their owning behavior. Reuse a helper only for genuinely shared configuration or validation, without creating a general execution framework.

Set finite input/output limits and a bounded tool-step count for the analyst. An ordinary SDK retry for a transient transport error is acceptable. Invalid structured output, exhausted retries, or an unavailable model produces an actionable failure or review item. There is no model failover chain, output-repair conversation, or custom replay accounting.

Record model identity, task, time, and available usage. Show provider-reported cost or a labelled estimate. Unknown usage stays unknown. A user-configured usage warning threshold can block new calls after observed usage reaches it, but it is not a guaranteed billing ceiling: delayed reports, unknown charges, and concurrent requests can exceed it. Settings explains this and provides an AI on/off control. A retry may incur another model charge.

## Document extraction

Deterministic parsing is the first path. If a supplied PDF needs model assistance, send only the required document/page content through a supported input format. Return literal transaction fields and page locators through structured output.

Validate dates, exact money, sign conventions, account identity, and reconciliation using the same importer as deterministic extraction. An unsupported or unreliable result leaves the source reviewable. The user can resolve a specific field using the visible source or supply a clearer export. Parser defects still need a code fix; routing an entire supported corpus to review is not completion.

Choose any extra rendering dependency only after a real supplied page demonstrates the need and the selected model input requires it. The text library and verified layout repairs remain in [Ingestion](/technical/ingestion#pdf-library-selection).

## Classification

Apply transaction-specific user corrections first, then accepted deterministic rules. Conflicting rules leave a review item. A model receives the relevant recorded description, established role, available context, and current category choices. It returns a category suggestion or an explicit need for review, with a short explanation.

Use SDK structured output, then validate the category against the current owner-scoped reference data. A valid response cannot overwrite a user correction or alter booked bank fields. Initially present model output as a suggestion with single and bulk acceptance controls. There is no mandatory confidence score or labelling quota before useful suggestions can ship.

The user can categorize directly when the model fails or cannot decide. An established cost remains unclassified and continues to contribute to spending. An unknown financial role remains visibly unresolved instead of being guessed from the category.

Model upgrades use representative real cases and synthetic financial fixtures. Check useful suggestions, incorrect categories, ambiguous cases, and preservation of corrections. Broader automatic application requires evidence that it improves the actual review workload while preserving user control; it is not a stage-three completion requirement.

## Analyst tools

Use AIChatAgent with the AI SDK's ordinary tool loop. Tools read existing API operations for transaction evidence, comparisons, commitments, and deterministic scenarios. Their inputs validate the requested scope. Financial totals always come from those operations.

Keep tools narrow enough to answer the product's supported questions. A question the tools cannot answer receives an explanation of the missing capability or evidence. The analyst does not generate arbitrary executable code or dispatch child agents.

## Mutation authority

Financial tools are read-only. An analyst suggestion links to the existing edit/review screen or renders a confirmation card. The user's authenticated acceptance invokes the ordinary version-checked command. Text such as "categorize this as strata" can prepare that choice, but cannot apply it by itself.

The server supplies owner identity and permissions. Bank descriptions, document text, saved notes, and model output are untrusted content and cannot authorize a mutation. The UI preserves the existing previews for bulk edits and changes to financial relationships.

## Conversation execution

AIChatAgent owns canonical messages, persistence, streaming, reconnects, and stopping an answer. Use SDK capabilities directly. The UI permits one active answer per conversation; another question can be sent after completion or stop. No application submission queue, intent pass, run-step store, or supervisor is required.

A disconnected client can recover available messages and streaming state through the SDK. A failed answer can require resubmission and may repeat reads or model calls. Display that failure honestly. Financial mutations remain protected by their ordinary command receipts, independently of chat execution.

## Answers and evidence

Render SDK text and typed tool results. Calculated money, period, account scope, and coverage appear in financial result components with links to the relevant records. Narrative explains those results and distinguishes observations from possible explanations.

There is no requirement to encode every date or count in a custom claim language. Evaluate numerical explanations against the actual tool results. Old messages keep their displayed calculation time; linked records and a rerun use current data. Chat history is not a replayable financial snapshot archive.

## Memory

Start with explicit user-managed notes and preferences. Account roles, classification rules, and personal events remain in their existing domain records. Load current notes relevant to the question, with supplied account/period scope where useful. Do not infer permanent personal facts from casual conversation.

A note edit or removal affects future retrieval. To prevent the old fact reappearing from an existing transcript, the edit flow starts a fresh conversation for subsequent analysis and leaves the earlier conversation read-only. Current notes are loaded into that fresh conversation. Explain this before the user confirms the note change. There is no global transcript-generation or historical-answer invalidation subsystem.

Conversation summaries are optional SDK context management. They cannot replace confirmed domain facts. A fresh conversation does not import an old summary after a note change.

## Evaluation

[Verification](/technical/verification) owns the tests. Use independently known financial results, representative category examples, structured-output failures, unavailable providers, and explicit human review. A live provider check verifies the chosen model/input format. It does not replace deterministic money and authorization tests.
