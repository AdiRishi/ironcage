Verification follows the [product acceptance scenarios](/product/acceptance). A schema-valid model response, successful build, or rendered chart is insufficient evidence that a financial answer is correct.

Contract tests encode and decode every [shared schema](/technical/contracts), exercise every [RPC method](/technical/rpc) through its public interface, and check the [database constraints](/technical/database-schema) against real Postgres. Processor fixtures cover every transition in [Import and job protocols](/technical/import-protocol). AI cases follow the [functionality specification](/technical/ai-functionality), and numerical expected values follow [Calculation rules](/technical/calculation-rules).

## Financial invariants

Tests exercise public finance operations with independently known expected outcomes. Fixtures use synthetic records that preserve the structural cases found in the supplied exports.

| Invariant                                              | Regression caught                                                      |
| ------------------------------------------------------ | ---------------------------------------------------------------------- |
| Same-file import is idempotent                         | Repeated uploads inflate transactions or repeat completed enrichment.  |
| Import order does not change accepted history          | Overlapping files produce different totals depending on arrival order. |
| Identical real purchases retain multiplicity           | A naive duplicate key removes genuine spending.                        |
| CSV and PDF observations converge                      | Cross-format aliases produce duplicate purchases.                      |
| Allocation sums equal the source amount                | Splits create or lose money.                                           |
| Own transfers and card settlements do not create costs | Money movement is counted as additional spending.                      |
| Partial refunds and reimbursements apply once          | Repeated links or retries reduce a purchase twice.                     |
| Balance anchors reconcile with movements               | Missing postings are silently treated as complete history.             |
| Corrections survive reprocessing                       | New extraction or merchant rules overwrite user decisions.             |
| Analysis revisions remain coherent                     | One answer mixes values before and after a correction.                 |
| Frequency and average contributions sum to the change  | A numerical explanation does not reconcile to its headline.            |

Date fixtures include month boundaries, leap days, daylight-saving changes, value dates, and missing purchase dates. Currency fixtures include decimal parsing, negative amounts, fee corrections, and aggregation near the supported range.

## Database transactions and snapshots

Repository and concurrency tests use real PostgreSQL with the production migrations. Pure finance tests remain in process. SQLite and mocked SQL clients cannot establish Postgres locking or isolation behavior.

| Scenario                                                      | Required evidence                                                                                         |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| A command fails after changing allocations                    | Financial rows, audit entry, receipt, revision, and dispatch all roll back.                               |
| Two commands claim the same remaining reimbursable amount     | The later command sees the committed allocation and cannot over-allocate it.                              |
| Two callers submit one command ID                             | One outcome is committed and both callers receive it. A different payload using that ID is rejected.      |
| A stale import publishes while a correction commits           | The owner lock and revision check prevent publication against obsolete matching decisions.                |
| A snapshot reads several tables while another command commits | Every value and the recorded revision belong to the same repeatable-read snapshot.                        |
| A commit succeeds but its response is lost                    | Retrying resolves the stored receipt without another correction or dispatch record.                       |
| A query follows a committed correction through Hyperdrive     | The query sees the committed value rather than a cached earlier result.                                   |
| A deadlock or transaction timeout interrupts a command        | Partial writes roll back and the bounded retry policy produces one committed result or a visible failure. |

Encoding checks round-trip `BIGINT`, exact aggregate values, negative amounts, and `DATE` values through the SQL driver and public boundary schemas. Chart formatting never changes the exact values used by evidence tables.

Migration tests cover an empty database and an upgrade with existing financial records. Restore checks cover database records and their R2 evidence together. An isolated hosted suite verifies PlanetScale roles, TLS, Hyperdrive pooling, fresh reads, and connection recovery. Local Postgres tests do not stand in for that hosted integration.

## Extraction and interpretation evaluation

A checked corpus includes headerless CSVs, empty card balances, multiline PDF descriptions, repeated headings, rewards rows, foreign currency, refunds, and conflicting sources.

Public fixtures are synthetic. Private statement evaluations use local or access-controlled sources and store only aggregate results in ordinary CI artifacts.

Extraction evaluation measures row completeness, date and amount accuracy, sign accuracy, and statement reconciliation. Categorization evaluation measures accuracy by role and category, ambiguity detection, and the financial amount affected by errors.

The model is compared with deterministic rules and prior accepted mappings. Evaluation separately measures unresolved cases rather than rewarding unsupported guesses. A model upgrade must preserve accepted corrections and improve or maintain the relevant checked outcomes.

## Analyst evaluation

An investigation corpus contains questions with independently verified calculations and supporting records. Checks verify that the answer uses the correct date range, reports complete contributors, and identifies missing coverage.

Scenarios include a mortgage-era comparison, a switch from debit to credit, a trip with advance bookings, an annual bill, a partial reimbursement, and a changed subscription.

Tool results are checked directly. Narrative checks verify agreement with those results and distinction between fact and inference. Model judges can assess clarity, but they cannot be the sole authority for numerical accuracy.

Clarification tests verify concrete questions, retained pending state, subject-version checks, one-time application, and subsequent recall. Context tests verify that model summaries cannot overwrite confirmed facts.

## Forecast evaluation

Rolling-origin backtests evaluate forecasts using only information available at each cutoff. Metrics cover absolute error, bias, and interval coverage at several useful horizons.

Every candidate is compared with a simple baseline. Scheduled obligations and variable spending are checked for double counting. A data gap before today must remain visibly estimated.

Scenario tests verify that overrides change only the intended assumptions, preserve historical data, and include explicitly modelled substitution effects.

## Repository test ownership

[Monorepo and ownership](/technical/monorepo#build-test-and-change-ownership) defines package-level test responsibilities, import restrictions, and browser bundle checks. Contract changes typecheck and test their consumers. Infrastructure tests verify the composed service graph and capability wiring.

Effect modules use `@effect/vitest`. React components use Vitest Browser Mode. Local Cloudflare integrations use `alchemy/Test/Vitest`, and complete browser flows use Playwright.

Each workspace keeps tests in `tests/`, mirroring the paths under `src/`, with a separate test TypeScript project. Module and component files use `.test.ts` or `.test.tsx`. Infrastructure suites live in `infra/tests/` with `.integration.test.ts`. Deployed browser suites use `.browser.test.ts`.

`pnpm check`, `pnpm typecheck`, and `pnpm test` are the root validation commands. Implemented database suites provision isolated local PostgreSQL instances in ordinary CI and need no production credentials. `pnpm test:infra-live` creates real hosted resources and is reserved for deployed behavior, including the isolated PlanetScale integration. Financial suites accompany their implementations. These specifications do not claim that those future suites already exist or pass.

## Completion evidence

The complete spend-management implementation is accepted when every product page's required behavior is implemented, its acceptance scenarios pass, and analyst results trace to verified calculations. Each requirement has a verification result or an explicit outstanding check.

Private-corpus validation accounts for every supplied source. Unresolved records identify specific missing or conflicting evidence. A parser failure or a blanket review state is an implementation defect, not proof that the source was handled.

The evidence includes recovery and access checks, mobile and keyboard flows, model evaluation results, and forecast backtests. Performance checks use the actual corpus and realistic growth, with measured query latency and bounded model usage.
