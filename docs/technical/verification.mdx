## Financial invariants

| Introduction | Regression to prevent                                                            |
| ------------ | -------------------------------------------------------------------------------- |
| Stage 1      | Reupload or overlapping exports duplicate transactions.                          |
| Stage 1      | A deduplication key collapses two real identical purchases.                      |
| Stage 1      | Missing or reused OFX IDs create false matches or reject valid history.          |
| Stage 1      | Missing rows or balances are silently labelled complete history.                 |
| Stage 1      | A failed or repeated publication creates partial or duplicate financial records. |
| Stage 2      | PDF decoding changes dates, decimal placement, signs, or row counts.             |
| Stage 3      | Splits create or lose money; repeated credit links over-reimburse a cost.        |
| Stage 3      | Transfers and card settlements count as additional income or spending.           |
| Stage 3      | Reprocessing or model suggestions overwrite user corrections.                    |
| Stage 4      | A headline mixes records from before and after a correction.                     |
| Stage 4      | Contributor totals, counts, and average-payment explanations disagree.           |
| Stage 5      | A scheduled cost remains in the variable baseline and is counted twice.          |

Money/date cases cover exact decimal decoding, negatives, supported range, leap days, calendar boundaries, value dates, and timezone handling. Driver encoding preserves BIGINT and DATE without an intermediate floating-point or local-midnight conversion.

## Database transactions

Use real PostgreSQL and production migrations for transaction and concurrency tests. Mocked SQL and SQLite cannot prove Postgres isolation. Test two overlapping imports, two commands claiming the same remaining credit, repeated command IDs, stale previews, and a committed write whose response is lost.

An injected failure before commit leaves no partial financial rows or receipt. A repeated successful command returns its result once. The same source published through a new action also cannot add records twice. Matching reads current records after acquiring the financial write lock. A correction made during parsing remains authoritative.

Related totals read consistent data. Through Hyperdrive, a query after a committed correction must see fresh values. Verify actual hosted roles, TLS, binding behavior, and database access separately from local database tests.

Test migrations from empty and previously populated databases when changing schema. Verify the chosen managed backup restore into an isolated environment, including correction preservation and access to independently retained source files. Repeated quarterly drills or a custom cross-store restore suite are not required.

## Extraction and interpretation evaluation

Inspect `fixtures/README.md` and the actual local files in `fixtures/commbank/`. Ordinary CI uses synthetic fixtures and runs without private data. Publish aggregate evaluation results only.

Stage 1 checks every supplied CSV and OFX. Cover headerless CSV, quoted/multiline fields, empty card balances, OFX 1.02 SGML, declared encoding, date-only values, offset-free timestamps, bank/card envelopes, and blank/reused FITIDs. OFX and CSV each work without a companion file.

Stage 2 checks every PDF, including multiline descriptions, repeated headings, rewards rows, foreign money, and visible decimal repairs. Compare row completeness, dates, exact signed amounts, and available balances against source evidence. Validate the chosen library in the hosted runtime.

Run overlapping files in different orders. Report accepted, matched, and unresolved rows, with the reason for each unresolved class. Compare final history after the same explicit review decisions. Fix missing deterministic matches and parser defects. A blanket review result is not successful ingestion; neither is a guessed duplicate merge that lowers the review count.

Stage 3 checks representative category suggestions, conflicting rules, manual single/bulk categorization, invalid model output, and provider failure. Accepted corrections must survive all of them. Use task-relevant examples without mandatory sample quotas or a model confidence score as a correctness gate.

## Analyst evaluation

Use questions with independently verified API results. Check dates, scope, coverage, source links, and whether the narrative agrees with financial tool output. A model judge is not the sole authority for numerical accuracy.

Verify that source text and model output cannot authorize writes. Suggested edits need explicit user acceptance and current version checks. Exercise failed answers, stop, and reconnect using the real SDK integration. After note removal, a fresh conversation must not inherit the withdrawn note through old transcripts or summaries.

## Forecast verification

Check the deterministic baseline, included schedules, one-offs, and scenario differences against independently calculated examples. Missing weeks remain missing. Scheduled costs are excluded from the variable mean before being added once. The cash calendar distinguishes payments from costs.

Changing a scenario preserves historical records and baseline commitments. Verify expected labels for estimates and historical balance dates. Statistical model selection, calibration thresholds, and probabilistic backtesting are outside the implemented forecast contract.

## Runtime and browser coverage

Exercise upload through transaction detail, a specific review decision, retry after failure, and the lost-write-response case. Browser refresh restores truthful import status even if a Workflow failed before writing its summary. Built-in workflow behavior needs integration verification, not a duplicate test suite for a custom execution engine.

Every stage checks desktop, mobile, keyboard navigation, source access, empty states, pending changes, failures, and unavailable data. Use the same public operations as the UI. Model tests use controlled external adapters plus a bounded live check for any selected document/tool format.

## Repository test ownership

Use existing workspace conventions. Effect modules use `@effect/vitest`, React components use Vitest Browser Mode, local Cloudflare integration uses `alchemy/Test/Vitest`, and complete browser flows use Playwright where needed. Tests remain under workspace `tests/`, mirroring `src/`, with separate test TypeScript projects. Infrastructure integration and browser suites stay in `infra/tests/`.

Run `pnpm check`, `pnpm typecheck`, and `pnpm test` before committing. `pnpm test:infra-live` is for isolated hosted checks. Database suites use disposable local Postgres with the same major version and migrations as production. Run `pnpm docs:doctor` and `pnpm docs:build` for documentation changes.

## Completion evidence

A stage is accepted when its frontend and backend work together, required outcomes have evidence, and earlier behavior remains correct. Report specific outstanding external checks rather than treating local success as proof of hosted behavior. Performance checks use actual input sizes and observed latency before justifying another runtime or more complex processing.
