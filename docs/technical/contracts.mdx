The implementation owns boundary schemas and infers TypeScript types from them. The RPC binding derives callable methods from the server implementation. This page defines shared meaning, not a second handwritten catalog of every future payload. Introduce fields when their behavior arrives in [Stage boundaries](/technical/stage-boundaries).

## Values

| Value             | Contract                                                                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Entity ID         | Stable server-generated identifier, typed by entity kind.                                                                                                      |
| Money             | Currency plus signed integer minor units. JSON encodes the integer as a decimal string, domain code uses bigint, and Postgres stores booked amounts as BIGINT. |
| Fractional amount | Exact decimal or rational calculation until the documented rounding boundary.                                                                                  |
| Calendar date     | Valid YYYY-MM-DD date, stored as DATE.                                                                                                                         |
| Instant           | UTC timestamp, stored as TIMESTAMPTZ.                                                                                                                          |
| Period            | Inclusive start and exclusive end calendar dates.                                                                                                              |
| Version           | Increasing version of a mutable record, used to reject stale edits.                                                                                            |
| Source identity   | SHA-256 of the verified bytes within the authenticated owner's data.                                                                                           |

Amounts retain their currency. Missing amounts are unavailable, never zero. [Calculation rules](/technical/calculation-rules) owns metric definitions and rounding.

Validate imported bytes, browser input, and model output at their boundaries. Internal decoded values use their types without repeated validation. Persisted structured payloads carry a version when deployment changes can affect their interpretation.

## Ownership and caller context

The web Worker derives the owner from verified authentication. The processor obtains it from the accepted import, and the analyst from its authenticated connection. User input and model tool arguments cannot select a trusted owner or actor. Every financial operation checks ownership of referenced records.

The analyst uses read-only financial tools. A user accepts a suggested change through an authenticated application control using the ordinary command interface.

## Lists and details

Stage 1 transaction filters cover account, currency, posting date, signed amount, original description, and import review state. Details contain the posting, source evidence, and relevant review items. Stage 3 adds interpretation and semantic filters. A newly recorded posting can still have no interpretation after stage 3 begins.

Lists use bounded pages and a deterministic sort, with posting date and ID as transaction tie-breakers. Cursor values represent the last sort key for the selected query and are validated as input. Authorization always applies independently of the cursor. Changing filters resets pagination. Live lists may change between pages; refreshing restarts from current data. Unrelated writes do not invalidate every cursor.

## Queries and evidence

Stage 4 queries identify the metric, resolved period, comparison period, date basis, currency, accounts, and implemented filters. Values within one filter dimension combine with OR; dimensions combine with AND. Category selection includes descendants. Deduplicate allocations before grouping overlapping tags or personal events.

Results include the resolved query, calculation time, values and units, coverage limitations, and contributing record references. Related totals and contributions use the same calculation population. A drill-down reruns that query against current data and refreshes its headline with the rows. It never presents changed rows as the evidence for an unchanged old total.

Coverage distinguishes observed dates, statement coverage, reconciled intervals, missing records, and unresolved interpretation. Each metric assesses its own evidence. A bank balance can be known when categories are unknown. Unresolved financial roles can prevent a complete spending total.

Forecast and scenario results in stage 5 contain estimates, assumptions, baseline periods, and missing inputs, as defined in [Calculation rules](/technical/calculation-rules#forecast-contract). Conversation messages in stage 6 use SDK message types and tool results.

## Commands and receipts

A financial command has a client-generated command ID, its typed input, and expected versions for records being edited. The API stores the command's input identity and result in the same transaction as the financial change. Repeating the same command returns its stored result. Reusing its ID with different input returns a conflict.

This receipt resolves a lost response to a financial write. It is not an execution log for parsing, model calls, or reads. Source hash and observation identity also protect imports repeated through a new browser action.

Single-record edits check that record's version. Bulk and relationship previews contain the proposed change and affected record versions. Acceptance rechecks those records and conservation constraints in the write transaction. For a bulk edit, rerun its selection and require the same target set shown in the preview; new matching records require another preview. Stale previews leave data unchanged and ask the user to review the current impact. Preview storage is an implementation choice; no global dataset revision is needed for unrelated edits.

## Failures

Expose an actionable distinction between invalid input, missing or unauthorized records, conflicting edits, import review, and a failed external operation. Keep the user's selected filters and edit input where possible. Failed jobs offer retry; uncertain classification offers manual review. A network error alone does not prove a financial write rolled back, so retry that command with its existing ID.

Timeouts and input limits are bounded configuration chosen for the actual workload. They do not require multiple fallback implementations or custom recovery states.
