# The Workbench

The workbench is where strategies face history before they face money: the research surface behind every backtest a trial report cites, every gate a proposal must pass, and every "would this have worked?" question the operator asks. The gate pipeline ([Sleeves](./02-sleeves.md)) is its automated customer; the operator is its interactive one.

## Historical data

The engine continuously collects market data (candles, at the timeframes mandates require) for every instrument in any mandate's universe, plus a configurable watchlist. The workbench shows **coverage plainly**: which instruments, which timeframes, what date ranges, and — crucially — where the gaps are. A backtest over gappy data says so on its face; it never silently interpolates. Historical depth is extended by deliberate backfill, which is itself a recorded act with a source.

## Backtests

A backtest runs a complete strategy configuration (a mandate, or a candidate version of one) against a chosen slice of history, through the same `strategy → cage → simulated fills` code path the live engine uses. Every backtest:

- **Is reproducible.** It records the exact configuration, code version, data window, and cost model it ran with; running it again produces the same result, and any report citing it links to it.
- **Models costs.** Fees at the venue's real schedule and a slippage model are always on; a costless backtest does not exist in this product.
- **Reports against benchmarks.** The same benchmark set the mandate declares — buy-and-hold of the universe always included — plus the standard risk statistics (drawdown, worst day, streaks) that trial reports use.
- **Defaults to walk-forward.** The headline result is out-of-sample by construction: fit/tune on one window, evaluate on the next, rolled forward. A single-window in-sample result is viewable but always labeled as the weaker thing it is.

## The trial count

The workbench counts trials. Every backtest run against a given strategy family increments a visible counter, and comparative displays ("best of these 12 variants") always show the count and frame results accordingly — the more candidates were tried, the more impressive a result must be before it is called evidence. This is the product-level defense against the lucky-monkey problem: the system makes it structurally awkward to launder a best-of-many backtest into a promotion argument, whether the many were generated by AI or by an enthusiastic operator.

## Gate runs and shadow runs

Design-time proposals ([Sleeves](./02-sleeves.md)) pass through the workbench's machinery, and their progress is visible here: each proposal's gate results (schema, backtest reproduction, walk-forward, shadow performance) as they complete, and the queue of what awaits the operator. **Champion/challenger shadow runs** — a candidate configuration running in simulation beside the incumbent, on live data — appear with both curves and the running comparison, under the same display discipline as everything else (simulated is always marked simulated).

## What the workbench is not

It is not the proving ground — dry run is. A backtest, however clean, is evidence about the past; the lifecycle's dry-run stage exists because live markets are the only honest test of execution, data, and behavior together. The workbench's job is cheaper: kill bad ideas early, kill lucky ideas reliably, and give surviving ideas a defensible number to carry into their trial.
