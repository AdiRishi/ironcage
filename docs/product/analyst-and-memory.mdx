All behavior here belongs to [stage 6](/stages/analyst). Earlier stages already provide the corresponding financial operations through working screens.

## Answers with evidence

Ask a question or attach a transaction/chart selection. The analyst can inspect recorded history, compare periods, explain contributors, and evaluate the existing deterministic scenarios. Numerical answers use the same financial queries as the UI and show calculation time, scope, coverage, and supporting links.

The analyst distinguishes observations from possible explanations. Missing card history is a coverage issue, not evidence of lower spending. If tools or records cannot answer a question, it explains the limitation or asks for the specific missing information.

## Clarification and changes

Clarifications remain in conversation history so the user can return later. A suggested correction opens the existing edit/review control or a confirmation card. Even an unambiguous textual edit waits for that user action before changing financial records. Bulk edits and financial relationships use their existing impact previews.

If records changed in the meantime, acceptance checks the current versions and asks for an updated decision. The analyst cannot change bank values, categories, or rules merely by producing text.

## Useful memory

Start with explicit notes the user chooses to save. Notes can have an account or period scope. Account roles, personal events, and classification rules remain editable through their existing controls. Casual conversation does not automatically become a permanent fact.

The user can edit or remove a note. The confirmation explains that subsequent analysis starts in a fresh conversation using current notes, so an old transcript cannot reintroduce the removed fact. Earlier conversations remain available for inspection but cannot continue with the withdrawn context. Existing financial records and notes remain available in the fresh conversation.

## Continuing work

Show an active answer, completed messages, and clear failures. Only one answer runs at a time in a conversation. The user can stop it before submitting another question.

Use the SDK's persistence and reconnect behavior to restore available messages or an ongoing stream. If execution failed, the user can ask again. The answer may restart and incur another model call. The product does not promise recovery from every internal step.

Historical messages keep their text and displayed calculation time. A link to live records or a repeated question uses current data. A chat answer is not a permanent snapshot of the financial database.

## Saving useful work

Use the existing saved-analysis controls to retain a useful query or scenario definition. It runs on open or explicit refresh. There is no requirement for arbitrary generated scripts, child investigations, or replayable computation artifacts.
