title: Imports
description: Upload statements, record bank transactions, and resolve uncertain evidence.

Stage 1 supports CommBank CSV and OFX. Stage 2 adds PDF and source-data controls. Stage 3 adds independent interpretation. Importing and recording a transaction never requires its category to be known.

## Upload and record

Choose files, confirm the account when the source cannot establish it, and inspect per-file progress. The result shows new transactions, matched records, repeated files, and specific unresolved rows. A failed file does not prevent unrelated files from completing.

CSV and OFX each work independently. The app retains original files and their extracted rows. Filenames are labels, not evidence of account identity or complete history. From stage 2, PDF rows link to the relevant statement page.

The transaction list shows accepted bank amounts, dates, descriptions, and accounts. Source evidence remains accessible from each record. A shorter later export does not remove previously accepted history.

## Repeated data

The same verified bytes have one source identity even under a different filename. A repeat upload adds no duplicate postings. Overlapping exports can attach more evidence to existing postings. CSV, OFX, and PDF can support the same purchase.

Two real purchases with the same date, merchant, and amount remain distinct. Bank transaction IDs are useful only when their account and values agree. Missing or reused IDs do not remove a purchase. Plausible duplicate ambiguity goes to review instead of being silently merged or accepted as another purchase.

## Review

A review identifies the source row, uncertainty, and candidate choices. The user can confirm the account, resolve a value against visible evidence, identify an existing posting, or confirm a separate purchase. Accepted decisions survive reprocessing.

Uncertain amounts and posting identities remain outside confirmed totals. Dismissing a question does not turn a missing amount into zero. An otherwise valid posting is recorded even when its financial role is unknown. From stage 3, an established cost with an unknown category contributes as unclassified.

Parser defects remain implementation work. Human review is for specific ambiguity or missing evidence, not a substitute for implementing the supported formats.

## Coverage

Distinguish requested export periods, observed transaction dates, stated coverage, and reconciled intervals. A file named for two years may contain only two weeks. Missing records differ from an evidenced interval with no activity. Balances and supplied statement totals support reconciliation where available.

## Failure and retry

A failed action may require the user to retry, reupload, or resolve a specific uncertainty. It leaves accepted history consistent and cannot duplicate records when repeated.

If upload succeeded, retain the source and offer processing again. If bytes were not received completely, ask for reupload. Processing may restart from the beginning; the product does not promise to resume a particular step or avoid every repeated model call.

Refreshing the browser restores the stored import summary or current processing status. A failure remains visible with the next action. Retrying after a lost publication response returns the committed outcome rather than recording the file twice.

## Interpretation after recording

Stage 3 provides a separate action to interpret recorded history, including earlier imports. User corrections and accepted rules take precedence over model suggestions. Failed or uncertain categorization leaves the bank transaction intact and offers manual single or bulk categorization.
