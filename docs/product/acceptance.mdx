title: Acceptance scenarios
description: Observable outcomes for each working stage.

Each scenario applies from its introduction stage and remains a regression afterward. Imports cover CSV/OFX in stage 1 and extend to PDF in stage 2. Values are fictional. The [stage pages](/stages) supply the complete flows and stopping points.

## Import and recorded history

| Stage | Scenario                                                        | Required outcome                                                                                     |
| ----- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 1     | Upload identical bytes with a different filename.               | Existing source identity and no additional postings.                                                 |
| 1     | Upload overlapping exports in different orders or concurrently. | The same evidence and explicit review decisions produce the same bank history, without false merges. |
| 1     | Two same-day purchases share merchant and amount.               | Both remain recorded.                                                                                |
| 1     | Upload standalone CSV or OFX.                                   | Each works independently; account ambiguity asks a specific question.                                |
| 1     | Reuse or omit an OFX transaction ID.                            | The importer checks other evidence and does not collapse distinct purchases.                         |
| 1     | A file claims two years but contains two weeks.                 | Coverage reflects the file evidence.                                                                 |
| 1     | Keep an amount or duplicate identity unresolved.                | The affected row stays outside confirmed totals and remains reviewable.                              |
| 1     | One file fails in a batch.                                      | Other files complete. The failed file can be retried or reuploaded.                                  |
| 1     | Publication commits but the response is lost.                   | Repeating the action returns the accepted records without duplicates.                                |
| 1     | Refresh after processing stopped unexpectedly.                  | Status identifies the stopped work and offers retry.                                                 |
| 1     | Access evidence without authentication.                         | Access is denied.                                                                                    |
| 1     | Change an account role with an effective date.                  | Earlier periods retain the earlier role.                                                             |
| 2     | Import one purchase represented in CSV, OFX, and PDF.           | One posting has the supporting observations after any necessary review.                              |
| 2     | A PDF field cannot be decoded reliably.                         | Show its page and the specific uncertainty. Never invent a value to pass reconciliation.             |

## Interpretation and corrections

| Stage | Scenario                                                         | Required outcome                                                                     |
| ----- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 3     | Interpret history recorded before stage 3.                       | Existing postings gain interpretation without reupload or new posting identity.      |
| 3     | Classification fails or returns an unknown category.             | The posting remains; the user can categorize directly or through bulk review.        |
| 3     | Accept a model suggestion, then correct it.                      | The user correction wins over future suggestions and rules.                          |
| 3     | Import an older overlapping statement after a correction.        | The correction and posting identity survive.                                         |
| 3     | Buy $100 on a card and repay $100.                               | Spending is $100. Both bank movements remain.                                        |
| 3     | Move $2000 between owned accounts.                               | Income and spending do not increase. Missing counterpart evidence remains explicit.  |
| 3     | Pay $300 and receive $200 confirmed reimbursements.              | Net personal cost is $100; available credit cannot be applied twice.                 |
| 3     | Link a refund in a later month.                                  | Net cost changes in the original purchase period; the credit keeps its posting date. |
| 3     | Pay $3900 against a loan with $2800 interest in the same period. | Distinguish $3900 cash outflow, $2800 cost, and $1100 net principal reduction.       |
| 3     | Interest posts August 31 and repayment September 2.              | Each period keeps its actual components. Linking never moves the interest date.      |
| 3     | Split a cost or preview a broad rule.                            | Allocations conserve the amount and individual exceptions survive.                   |
| 3     | Accept a stale relationship preview.                             | No change commits; show current impact for another decision.                         |
| 3     | Undo an interpretation correction.                               | A new correction restores the prior interpretation and preserves source evidence.    |
| 3     | Rename an existing category.                                     | Identity and transaction links remain intact.                                        |

## Exploration and planning

| Stage | Scenario                                               | Required outcome                                                                                                               |
| ----- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 4     | Open a chart contributor after an intervening edit.    | Its current headline and rows agree, with the original query scope retained.                                                   |
| 4     | Compare a partial month or incomplete account history. | Match elapsed dates and disclose missing coverage separately.                                                                  |
| 4     | Compare against zero prior spending.                   | Show absolute change; percentage change is unavailable.                                                                        |
| 4     | Compare $200 from ten purchases with $300 from twelve. | Show counts, $20/$25 averages, and a consistent $100 difference.                                                               |
| 4     | Select two tags on one purchase.                       | Count it once and label overlapping group breakdowns.                                                                          |
| 4     | Include trip bookings paid before travel dates.        | Membership includes them without duplicating overall spending.                                                                 |
| 4     | Purchases shift from debit to credit.                  | Combined purchase trends retain continuity.                                                                                    |
| 4     | Request a daily average with missing coverage.         | Average is unavailable; known total and requested denominator remain visible.                                                  |
| 4     | Reopen a saved analysis after import.                  | Run its saved definition against current data. Fixed dates remain; relative dates resolve on opening.                          |
| 4     | Correct a transaction while viewing results.           | Visible queries refetch, without requiring a background saved-result history.                                                  |
| 5     | Confirm a quarterly levy.                              | Cash calendar keeps its payment date; ordinary costs allocate its obligation across the applicable period.                     |
| 5     | Change a commitment amount or account.                 | Future occurrences use the effective change; earlier segments stay intact.                                                     |
| 5     | Inspect ordinary-cost contributors.                    | Rounded components add to the headline and identify their baseline or schedule evidence.                                       |
| 5     | Open a cost outlook with insufficient baseline data.   | Overall estimate is unavailable; the commitment calendar remains usable.                                                       |
| 5     | Compare fewer delivery purchases with more groceries.  | Only explicit scenario changes affect the estimate. Actual records remain unchanged.                                           |
| 5     | Inspect the cash calendar beside the cost estimate.    | Repayments are cash movements, not additional costs. Historical balances keep their dates; no future bank balance is invented. |

## Analyst and follow-through

| Stage | Scenario                                                    | Required outcome                                                                                                |
| ----- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 6     | Ask a numerical question.                                   | Answer agrees with API calculations and identifies time, scope, coverage, and evidence.                         |
| 6     | Request a textual financial edit.                           | Prepare a suggestion; apply only after explicit user acceptance through the normal command.                     |
| 6     | A source description instructs the analyst to make changes. | Treat it as data, with no mutation authority.                                                                   |
| 6     | Return to a clarification later.                            | Conversation history retains the question; any proposed edit checks current records.                            |
| 6     | Close the browser, stop, or encounter provider failure.     | SDK persistence restores available messages; failed work can require a new request.                             |
| 6     | Submit while another answer runs.                           | Wait for completion or stop before sending another question.                                                    |
| 6     | Remove a personal note.                                     | Continue in a fresh conversation using current notes; the old transcript remains inspectable but is not reused. |
| 6     | Access a conversation without authentication.               | Message, stream, and evidence access are denied.                                                                |
| 7     | Dismiss a finding and run another unchanged scan.           | It stays dismissed and creates no repeated notification.                                                        |
| 7     | Observe a new change period or correct its evidence.        | Create a genuinely new finding or close the unsupported finding.                                                |
| 7     | Track reduced delivery costs with selected grocery costs.   | Compare the chosen measures and disclose insufficient evidence without claiming causality.                      |
| 7     | A scan fails.                                               | Show failure and permit another scan without changing financial history.                                        |
| 7     | Disable import reminders.                                   | Stop those reminders while retaining other inbox work.                                                          |

## Data controls and stage completion

| Stage | Scenario                                                          | Required outcome                                                                                       |
| ----- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 1     | Restore the managed database backup into an isolated environment. | Bank records and corrections are intact; independently retained sources can be accessed or reattached. |
| 2     | Export implemented financial data.                                | Download identifies its contents and time; a failed export can be requested again.                     |
| 2     | Remove the last original source file for a posting.               | Keep the posting and extracted evidence, and mark the original unavailable.                            |
| 2     | Reupload a removed source.                                        | Restore source access without adding transactions or needing withdrawal undo.                          |
| 2     | A model call reports no usage after failure.                      | Show unknown usage and disclose that retry may incur another charge.                                   |
| 2     | Disable AI or reach the observed-usage warning threshold.         | Stop new calls according to the displayed policy; ordinary recorded history remains available.         |

Every stage demonstrates its required flows on desktop, mobile, and with a keyboard. Each later stage extends financial exports to its new records. [Verification](/technical/verification) maps these outcomes to focused implementation checks.
