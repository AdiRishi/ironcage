title: Decisions
description: Why the architecture looks the way it does.

Each entry records a decision, the reason, and what would change it. Newer entries come first.

## The analyst is Effect AI in a Durable Object

**Decision.** The analyst is an Alchemy Effect Durable Object, `Conversations`, hosted by a small Analyst Worker. It keeps conversations in the object's SQLite through `@effect/sql-sqlite-do` and calls the model through Effect AI's `LanguageModel`, `Chat`, and `Toolkit`, with Alchemy's Workers AI adapter behind its own AI Gateway. A question is stored as a queued turn and answered by the object's alarm, and the web app polls the conversation. It replaces the plan for an Agents SDK `AIChatAgent`.

**Why.** The rest of the system is Effect, and the object is an Effect layer like the API. It reads the API through a binding typed `ApiClient<AnalystOperation>`, so calling any command other than recording its own model usage fails to compile, and `FinanceError` crosses every hop as the class. Tools take their parameters from the contract schemas. `AIChatAgent` is a plain Durable Object subclass, so it would need hand-written RPC to the API, a second AI stack with its own schema adapters, a WebSocket outside the server functions, and tests in the Workers pool. It adds resumable token streams and broadcast to several clients, which the product does not use, because an answer appears only after its figures are checked. The analyst's tests run the same SQL on `node:sqlite` and replace only the API and the model.

**Would change if** answers need to stream as the model writes them, or several people share one deployment.

## Alchemy is patched until upstream has the fixes

**Decision.** `patches/alchemy@2.0.0-beta.79.patch`, made with `pnpm patch`, changes Alchemy's TypeScript source, which Workers bundle, and its compiled `lib` files, which Node and the type checker load. Docker container and volume reads accept a resource with no previous inputs. `bindWorker(worker, { errors })` revives the declared error classes, as a Durable Object's `errors` already does. The Workers AI `LanguageModel` fails with the matching `AiError` reason when the reply has an HTTP error status, instead of returning an empty answer. It leaves token counts the reply does not report undefined instead of zero, and it accepts `reasoningEffort` and extra request headers.

**Why.** Each change fixes a bug or adds a missing option that the analyst, the model usage records, or the local stack depend on. Each is small enough to send upstream as it is. Wrapping Alchemy in application code would copy its adapter and binding code.

**Would change if** an Alchemy release includes the changes. The patch then shrinks or goes away with the upgrade.

## Counterparty history as row images, undone last first

**Decision.** A counterparty change stores every record it wrote, counterparties, aliases, reference defaults, and the events, rules, and movement-link snapshots it pointed elsewhere, as it was before and as the change left it. Undo is a new change that writes the before images back, and only while every record is still as the change left it.

**Why.** A merge deletes its source, and a descriptor move changes the meaning of every transaction the bank writes that way, so undo needs the rows themselves, not a description of the command. Replaying an earlier snapshot, as an event correction does, would silently revert later changes to the same records, such as renaming the target of an old merge. Refusing until the later change is undone keeps undo exact.

**Would change if** undoing one change often has to wait on a long chain of later ones, which would call for a merge of images instead of last in, first out.

## Previews run the write and roll it back

**Decision.** A preview of a counterparty change, an undo, or a counterparty move runs the command's real write inside a write transaction, measures every month whose facts it changed, and rolls back.

**Why.** A counterparty change reaches its transactions through reinterpretation, and a second model of that derivation for previews would drift from the command. Running the write gives the preview the same checks, the same derivation, and the same facts the overview will read. The write also reports how many transactions change meaning, which a totals-only preview misses when a change moves spending between categories and leaves every total as it was.

**Would change if** previews of large merges hold write transactions long enough to cause serialization retries for other writers.

## Serializable writes instead of one lock

**Decision.** Every write runs as a `SERIALIZABLE` transaction and runs again when Postgres reports a serialization failure. The events a transaction changed are noted in a transaction-local setting and their facts refreshed before commit.

**Why.** One advisory lock serialized every write, so a long publication or a large recategorisation blocked every other write, and background writers make that worse as history grows. Serializable isolation keeps the guarantee the lock gave, a result equal to some serial order, while writes to different records run at once. A stale flag on events would have been a shared marker every write reads, which makes any two concurrent writes conflict.

**Would change if** retries become frequent enough to cost more than waiting, for example several background writers working on the same account.

## Model assignments apply automatically, with provenance

**Decision.** Enrichment applies counterparty identities and defaults when the model's confidence reaches the threshold, and asks about the rest. Every assignment records its source.

**Why.** Requiring a click on every suggestion left 9,256 of 9,263 allocations uncategorized. Provenance keeps the "trust through evidence" rule: every total can say how much of it rests on the model, and every value you set outranks the model permanently.

**Would change if** the check against your answers in Settings shows auto-applied assignments are wrong often enough to mislead totals.

## Interpret at the counterparty, not the transaction

**Decision.** The model resolves alias keys to counterparties with default categories and roles. Transactions inherit from their counterparty.

**Why.** Around 9,000 postings come from a few hundred to 1,500 counterparties. Resolving each alias once costs far fewer model calls, sends only descriptor text without amounts, and makes one correction fix every transaction from that counterparty.

**Would change if** a counterparty often needs different categories per purchase. Mixed retailers default to Shopping, then General, and a split handles the exceptions.

## Descriptor parsing is a shared pure function

**Decision.** The CommBank descriptor profile lives in `packages/finance` and runs in the API during publication and reinterpretation.

**Why.** Descriptors derive from one posting's description and account kind. Running them in the write transaction keeps the API the only writer without an extra RPC. File parsers stay in the processor because they carry large libraries.

## Analysis reads a projection written with each change

**Decision.** `ledger_facts` holds one row per allocation effect, rewritten by the command transaction that changes the event.

**Why.** Loading every event and posting for each request grows with history. The projection keeps period queries bounded and indexed. Writing it in the same transaction keeps read-after-write consistency, which a materialized view refreshed later would not.

## Four Workers with one writer

**Decision.** Web, API, processor, and analyst are separate Workers. Only the API has a database binding.

**Why.** One writer makes the write protocol, receipts, and serializable transactions the single place consistency is enforced. PDF.js stays out of the writer's bundle and CPU budget. Model calls run in the processor's enrichment Workflow and the analyst's Durable Object through the Workers AI binding, so a slow or failed call never holds a write transaction open.

## Postgres for financial records

**Decision.** PlanetScale Postgres through Hyperdrive, with a Docker Postgres of the same major version locally.

**Why.** Financial records outlive any platform choice. Postgres gives interactive transactions for the write protocol, `REPEATABLE READ` reads, `pg_dump`, and standard SQL tooling. D1 lacks interactive transactions. A Durable Object's SQLite would tie the records to one platform's storage.

## Exact integer money

**Decision.** Money is `bigint` minor units in code, `BIGINT` in Postgres, and a decimal string in JSON.

**Why.** Planned investment and crypto amounts exceed JavaScript's safe integer range at their native precision. Exactness costs little and removes a class of rounding bugs.

## Pre-release dependencies are deliberate

**Decision.** Effect 4, Alchemy 2, TypeScript 7, and Vite 8 track their latest releases, including pre-releases.

**Why.** The project follows these ecosystems closely. `.repos/` holds the pinned sources for reference, and `pnpm sync:repos` keeps them aligned.
