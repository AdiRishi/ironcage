---
title: Interpretation
description: How postings become financial events with counterparties, roles, and categories, and who decides each one.
---

Interpretation sits above the ledger. It never changes a posting. It decides who is on the other side, what role the money played, and which category it belongs to, and it records who made each decision.

```
posting ──► descriptor ──► alias ──► counterparty ──► event role + allocation category
            (bank profile)  (normalized)  (model or you)     (bank structure, counterparty, rules, you)
```

## Descriptors

A bank profile reads a posting's description and account kind into a descriptor. `descriptorProfiles` in `packages/finance/src/descriptors/index.ts` holds one profile per institution, and a posting uses the profile of its account's institution. The CommBank profile lives in `packages/finance/src/descriptors/commbank.ts`. A profile is a pure function with a version, so the API computes descriptors inside the publication transaction. Each stored descriptor records the profile and version that read it, and the API reads it again when its account's profile is different or newer. Adding a bank adds a profile to the registry; its type requires one for every institution.

```ts
type Descriptor = {
  profileVersion: number;
  channel:
    | "card"
    | "transfer"
    | "bpay"
    | "directDebit"
    | "directCredit"
    | "salary"
    | "cash"
    | "interest"
    | "fee"
    | "loan"
    | "cardPayment"
    | "other";
  counterpartyText: string | null; // "WOOLWORTHS METRO", "Jane Smith"
  aliasKey: string | null; // normalized counterpartyText, the grouping key
  cardSuffix: string | null; // "1234" from "Card xx1234"
  ownAccountSuffix: string | null; // "5678" from "Transfer to xx5678 CommBank app"
  payId: string | null;
  reference: string | null;
  referenceKey: string | null; // "rent" from "Rent Aug 2026"
  foreign: { currency: string; amount: string } | null; // "USD 12.34"
};
```

CommBank shapes the profile recognizes, with invented examples from `packages/finance/tests/descriptors/commbank.test.ts`:

| Shape                                                                                         | Channel        | Counterparty text              |
| --------------------------------------------------------------------------------------------- | -------------- | ------------------------------ |
| `WOOLWORTHS 1234 SYDNEY AU Card xx1234 Value Date: ...`                                       | `card`         | `WOOLWORTHS 1234 SYDNEY AU`    |
| `NETFLIX.COM Card xx1234 USD 15.99`                                                           | `card`         | `NETFLIX.COM`                  |
| `Refund Purchase MYER SYDNEY`, `Return UNIQLO 12345 Card xx1234`                              | `card`         | `MYER SYDNEY`, `UNIQLO 12345`  |
| `Transfer To Jane Smith NetBank Rent`                                                         | `transfer`     | `Jane Smith`, reference `Rent` |
| `Transfer To Jane Smith PayID 0412345678 from CommBank app dinner`                            | `transfer`     | `Jane Smith`                   |
| `Transfer to xx5678 CommBank app Savings`                                                     | `transfer`     | none, own suffix `5678`        |
| `Fast Transfer From John Citizen dinner split`                                                | `transfer`     | `John Citizen`                 |
| `Direct Debit 123456 ORIGIN ENERGY 0012345678`                                                | `directDebit`  | `ORIGIN ENERGY`                |
| `Direct Credit 654321 ATO ATO012345 1`                                                        | `directCredit` | `ATO`                          |
| `Salary ACME PTY LTD HR123456`                                                                | `salary`       | `ACME PTY LTD`                 |
| `BPAY` followed by a biller name and reference                                                | `bpay`         | The biller name                |
| `International Transaction Fee`, or a debit with no card marker that contains `Fee` or `Fees` | `fee`          | none                           |
| `Credit Interest`, `Bonus Interest`, `Interest charged`                                       | `interest`     | none                           |
| `Repayment/Payment`, `Loan Repayment LN REPAY 123456789`                                      | `loan`         | none                           |
| `Wdl ATM CBA ATM SYDNEY 123456`                                                               | `cash`         | none                           |
| Card account row with no marker, such as `SPOTIFY STOCKHOLM SE`                               | `card`         | `SPOTIFY STOCKHOLM SE`         |
| Card account credit starting `Payment`                                                        | `cardPayment`  | none                           |
| Deposit row with no marker, such as `UBER *TRIP HELP.UBER.COM`                                | `other`        | `UBER *TRIP HELP.UBER.COM`     |

An incoming transfer with no channel word, such as the `Fast Transfer From` row, takes up to four capitalised words as the name. The rest is the reference. Direct debits, direct credits, salary, and BPAY rows end the name at the first word that contains a digit.

The reference key, from `referenceKey`, lowercases the reference and keeps its words of three or more letters, without numbers or month names, so `Rent Aug` and `rent 2026` share the key `rent`.

The alias key uppercases the counterparty text, turns punctuation other than `&` and `'` into spaces, removes words that contain digits, drops a trailing country code, and collapses spaces. `WOOLWORTHS 1234 SYDNEY AU` and `WOOLWORTHS 5678 SYDNEY AU` share the key `WOOLWORTHS SYDNEY`. A transfer to an own-account suffix gets the key `ACCOUNT 5678`, so an account outside the ledger can be answered once.

On the corpus, the profile yields 1,203 alias keys for 9,224 postings, and 378 transfers name an own-account suffix. 272 of those name an account in the ledger; the other 106 name accounts outside it.

## Counterparties

A counterparty is who is on the other side: a `business`, a `person`, an `ownAccount` held outside the ledger, or an `institution` such as the ATO, a bank, or an insurer. It has a name, an optional brand, a default category, and for people and institutions an optional default role. `takesDefaultRole` in `packages/finance/src/interpretation.ts` says which kinds take one, for the counterparty page and for enrichment.

Aliases map alias keys to counterparties. Many aliases can point at one counterparty: `WOOLWORTHS SYDNEY`, `WOOLWORTHS METRO`, and `WW METRO` are all Woolworths. An event takes the counterparty of its primary posting's applied alias, unless you assigned one to the event.

Counterparties and aliases carry provenance: `model` when the enrichment pipeline created them, `user` when you did. A counterparty's status is `applied` or `proposed`. Only applied counterparties lend their own defaults to events; a proposed one still names the events it identifies, so the ledger can show it. A user-made counterparty or alias is never changed by the model.

An alias's status is also `applied` or `proposed`. A proposed alias comes from a model answer below the auto-apply threshold that named an existing counterparty. It stores the model's confidence and reason. The engine reads only applied aliases, so the events of a proposed alias have no counterparty until you answer its `alias` question.

A counterparty can also have defaults for one reference key, in `counterparty_references`. They outrank the counterparty's own default role and category for the payments that carry that key, so rent and a bill split paid to the same person can mean different things. A reference default is always yours, so it applies whatever the counterparty's status. The counterparty page lists the references on its payments, most frequent first, with any defaults you set.

Every change to these records is one `CounterpartyChange`, defined in `packages/contracts/src/finance/counterparties.ts`. It carries the version of each record it changes as you saw it, and a null version says the record did not exist yet. Counterparties, aliases, and reference defaults each have their own version, so moving a descriptor does not conflict with renaming the counterparty that held it. Each change recomputes the events it affects.

- `create` makes a counterparty with `user` provenance and status `applied`. It can claim alias keys, which become applied user aliases.
- `update` sets the name, kind, brand, and defaults, and makes the counterparty a user counterparty with status `applied`. Neither `create` nor `update` gives a person the default role `transfer`, which fails with `invalid` as it does for a reference default.
- `merge` joins a source counterparty into a different target and deletes the source. The target becomes a user counterparty with status `applied`, so a target the model proposed starts lending its defaults to its own transactions too. The source's applied aliases become user aliases of the target. Its proposed aliases move still proposed, with the model's confidence and reason, so their question names the target. Transactions assigned to the source by hand, transactions a movement link joined into another, movement-link snapshots, and rules that named it name the target, and each rule's version rises. Where both have a default for the same reference key, the target's default wins, and history keeps the source's.
- `moveAlias` points one alias key at a counterparty as an applied user alias. A move chosen from one transaction names that transaction and the version you saw. The transaction follows the descriptor afterwards, even if you had moved it to another counterparty by hand, and the change fails with `invalid` when the bank does not write it that way. Other transactions you moved by hand stay where you put them.
- `saveReference` and `deleteReference` set or remove the defaults for one counterparty and reference key. Saving one for a person the model proposed also confirms the person in the same change: it becomes a user counterparty with status `applied`, and the model's default role and category go, so its payments with other references still ask. Undo restores both. A person's reference default cannot be `transfer`: the change fails with `invalid` and says to mark the person as your own account instead.

`previewCounterpartyChange` and `applyCounterpartyChange` in `workers/api/src/interpretation/counterparties.ts` run every kind. `planChange` in `workers/api/src/interpretation/counterparty-changes.ts` reads the records a change touches, checks their versions, and plans it as row images: each record it alters, as it is and as the change leaves it. A change that alters nothing records nothing and returns no change ID. `applyImages` writes the images in dependency order with plain inserts, updates, and deletes, so the fact triggers see each one, and then reinterprets the events of every counterparty and alias key the images name. It deletes a counterparty last, and only when no transaction, descriptor, reference default, rule, or movement-link snapshot outside the change still names it. Otherwise the change fails with `conflict` and says what still names the counterparty. The contract refuses a merge into the same counterparty. A default category that `create`, `update`, or `saveReference` newly sets must be active. A record can keep a category archived since, which the engine ignores, so merges and undos write back whatever the records held.

A default category can move every transaction of a counterparty without changing any total, so a preview of a change reports how many transactions change meaning as well as the months whose measures change. A preview of a descriptor move chosen from one transaction also returns that transaction as the move leaves it.

`searchDescriptors` finds the alias keys whose printed text or key contains the search, or whose counterparty's name does. Each match has its most frequent printed texts, its active transactions, and the counterparty that holds it with the alias's status and version, so a counterparty page can take the descriptor with a `moveAlias` change. The counterparty list searches names, brands, alias keys, and printed text the same way. Both match through `containsText` in `workers/api/src/database/columns.ts`, a case-insensitive `ILIKE` in which `%` and `_` match only themselves. Trigram indexes from migration `0028_counterparty_history.sql` serve it.

## Roles

The role of an event comes from, in order:

1. Your correction on the event. A movement link also fixes the role, and so does an accepted credit link or fee association that depends on it.
2. A rule that sets a role.
3. Bank structure, described below.
4. The counterparty's default role for the payment's reference key, when you set one, otherwise its own default role, set by you or proposed by the model. This decides transfers to and from people and direct credits: rent to a landlord is a `purchase`, a friend repaying dinner is a `reimbursement`, and money to your own account at another bank is a `transfer` to an external endpoint.
5. Otherwise the event is `unresolved` and raises a question.

Bank structure is `bankReading` in `packages/finance/src/interpretation.ts`. It uses the descriptor, the sign, and the account kind. An own-account suffix matches one of your accounts when it equals the last four digits of the account number.

| Descriptor                                            | Debit            | Credit           |
| ----------------------------------------------------- | ---------------- | ---------------- |
| Own-account suffix of a deposit account               | `transfer`       | `transfer`       |
| Own-account suffix of a card account                  | `cardSettlement` | `transfer`       |
| Own-account suffix of a loan account                  | `loanPayment`    | `borrowing`      |
| `interest`                                            | `financingCost`  | `income`         |
| `fee`                                                 | `financingCost`  | `refund`         |
| `loan` on the loan account                            | `borrowing`      | `loanPayment`    |
| `loan` on another account                             | `loanPayment`    | `borrowing`      |
| `cardPayment`                                         | `cardSettlement` | `cardSettlement` |
| `card`, `directDebit`, `bpay`                         | `purchase`       | `refund`         |
| `cash`                                                | `purchase`       | none             |
| `salary`                                              | none             | `income`         |
| `transfer`, `directCredit`, `other` on a card account | `purchase`       | none             |
| `transfer`, `directCredit`, `other` on other accounts | none             | none             |
| Own-account suffix that matches none of your accounts | none             | none             |

Where bank structure gives no role, the counterparty decides. A default role of `income`, `refund`, or `reimbursement` applies to credits, and a debit to that counterparty is still a `purchase`. A default role of `purchase` makes debits purchases and credits refunds, and `transfer` applies both ways. A counterparty without a default role still decides by kind: a business receives purchases and pays refunds, an institution receives purchases and pays income, and an own account is always a transfer. A person always needs a default role.

A transfer is never internal because of its wording. `Transfer To Jane Smith` is spending until you or a counterparty default says otherwise.

## Categories

Categories form two trees, spending and income, two levels deep. The default taxonomy is seeded by migration `0015_understanding.sql`, with stable slugs such as `food.groceries` and `income-salary`. A category you create has no slug. Top-level spending categories:

| Category            | Subcategories                                                                                      |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| Housing             | Rent, Mortgage interest, Strata, Rates, Maintenance, Home insurance                                |
| Bills and utilities | Electricity, Gas, Water, Internet, Phone                                                           |
| Food                | Groceries, Dining out, Delivery, Coffee, Alcohol                                                   |
| Transport           | Fuel, Public transport, Rideshare, Parking and tolls, Car maintenance, Car insurance, Registration |
| Shopping            | General, Clothing, Electronics, Home and furniture, Gifts                                          |
| Health              | Medical, Pharmacy, Dental, Fitness, Health insurance                                               |
| Personal care       | Hair and beauty, Personal care products                                                            |
| Entertainment       | Streaming, Events, Games, Hobbies                                                                  |
| Travel              | Flights, Accommodation, Travel activities                                                          |
| Subscriptions       | Software, News and media, Memberships                                                              |
| Education           | Courses, Books                                                                                     |
| Giving              | Donations, Gifts to people                                                                         |
| Fees and interest   | Bank fees, Foreign transaction fees, Card interest                                                 |
| Government          | Tax, Fines                                                                                         |
| Cash                | Cash withdrawals                                                                                   |

The income tree has Salary, Interest, Refunds and reimbursements, Government, and Other income, with no subcategories.

A spending allocation's category comes from, in order: your correction, a rule, the counterparty's default category for the payment's reference key or else its own default category, then the bank structure. A category applies only when it is in the tree the role uses. Purchases, financing costs, refunds, and reimbursements take a spending category. Income takes an income category. Transfers, card settlements, borrowing, loan payments, and unresolved events take none. The model puts mixed retailers in Shopping, then General.

Bank structure sets these categories:

- An `interest` debit is Mortgage interest on a loan account, Card interest on a card account, and Bank fees on a deposit account. An `interest` credit is income Interest.
- A `fee` row is Foreign transaction fees when its description starts `International Transaction Fee`, and Bank fees otherwise. A fee refund takes the same category.
- A `cash` debit is Cash withdrawals.
- A `salary` credit is income Salary.

When the model finds a cluster of counterparties that no subcategory fits, it records a proposed subcategory. You accept or dismiss it in Questions. The model never changes the taxonomy on its own.

## Tags and personal events

Tags and personal events are labels on allocations. You manage them in Settings beside the categories and attach them to an allocation when you edit an event. A personal event has a name and a date range, such as a wedding or a move. The ledger filters by either one. A personal event also stores an exclude-from-ordinary flag that no measure reads yet. A tag or personal event that an allocation uses cannot be deleted.

## Provenance

Every assignment stores its source:

| Source         | Meaning                                                                                                  |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| `user`         | A correction on this event or allocation. Never overwritten by anything else.                            |
| `link`         | A role set by a movement link. Kept until you remove the link.                                           |
| `rule`         | A user-accepted rule. The rule's ID is recorded.                                                         |
| `counterparty` | Inherited from the counterparty. The counterparty's own provenance says whether you or the model set it. |
| `bank`         | Deterministic from the descriptor and account structure.                                                 |

`link` applies to roles only. An event's counterparty has its own source: `alias` when it comes from the alias, `user` when you assigned it.

A result can therefore report how much of an amount rests on the model's judgment: the sum of allocations whose value came from a counterparty the model set.

## Precedence and propagation

When a counterparty's default changes, every event and allocation whose assignment came from `counterparty` is recomputed in the same database transaction. Assignments from `user` and `rule` are not touched. When you change one transaction's category, the UI offers to set the counterparty's default instead, which applies it everywhere at once.

Reinterpreting a posting, whether after a profile version change or after a new import, keeps the event ID and keeps every `user` assignment.

## Questions

Questions are computed from current records, not stored, so answering one makes it disappear. `questionEventsTable` in `workers/api/src/interpretation/question-events.ts` is the one definition of an open question. It loads the rule conflicts and returns the common table `question_events`, with every active event behind a question and the question's kind and ID, for a query's `WITH`. The question list, its summary, and the ledger's open-question mark and filters all read it. Each event takes the first kind below that fits it, so a descriptor the model only proposed asks who it is before anything else.

| Kind           | Raised when                                                                                                                                   | Grouped by                     |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| `alias`        | The event has no counterparty and its alias key has a proposed alias. The question asks "Is this" and the counterparty's name.                | Alias key                      |
| `person`       | The event's counterparty is a person with no default role, or one the model proposed, and you set no default for the payment's reference key. | Counterparty and reference key |
| `counterparty` | The event's counterparty is not a person and the model proposed it, so its own defaults do not apply.                                         | Counterparty                   |
| `ownAccount`   | An unresolved transfer with no counterparty names an own-account suffix that matches none of your accounts. Its alias key is `ACCOUNT 9921`.  | Alias key                      |
| `unresolved`   | The event is still `unresolved` after every source above.                                                                                     | Alias key, else event          |
| `ruleConflict` | Two claimed rules set different values, and no correction, split, or link fixes that value.                                                   | Event                          |

Rule conflicts come from `conflictingRules` in `packages/finance/src/interpretation.ts`, which ignores a disagreement over a value you fixed. An event can be behind two questions, such as an unresolved transfer whose rules also disagree. A question covers only the events its answer can change. Every kind but `alias` leaves out an event whose role you or a movement link set, when that role takes no category, or when you also set its category or split it. A `person` question therefore closes once you set each of its payments by hand, and money you set is not money it affects. An `alias` answer changes the counterparty itself, so it covers every event of the alias key.

`listQuestions` in `workers/api/src/interpretation/questions.ts` returns the questions in one currency, 25 to a page, with the most money first: outflow plus inflow, then question ID. The cursor holds the money and ID of the last question on the page. A `QuestionFilter` narrows the kinds before paging, so every page holds only that filter's questions. With a period, the list keeps only the questions with an event whose spending date falls in it, ranks them by those events' money, reports those events as `affectsInPeriod`, and shows them first among the samples. The spending date is the one ledger facts use: a purchase's purchase date when it has one, otherwise the posted date. `summarizeQuestions` counts the questions in each filter and the money their events move, each event counted once, over the whole history or over the events in a period. Each reads in one `REPEATABLE READ READ ONLY` transaction.

Every answer is an ordinary command with the versions the question carries. A `counterparty`, `alias`, `person`, `ownAccount`, or descriptor `unresolved` answer is a `CounterpartyChange`, previewed and then applied, and a rule conflict or an `unresolved` event without an alias key is a correction on that event.

| Kind           | Accept                                                                      | Something else                                                                              |
| -------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `counterparty` | `update` with the counterparty's own fields, which makes it yours.          | `merge` into a counterparty you have, or `update` with a new name, kind, role, or category. |
| `alias`        | `moveAlias` to the proposed counterparty.                                   | `moveAlias` to a counterparty you have, or `create` a new one that takes the alias key.     |
| `person`       | `saveReference` for the payments' reference key, or `update` for every one. | The same with a role and category of your own, or `update` to kind `ownAccount`.            |
| `ownAccount`   | `create` an own account named for the suffix, taking the alias key.         | `moveAlias` to a counterparty you have, or `create` one.                                    |
| `unresolved`   | None.                                                                       | For an alias key, `moveAlias` or `create` as for `alias`. For one event, a correction.      |
| `ruleConflict` | None.                                                                       | A correction on the event, which makes the disputed value yours even if it keeps it.        |

`Question` in `packages/contracts/src/finance/questions.ts` is a union on `kind`. Every question carries its ID, what it affects, up to five sample transactions, and the versions its answers expect. What it affects is the number of transactions, the money out and in, and the first and last posted dates. The Questions screen filters by `QuestionFilter`, and `questionFilterKinds` says which kinds each filter holds. `who` holds `counterparty`, `alias`, and `unresolved`. `people` holds `person`, `accounts` holds `ownAccount`, and `rules` holds `ruleConflict`.

A `counterparty` or `alias` question proposes the model's counterparty, and its basis is the model's confidence and reason. A `person` question's proposal is a default role and category for the payments, from `personProposal` in `packages/finance/src/questions.ts`. The payments' direction decides the role in each category tree. Payments out propose `purchase` with a spending category, and none with an income category. Payments in propose `reimbursement` with a spending category or `income` with an income category. The direction is out when the payments move at least as much money out as in. `personProposal` takes the first of these that gives a proposal:

1. Your defaults for the same reference key on other counterparties that give these payments a role, when they all give the same role and category. The basis names the first of those counterparties. A flatmate's rent that you set as Rental income therefore proposes nothing for the rent you pay your landlord.
2. The one active category whose name reduces to the reference key by `referenceKey`, among the categories the payments' direction allows. A category named Rent gives payments out with the reference `Rent Aug` the role `purchase` in Rent. A reference that names no such category, or more than one, proposes nothing here.
3. The model's default role for a person it proposed, with its confidence and reason. The model receives no references, amounts, or dates, and its instructions forbid a role read from a name alone, so it rarely gives a person one.

A proposal keeps a category only when the category is active and in its role's tree, and it is never `transfer`. Money to yourself at another bank makes the counterparty an own account, so `PersonRole` leaves `transfer` out, and `applyCounterpartyChange` refuses a person's default or reference default of `transfer` with `invalid`.

Below the questions, the Questions screen shows proposed subcategories, open source reviews from the importer, refunds to link, and movements to confirm.

## Links and credits

Movement links join the two sides of a transfer, card settlement, loan payment, or borrowing into one event. Only you make a link, through the `applyRelationship` command in `workers/api/src/relationships/plan.ts`. The counterpart is either another event or an external endpoint with a label. Linking another event moves its posting into the linked event and makes its own event inactive. The link sets the role with source `link`. A card settlement must pay into a card account, a loan payment must pay into a loan account, and borrowing must come from one. Both accounts must use the event's currency. Removing the link restores both events.

After an import creates events, `proposeMovements` in `workers/api/src/relationships/proposals.ts` looks for pairs and records each one as a `relationship` review item. A pair is two active events on different accounts whose primary postings have exactly opposite amounts in one currency, posted within three days of each other. Both events must be a transfer, card settlement, loan payment, borrowing, or unresolved, and at least one must not be unresolved. Neither event may already have a movement link, and a pair that was proposed before, including a dismissed one, is not proposed again. The rule does not read own-account suffixes. Amount and date alone produce a proposal, never a link.

After an import creates events, `proposeCredits` in the same file looks for the purchase each unlinked refund or reimbursement returns, through `creditProposals` in `packages/finance/src/proposals.ts`. A refund is proposed against a purchase from the same counterparty or alias key in the 120 days before it, no smaller than the refund. A reimbursement is proposed against a larger purchase in the 14 days before it whose description shares a word of four or more letters with the transfer's reference, such as `dinner`. When several purchases qualify, the one with exactly the credit's amount wins, and otherwise nothing is proposed. Each credit is proposed once, including after you dismiss it. Accepting links the remaining credit through `applyRelationship`.

Proposals appear under Refunds to link and Movements to confirm in Questions. For a movement, Review opens the transaction so you can link it, and Not a movement dismisses the proposal. For a credit, Link applies it and Not related dismisses it. Any relationship change to either event resolves its open proposals. Look for more runs the same search on demand.

A refund or reimbursement counts against its category in the month it arrives. Linking it to a specific purchase with a credit link moves that amount to the purchase's period instead. The applied amount cannot exceed the remaining credit or the remaining cost.

## Rules

A rule's conditions are an account, a role, a counterparty, a channel, and description text, combined with AND. Every condition is optional. The account is the event's reporting account. The role condition compares with the event's current role. The description matches when any posting of the event contains the text, ignoring case, and empty text matches every event.

A rule sets one category or one role, with a scope of `past`, `future`, or `both`. Saving a rule with `past` or `both` scope claims every matching event at once. Rules with `future` or `both` scope claim matching events when an import creates them. A claim stores a snapshot of the rule, so editing a `future` rule leaves its earlier claims as they were. When you save a rule you can exclude specific events. `rule_exceptions` records them, and the rule never claims them.

Rules are for patterns a counterparty default cannot express. A rule with counterparty Jane Smith, role `purchase`, and description `rent` can set Housing, then Rent, while her other payments keep her default category. Two rules that disagree on an event create a `ruleConflict` question and apply neither.

## Account history

`workers/api/src/accounts/periods.ts` stores two kinds of dated account record. A label period gives an account a different label for a date range. A posting shows the label of the period that covers its posted date, or the account's own label when none does. An offset relationship pairs a deposit account with a loan account in the same currency for a date range. Nothing reads offset relationships yet. End dates are exclusive, and periods of one kind cannot overlap for one account.

## Corrections and history

Every change to an event, an allocation, a counterparty, an alias, or a reference default is a command with the versions it expects.

A correction changes one event and keeps it as it was before and after. Its `change` is `allocations` when it sets the role, purchase date, and allocations, which must conserve the event's magnitude exactly. It is `counterparty` when you move the transaction to another counterparty with `assignEventCounterparty`, which gives the event counterparty source `user` so its descriptor no longer decides. Moving it to no counterparty returns it to its descriptor's counterparty. Neither applies to an event that a movement link joined into another.

`correctEvent` in `packages/finance/src/corrections.ts` gives source `user` only to the role and categories the correction changes, so the rest keep following rules and defaults. A role or category that the event's rules dispute also becomes yours as the correction leaves it, even unchanged, because correcting the event chooses it. `disputedValues` in `workers/api/src/interpretation/engine.ts` reads what the rules dispute, so saving the value a rule conflict already shows closes the conflict.

Undo writes a new correction with `action` `undo` that sets the same part back. `restoreEvent` in `packages/finance/src/corrections.ts` returns the prior role, purchase date, and allocations with the sources they had then, and still requires the allocations to sum to the event's current magnitude. The event is then reinterpreted, so only values that were yours before stay yours, and a value you did not set follows current rules and defaults again. A movement link fixes the role only while it exists. Undoing a counterparty move restores the counterparty you set before, or returns the event to its descriptor. When a merge or an undone creation has removed the counterparty you set before, the undo fails with `conflict`, the event stays where it is, and the message says to choose with Change instead.

A counterparty change keeps row images, `CounterpartyImages` in `packages/contracts/src/finance/counterparty-history.ts`: every counterparty, alias, and reference default it wrote, as it was before and as the change left it, and the events, rules, and movement-link snapshots it pointed at another counterparty. Undo is a new counterparty change that writes the before images back. It applies only while every record the change wrote is still as the change left it. Otherwise it fails with `stale` and says to undo the later change first, so undo is last in, first out per record. A correction's undo restores one event's earlier values over later edits to that event. A counterparty change touches many records, and restoring them the same way would silently revert later changes, such as renaming the target of an old merge.

`recordChange` stores a counterparty change in `counterparty_changes` with its kind, its images, and the change it undoes. Accepting a proposed subcategory records an `acceptCategory` change for the counterparties it moves. `counterparty_change_subjects` names each counterparty the images mention as it was named then. It has no foreign key, so a merged counterparty keeps its history. `counterparty_change_events` holds the transactions whose meaning the change altered, which are the events the fact triggers noted in its transaction.

Undo compares each record with its after image without the version, so a record that an undo returned to earlier values still matches the change that left those values. A record a change updates, an undo included, takes a version above the one it replaced, and a record an undo recreates takes one above the version it had. A deleted alias or reference default leaves no row, so the next one saved for its key starts again at version 1. A page still showing the deleted row at version 1 can then change the new row without a `stale` reply. That takes a delete and a new save between the page's read and its write, so the gap is accepted. A change is undone at most once, and its undo can be undone in turn. Undoing a counterparty's creation deletes the counterparty, so it is refused while a transaction you assigned to it by hand, or anything else outside the creation, still names it.

`listCounterpartyHistory` in `workers/api/src/interpretation/counterparty-history.ts` returns a counterparty's changes newest first, 20 at a time. Each entry has the counterparties the change wrote, the number of transactions it changed, whether it was undone, and whether it can be undone now. `previewCounterpartyUndo` and `undoCounterpartyChange` preview and apply an undo.

A transaction's history, from `getEventHistory` in `workers/api/src/events/corrections.ts`, lists its corrections and every counterparty change that changed what it means, newest first. Its `names` name every counterparty the corrections refer to, including one a merge has since removed. A counterparty change names its own in `subjects`, as they were named when it was made. `previewEventCounterparty` and `previewUndoCorrection` preview moving a transaction and undoing a correction.
