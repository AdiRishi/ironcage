The ledger is the bank's record: accounts, source files, observations, and postings. [Interpretation](/reference/interpretation) sits above it and never changes it. [Analysis](/reference/analysis) owns arithmetic.

## Values

| Value        | Contract                                                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ID           | UUID generated by the API, branded by record kind in TypeScript.                                                                                                |
| Money        | `{ currency, minor }`. `minor` is a signed integer of minor units: `bigint` in code, `BIGINT` in Postgres, a decimal string in JSON. Never a JavaScript number. |
| CalendarDate | `YYYY-MM-DD` string in code and JSON, `DATE` in Postgres. Decoded without passing through a local-midnight `Date`.                                              |
| Instant      | ISO 8601 UTC string in JSON, `TIMESTAMPTZ` in Postgres.                                                                                                         |
| Period       | `{ start, endExclusive }` of calendar dates.                                                                                                                    |
| Version      | Integer incremented on every write to a mutable record. Commands carry the version they expect.                                                                 |

Parsing converts decimal text straight to minor units using the currency's exponent. Aggregates in SQL use `SUM` over `BIGINT` or `NUMERIC`. Fractional intermediate values stay exact as rationals or decimals until the output boundary named by the calculation. An amount that a source does not supply is absent, never zero.

Queries go through `@effect/sql-pg`'s own Postgres client, which types each parameter from its value. A `bigint` binds as `BIGINT` and a string binds untyped, so Postgres infers it from the statement. An object or array stored as `JSONB` goes through `sql.json`, or through `PgTypes.jsonb` when it is a value inside a `sql.insert` row: the Workers get the client through Alchemy's deferred proxy, which resolves `sql` helpers passed directly but not ones nested in an object. A list that can be empty goes through `sql.in`, because an empty array has no type to infer. Reads cast `BIGINT`, `NUMERIC`, and `DATE` results to text, which the contracts decode, so decoding does not depend on the driver's type mapping.

Boundary schemas validate imported bytes, browser input, stored JSON payloads on read, and model output. Everything inside the API trusts decoded types.

## Identity

- A source file is its SHA-256. Same bytes, same file, whatever the name.
- An observation is its source file plus locator key. Reparsing a file yields the same observation IDs for the same rows.
- A posting is created once by publication and never recreated by reparsing. Observations point at postings; postings do not point at observations.
- A financial event keeps its ID when its allocations, links, or counterparty change, and when its postings are reinterpreted.
- Categories and counterparties keep their IDs through renames and moves.

## Write protocol

Every write of financial records is a command with a client-generated `commandId`. The API runs each command like this:

1. Open a `SERIALIZABLE` transaction through `writeTransaction` in `workers/api/src/database/transactions.ts`. Writes that touch different records run at the same time. When two writes would not give the same result one after the other, Postgres aborts one with a serialization failure and the helper runs it again from the start, up to eight times with jittered backoff. A command therefore does nothing outside the database until its transaction commits.
2. Look up `command_receipts` by `commandId`. If the input hash matches, return the stored result. If it differs, fail with `conflict`.
3. Read the records the command touches. Compare each `expectedVersion`. Any mismatch fails with `stale` and changes nothing.
4. Validate business preconditions against current records: allocation conservation, remaining credit, matching decisions.
5. Write the change, its correction history, and the receipt. Refresh the [ledger facts](/reference/analysis#ledger-facts) of every event the transaction changed. Commit.

Parsing, model calls, and uploads to R2 happen before the transaction opens. Source removal deletes from R2 after the transaction, using the key saved in its receipt. A repeat completes that delete before returning, as defined in [Source removal](/reference/imports#source-removal). A client that loses the response repeats the same command with the same ID and gets the first result. A network error alone does not prove the write rolled back.

Import publication follows the same shape. Its command ID is a UUID v5 of the import ID, the parser version, and a SHA-256 hash of the whole encoded `PublishImport`: the account, the statement, and the observations. A retry of the same parse returns the stored summary. A retry after a parser fix, or any change to the parsed statement or account, is a new publication. Publication does not check the import's status, so a repeat returns the stored summary even after the import changed state.

## Reads

Reads that return related totals, such as a period's flow and its coverage, run in one transaction with `REPEATABLE READ` so the parts agree. Lists use a cursor made of the sort key and ID of the last row. The cursor is validated as input; changing filters resets it. Hyperdrive caching is off so a read after a commit sees the commit.

## Postings

A posting records what the bank booked: account, currency, signed booked amount, posted date, optional value date, description, and optional original-currency money. Booked amounts are asset-positive: a deposit account balance is positive when the user has money, and a card or loan balance is negative when the user owes money. A purchase on any account is negative; a repayment into a card or loan is positive.

Historical totals use the booked AUD amount. Original-currency money is display information and its own supporting observation. Separate fee postings stay separate postings.

Posted date is the date basis for account views. Value date is stored beside it and never used as a purchase date on its own.

## Failures

Commands and reads fail with one of these kinds so the UI can act on them.

| Kind          | Meaning                                                            | UI action                                         |
| ------------- | ------------------------------------------------------------------ | ------------------------------------------------- |
| `invalid`     | Input failed its schema.                                           | Show the field error, keep the input.             |
| `notFound`    | A referenced record does not exist.                                | Return to the list.                               |
| `stale`       | An expected version no longer matches.                             | Show current records, keep the input, ask again.  |
| `conflict`    | Command ID reused with different input, or a uniqueness violation. | Show the stored result or the conflicting record. |
| `needsReview` | The write created or requires a review item.                       | Link to the review item.                          |
| `unavailable` | Database, storage, Workflow, or model call failed.                 | Offer retry with the same command ID.             |
