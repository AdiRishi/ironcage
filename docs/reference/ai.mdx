Models are used in three places:

- **Enrichment**, which resolves counterparties and their defaults.
- **Document extraction** for a statement page the parser cannot read. No page in the corpus needs it.
- **The analyst**, which is on the [roadmap](/roadmap).

A model never computes a total and never changes a booked field.

## Access

Every model call goes through the Workers AI binding with a stage-specific AI Gateway, billed to the Cloudflare account, so the application holds no provider key. The gateway has authentication on, and request logging and response caching off. The model ID lives in `packages/contracts/src/finance/models.ts`, and `infra/src/enrichment.ts` owns the gateway and the price table used for usage estimates.

Enrichment uses `@cf/zai-org/glm-5.3-flash` at $0.15 per million input tokens, $0.03 per million cached input tokens, and $0.50 per million output tokens. The request and reply types come from `@cloudflare/workers-types`. The request asks for JSON matching a JSON Schema generated from the `EnrichmentOutput` contract, and the answer is decoded against that same contract. The model has no web search, so a descriptor it does not recognise gets a low confidence and becomes a question.

A request that fails is retried three times with exponential backoff from 5 seconds. A reply that arrives is never retried, even when it fails to decode, because the answer was already billed.

## Enrichment

Enrichment runs as a Cloudflare Workflow in the processor. It turns alias keys that have no counterparty into counterparties with defaults.

1. **Collect.** Requesting a run records every alias key without a counterparty, largest total amount first. The amounts order the work and never reach the model. Each batch carries up to three descriptor samples per alias, its channels, directions, account kinds, and transaction count.
2. **Resolve.** A batch of up to 25 aliases goes to the model with the taxonomy, each category keyed by its slug (or ID for a category you created), and the existing counterparties. For each alias, the model returns:
   - whether it belongs to an existing counterparty or a new one
   - the counterparty's name, kind, brand, and default category slug
   - a default role for people and institutions, if it can tell
   - a confidence from 0 to 1, and a one-line reason
     The model may propose a subcategory that does not exist yet.
3. **Apply.** The API validates the response against the current taxonomy and counterparties, then applies it in one command:
   - A confidence at or above the auto-apply threshold (0.8 by default) creates or links the counterparty with `model` provenance and status `applied`, and its defaults apply to events immediately.
   - A lower confidence, or any person counterparty, creates the counterparty with status `proposed`, which raises a question with the model's proposal.

A counterparty with the same name as the model's answer is reused, so aliases of one business resolved in different batches still meet. Proposed subcategories appear in Questions. Accepting one creates it and moves the counterparties the model placed in its parent, or in a sibling subcategory, into it. Counterparties you set are never moved. Rerunning enrichment only touches aliases without a counterparty. A counterparty you edited is never sent back to the model.

The corpus has 1,203 alias keys, which is 49 batches.

### What the model receives

- The descriptor samples with card suffixes, own-account suffixes, PayIDs, references, and value dates removed
- The channel, the direction, and the transaction count
- The taxonomy's slugs and names
- Existing counterparty names

It never receives amounts, balances, dates, account numbers, or notes. Settings shows this list.

### Learning from corrections

Every counterparty you created or edited becomes an example. Each batch includes up to 20 recent ones as descriptor samples with your answer, so the model follows your conventions, such as "Bunnings is Home and furniture, not Maintenance".

### Evaluation

There is no evaluation yet. The intended set is your answers: every counterparty you created or corrected, with its descriptors and your answer. A candidate model or prompt would be scored on name agreement, category agreement at both levels, kind agreement, and calibration: of the answers above the auto-apply threshold, the share that matched.

## Document extraction

The statement parser runs first. A page it cannot read becomes a `value` source review showing the page. If a statement ever needs it, one model call per page can extract rows with page locators. The result goes through the same candidate validation, reconciliation, and matching as parser output. There is no switch for this until a statement needs it.

## Usage and limits

Every batch writes a usage record with the task, model, time, reported tokens, and estimated cost. The estimate prices cached input tokens at the cached rate. A batch without a usable usage report stores unknown usage, not zero. A USD warning threshold blocks new calls once recorded usage reaches it. Delayed reports and concurrent calls can overshoot it, and Settings says so.

Each batch has a 16,000-token output limit and a ten-minute Workflow step timeout. The Workflow never repeats a batch whose retries ran out. A failed batch leaves its aliases unresolved and the run moves on; three failed batches in a row stop the run. The next run picks up every alias still without a counterparty, including the failed ones.

Logs carry operation IDs and timings, never prompts, completions, or descriptions.

## Safety

Descriptors and model output are untrusted data. Model output is validated against a schema and against current records before anything is written. Text in a description has no authority. A model can propose a correction, but only your action applies one.
