## Outcome

Every posting can carry a financial role, a category, a merchant, tags, and links to related postings. The user corrects anything, previews the effect of broad changes, and undoes through history. A model suggests categories; the user accepts or ignores them.

Prerequisite: stage 2 verified. Existing postings are interpreted in place; nothing is reuploaded.

Also read [Financial model](/technical/financial-model#financial-events), [Calculation rules](/technical/calculation-rules#financial-event-construction), and [AI](/technical/ai#classification).

## Milestones

1. **Events from postings.** Migration, reference data, and an Interpret action that creates one event per posting using the source-marker table below. Done when every corpus posting has an event, unresolved ones are listed, and the detail shows the interpretation beside the bank fields.
2. **Corrections.** Change role, category, merchant, tags, personal event, and purchase date on one event. Split a purchase. History and undo. Done when the worked examples below pass through the UI.
3. **Links.** Movement links with proposals for transfers, card settlements, loan payments, and borrowing. Credit links for refunds and reimbursements. Fee associations. Offset relationships and effective-dated account changes. Done when the card, transfer, reimbursement, and mortgage examples show the right measures in the detail preview.
4. **Rules and suggestions.** Rules with preview and per-event exceptions. Category suggestions from the model with single and bulk acceptance. Export extended. Done when suggestions run over the corpus, corrections survive a rerun, and manual categorization works with the model disabled.

## Source markers

Initial roles come from CommBank description patterns, verified against the corpus and adjusted there. Anything not matched is `unresolved`.

| Account kind | Pattern in description                                      | Role                                                     |
| ------------ | ----------------------------------------------------------- | -------------------------------------------------------- |
| any          | contains `Card xx` and amount negative                      | `purchase`                                               |
| any          | debit starting with `Interest` or containing the word `Fee` | `financingCost`                                          |
| deposit      | starts with `Transfer to` or `Transfer from`                | `transfer` proposal, counterpart by amount and reference |
| loan         | `Repayment/Payment`                                         | `loanPayment`, deposit counterpart by amount and date    |
| loan         | `Money we lent you`                                         | `borrowing`                                              |
| card         | starts with `Payment` and amount positive                   | `cardSettlement`, deposit counterpart by amount and date |
| deposit      | credit with a recurring employer description                | `income` after the user confirms the first one           |

Interest credits remain unresolved until confirmed. A category never establishes income.

A proposal becomes a link only when the counterpart is found with equal opposite amount in one currency and a shared reference, or when the user confirms it. The current implementation proposes equal opposite movements within three calendar days and requires confirmation. Amount and date alone never create a link.

## Screens

[Screen designs](/design/interpret-transactions).

### Transactions

- Filters gain role, category, merchant, tag, personal event, and interpretation review state. Search matches merchant names as well as descriptions.
- Detail shows the event: role, allocations with category and merchant, tags, personal events, links with their counterpart postings, credits applied, and the correction history. Bank fields stay visible above it.
- Edit controls: change role, category, merchant, tags, personal event, purchase date; split; link or unlink a movement; apply or remove a credit; associate a fee; undo a correction.
- A role or link change shows a preview of the effect on costs, income, cash change, and loan measures for the affected period before accepting.

### Review

- Interpretation items: `role` for an unresolved posting with candidate roles, `relationship` for a proposed link, `ruleConflict` for two rules that disagree. Resolving applies the ordinary command.

### Settings

- Categories as a tree with rename, move, and archive. Merchants with aliases. Tags. Personal events with a period and an exclude-from-ordinary flag.
- Rules: condition, action, scope of past, future, or both. Editing previews affected events and lists exceptions.
- Accounts gain offset relationships with effective periods, and effective-dated label changes. These periods include `start_on` and exclude `end_on`; a missing end means ongoing. Periods for the same account cannot overlap within either kind. Account kinds are immutable.
- Classification: enabled or disabled, provider, what is sent, usage, and Suggest categories for uncategorized events.

Unlinking a movement restores its original interpretation and reactivates the counterpart event with its original ID. Applied credits and fee associations must be removed before a correction can invalidate their roles or amounts. Credit previews include the original cost period even when the credit posts later. Loan principal reduction remains unavailable until the selected period has complete loan coverage.

Database checks: allocations of an event sum to `magnitude_minor`, enforced in the command transaction; `credit_links.amount_minor` positive and bounded by both remaining amounts, enforced in the command transaction; one active event per posting by a partial unique index.

## Operations

User writes are commands with `commandId` and expected versions. Internal Workflow
completion records use the batch command ID for replay; terminal failure status
is idempotent.

Rules match account, established role, merchant or alias, and a description
substring. Conditions combine with AND. An action assigns one category or one
financial role. Explicit exceptions, specific corrections, splits, and accepted
relationships take precedence. Conflicting actions restore the interpretation
before rules and create a `ruleConflict` review item. Editing with future scope
leaves existing events unchanged. Deleting a rule stops its future application
and preserves accepted interpretations. A category used by a rule must be
removed from that rule before it can be archived.

| Operation                                                                                   | Contract                                                                                                                             |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `interpretPostings({ commandId, scope })`                                                   | Creates events for postings without one. `scope` is all or a list. Never touches existing events.                                    |
| `getEvent({ eventId })`                                                                     | Event with postings and allocations. Companion queries load relationships, suggestions, history, and review items.                   |
| `previewCorrection({ change })`, `applyCorrection({ commandId, change, expectedVersions })` | Single-event changes including role, category, merchant, tags, personal event, purchase date, split. Preview returns measure impact. |
| `linkMovement`, `unlinkMovement`, `linkCredit`, `unlinkCredit`, `associateFee`              | Commands with preview variants. Conservation and remaining-credit checks run in the transaction.                                     |
| `undoCorrection({ commandId, correctionId })`                                               | Writes a new correction restoring `prior`.                                                                                           |
| `previewRule({ rule })`, `saveRule({ commandId, rule, expectedVersion })`                   | Preview lists affected events and current exceptions. Save applies to the chosen scope.                                              |
| `suggestCategories({ commandId, eventIds })`                                                | Starts a processor run that writes each result to `events.suggestion`. Never applies.                                                |
| `acceptSuggestions({ commandId, expectedVersions })`                                        | Applies suggestions that are still valid under precedence. Skips corrected events.                                                   |
| Reference data CRUD                                                                         | Commands for categories, merchants, aliases, tags, personal events, offset relationships, account periods.                           |
| `requestExport`                                                                             | Includes every table above.                                                                                                          |

## Worked examples

Amounts in dollars, spending on the posted basis.

1. **Card purchase and settlement.** A $100 grocery purchase on the card is a `purchase` event. A $100 payment from the deposit account and the matching credit on the card link as one `cardSettlement` event with magnitude $100 and a transfer allocation. Spending for the period is $100. Cash change on the deposit account is minus $100. Card balance change is zero.
2. **Transfer with one side.** A $2000 debit "Transfer to" an account not in the corpus. The user confirms an external owned endpoint. The event is a `transfer` with one posting. Income and spending are unchanged; the detail shows the missing counterpart.
3. **Reimbursement.** A $300 dinner and a later $200 credit from a friend. The user applies $200 of the `reimbursement` allocation to the dinner's cost allocation. Net personal cost is $100. Applying another $200 fails with `conflict`; the detail shows $100 remaining.
4. **Mortgage.** A $3900 repayment and $2800 interest in September. The repayment is a `loanPayment` event with a transfer allocation; the interest is a `financingCost` event. Costs are $2800. Net principal reduction is $1100. If the interest had posted on 31 August, August would carry the $2800 cost and September the $3900 repayment.
5. **Split and rule.** A $150 purchase is split into $100 groceries and $50 household. A rule "merchant Woolworths, category groceries, scope both" previews 240 events and lists this split as an exception; saving changes the 239 others.
6. **Undo.** The user changes a category, then undoes it. History shows both corrections. The event carries the original category and the bank fields never changed.

## Verification checklist

- Interpreting the corpus assigns roles from the marker table; report counts per role and the unresolved list.
- The six worked examples pass through the browser with the stated measures in the preview and the detail.
- Splits that do not conserve are rejected. Credit over-application is rejected. Two commands racing for the same remaining credit produce one success and one `conflict`.
- A rerun of `interpretPostings` and of `suggestCategories` after corrections changes no corrected event.
- Importing an older overlapping statement after corrections keeps every event and correction.
- Two conflicting rules produce a `ruleConflict` item and apply nothing to the disputed events.
- Model unavailable and invalid output both leave manual categorization working.
- Renaming a category keeps its ID and every allocation.
- Screens work at phone width and by keyboard. Stage 1 and 2 checklists pass.

## Implementation verification

The original private corpus has 9,224 interpreted postings in either import
order. Initial roles are 4,647 purchases, 753 financing costs, 1,035 transfers,
12 loan payments, 1 borrowing, and 2,776 unresolved events. Initial interpretation
and subsequent imports preserve existing event IDs and corrections.

Browser checks cover role and category corrections, split conservation, preview,
stale edits, history, and undo. The $150 example retains $100 groceries and $50
household. A supermarket rule matches two events, updates the ordinary purchase,
and lists the split as an exception. A conflicting rule creates one dispute;
excluding that event restores the first rule's category and clears the dispute.
The rule and suggestion screens fit a 390-pixel viewport, with keyboard saving,
selection, and acceptance.

The $100 card payment and its counterpart link as one settlement. The external
$2,000 transfer has an owned endpoint and adds no cost or income. A $200
reimbursement reduces the $300 dinner to $100. The $3,900 mortgage payment links
to its loan counterpart while $2,800 interest remains a separate financing cost.
The complete-coverage calculation fixture produces $1,100 principal reduction;
the development browser correctly reports that measure unavailable because
its selected account set has incomplete coverage. Preview coverage combines
consecutive reconciled statement intervals; a missing day remains a gap. Concurrent credit commands,
over-application, and changes that would invalidate accepted links are covered
through the API.

Three synthetic transactions completed through the native Workflow and live
Cloudflare Workers AI binding using Llama 4 Scout, suggesting Groceries, Dining, and Household.
Single acceptance and bulk acceptance of two suggestions passed. A rerun on an
accepted event requested zero events. With the model disabled, manual financing-cost
categorization still saved through preview. The three calls reported 1,197 input
and 193 output tokens, with a recorded estimate of USD 0.03. API tests
cover corrections during inference, stale acceptance, command replay, unknown
usage, the warning threshold, invalid responses, and unavailable models.
Rule applications retain their accepted rule snapshots so later future-only
edits cannot reinterpret past rule applications.

After switching to GLM-5.3-Flash through AI Gateway, three new synthetic
transactions completed through the application workflow: coffee suggested
Dining, a grocery purchase suggested Groceries, and an ambiguous reference
returned Needs review. Their allocations remained uncategorized until user
acceptance. These calls reported 1,196 input and 896 output tokens, with a
recorded estimate of USD 0.03. Cloudflare's API confirmed authentication enabled,
logging disabled, and caching disabled on the Alchemy-created development
gateway. Model access was disabled again after verification.

The full local suite includes all prior-stage tests and checks every table and
manifest count in the export. The managed database restore test passed again.
Hosted application tests could not deploy the Access application: both Alchemy
and a direct Cloudflare API retry returned HTTP 403. The isolated hosted
resources were removed after the attempt.

The private-corpus model run remains pending explicit consent to send its
transaction descriptions and classification context to Cloudflare Workers AI.
The feature is implemented and the synthetic provider flow is verified; this
remaining corpus check is not claimed as complete.
