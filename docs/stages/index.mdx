Ironcage is built one stage at a time. Each stage delivers a working browser application with its backend, integration, and tests, then stops. Stage 1 is the default target unless a task names another stage. Nothing has shipped yet; the docs describe what to build.

| [1. Upload and record transactions](/stages/record-transactions)        | Upload CSV and OFX, resolve source reviews, browse postings and their sources. | [Starting point](/stages/starting-point) |
| [2. Import the full historical corpus](/stages/historical-imports)      | Add PDF statements, cross-format matching, source removal, and exports.        | Stage 1                                  |
| [3. Interpret and correct transactions](/stages/interpret-transactions) | Financial events, categories, links between postings, corrections, and rules.  | Stage 2                                  |

## How to build a stage

1. Read [Starting point](/stages/starting-point) once. Inspect the repository to see what already works; the docs describe intent, not status.
2. Read the stage page. It owns the milestones, screens, tables, operations, worked examples, and verification for that stage. The "Also read" section lists the two or three reference pages it depends on.
3. Work through the milestones in order. Each milestone ends with a working browser flow backed by real records. Commit at each one.
4. Prefer an installed library or a Cloudflare platform feature over custom code. Check the installed source and official documentation before choosing an API. Keep exact money and date rules in shared code that every consumer imports.
5. Run the stage's verification checklist and the earlier stages' regressions. Run `pnpm check`, `pnpm typecheck`, and `pnpm test`.
6. Report the stage, what was verified, and which hosted checks are still outstanding. Stop.

## What every stage delivers

- Every flow on the stage page works on desktop and mobile and with a keyboard, with empty, loading, failed, and retry states.
- Navigation shows only destinations that work. Settings shows only controls whose behavior exists.
- The API is the only writer of financial records. Exact money, source evidence, posting identity, and command receipts hold from stage 1.
- A failed action leaves accepted records consistent and can be repeated without duplicating anything. Retry, reupload, or a source review are the recovery paths.
- Financial exports exist from stage 2 and include each later stage's records.
- Earlier stages keep working. Their tests keep passing.
