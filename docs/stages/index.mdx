Build Ironcage one stage at a time. Every stage includes the frontend, backend, integration, and verification needed for a usable application. Completion is a working browser experience with persisted data and recovery, followed by a stopping point.

The default implementation target is [stage 1](/stages/record-transactions). This is a scope selection, not a claim that any stage has shipped. A request for a later stage includes verifying its prerequisites. Completing a stage does not authorize starting the next one.

## Scope and authority

Stage pages own delivery scope, prerequisites, and completion. [Product references](/product) own detailed behavior. [Technical references](/technical) own architecture, contracts, and invariants. A reference to a later capability explains the eventual system and does not add that capability to an earlier stage.

Each behavior has one introduction stage. Later stages extend the same modules and preserve earlier outcomes. [Stage boundaries](/technical/stage-boundaries) assigns shared schemas, methods, jobs, and controls to their introduction stages and specifies the few contracts that grow across stages. Follow those explicit projections instead of creating unused tables, dummy results, disabled controls, or jobs without consumers.

Read the selected stage, the [build guide](/technical/build-spend-management), and the reference sections named by that stage. There is no requirement to read or implement the entire reference library before starting. If a dependency is missing from the stage contract, resolve its ownership there and in the affected technical reference before implementing dependent behavior.

## Completion of every stage

Each stage must demonstrate its complete user flows on desktop and mobile, including keyboard access, empty states, loading, failures, retry, and retained progress where applicable. Navigation exposes only working destinations. Required controls, settings, and evidence access arrive with their owning behavior.

The API remains the authority for records and financial calculations. Source evidence, exact money, canonical transaction identity, ownership, and idempotent commands hold from their first use. Durable storage and verified recovery accompany the first private imports. Later stages extend export and restore coverage to their new records.

Run the checks in [Verification](/technical/verification) for the selected stage and preserve regression evidence for earlier stages. Report the verified stage, evidence, and specific outstanding external checks. An unverified hosted integration remains outstanding, even when the local prototype works.

## Written experience contracts

These docs specify actions, information, states, and observable outcomes. Visual branding, colors, typefaces, layout composition, and screen images are intentionally unspecified. A design task can use one stage's flows and its prerequisites to develop a visual proposal. The frontend stack and accessibility requirements remain engineering and product constraints.

## Longer-term scope

The seven stages retain the planned spend-management product. The [vision](/vision) also discusses investment and trading capabilities, which have no implementation stage or contract here.
