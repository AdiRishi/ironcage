## Outcome

The user uploads CommBank CSV and OFX exports for four accounts, resolves the few questions the importer cannot answer, and browses every posting with its source rows. Uploading the same data twice changes nothing. The private deployment has authentication, backups, and a verified restore.

Prerequisite: [Starting point](/stages/starting-point). Nothing from the starter feature survives.

Also read [Import protocol](/technical/import-protocol) for parsing and matching, [Financial model](/technical/financial-model) for value types and the write protocol, and [Verification](/technical/verification) for test layout.

## Milestones

Build these in order. Each ends with something that works in the browser.

1. **Platform.** Delete the artifacts feature. Add Postgres through Hyperdrive, the `Sources` R2 bucket, the `ImportWorkflow`, and Cloudflare Access. Migrations create the stage 1 tables. Done when an authenticated request reaches a page that reads an empty accounts list from Postgres, and the same works in the local Alchemy stack.
2. **CSV to postings.** Upload one CSV, choose the account, watch the import complete, see its postings in the Transactions list with detail and source download. Done when every CSV in the corpus imports on its own with the expected row count and reconciled balances.
3. **OFX.** Same for OFX, with account identity from the envelope. Done when every OFX imports on its own and the four accounts are created from envelopes.
4. **Matching and source review.** Upload overlapping files in any order. Observations attach to existing postings; ambiguous rows become review items the user resolves. Done when the whole CSV and OFX corpus imports in any order to the same postings and agrees with the matching labels.
5. **Operations.** Retry, lost-response handling, account and settings editing, backups configured, restore drill performed. Done when the verification checklist passes.

## Screens

### Imports

- Drop one or several files. Each file uploads and processes independently. Show per-file state: uploading, processing, needs review, complete, failed, already imported.
- When a CSV cannot identify its account, ask for the account before processing. Offer the existing accounts and a way to create one with a label and account kind.
- A complete file shows counts: observations, new postings, matched postings, review items. Link to its postings and to its review items.
- A failed file shows the failure and a Retry button. Retry reruns processing from the stored bytes. If the bytes never fully arrived, ask for reupload instead.
- A file already imported links to the existing import. Renaming the file makes no difference.
- Refreshing the page shows the same states from the server.

### Transactions

- A list of postings across accounts, newest first. Filters: account, currency, posted date range, signed amount range, description text, and whether the posting has open review items. Filters live in the URL.
- Each row shows account, posted date, booked amount with currency, and description.
- Detail shows the posting, its value date if any, and every supporting observation with its file name, locator, and literal fields. Download the original file from here.
- Paginate with a cursor of posted date plus posting ID. Changing filters resets the cursor.

### Review

- A list of open source review items across imports, each naming the file, the row, the question, and the candidate answers.
- Resolve by choosing a candidate: confirm the account, accept a decoded value shown beside the literal text, match a specific existing posting, declare a distinct posting, or keep the accepted posting against a changed parser result.
- Resolving reruns publication for that import. The item closes, the import status updates, and the affected postings appear.

### Settings

- Accounts: label and account kind, with the bank identifiers shown read-only once a source has established them.
- Display: timezone, default Australia/Sydney, and reporting currency, default AUD.
- Retention: a read-only statement of the configured database backup retention and where original files are also kept.

The second unique constraint on `observations` is the rule that one file supports one posting at most once. The same posting can have one observation from each of several files.

`raw` holds the literal parser fields: the four CSV columns, or every OFX tag in the `STMTTRN`. `candidate` holds the normalized values the importer derived: `postedOn`, `valueOn`, `amountMinor`, `currency`, `description`, `balanceMinor`, `bankId`, `originalMoney`. `issue` holds the reason a candidate is missing or doubtful. [Import protocol](/technical/import-protocol#observations) defines both shapes.

## Import status

```
upload ──► processing ──► complete
              │  ▲           ▲
              │  │           │ last review resolved
              │  └── retry   │
              ├──► needs_review
              └──► failed
```

- `processing` is set when the import row is created and the Workflow instance starts.
- The Workflow parses the file and calls `publishImport`. Publication sets `complete` or `needs_review` and writes `summary` in the same database transaction as the postings.
- A parse failure or a Workflow error sets `failed` with a `failure` payload. If the Workflow dies before reporting, `getImport` asks the processor for the instance status and reports `failed` with the platform's error.
- `retryImport` moves `failed` back to `processing` and starts a new Workflow instance on the same bytes.
- `resolveReview` applies the decision and reruns publication for the import inside one transaction. When no open review items remain the status becomes `complete`.

Authentication: the web Worker validates the Cloudflare Access JWT on every request and rejects anything without one. The API and processor have no public routes; only service bindings reach them. Because the application has exactly one user, records carry no owner column.

## Corpus facts

Measured on the private corpus in September 2026. The parser is built for these files.

- 26 CSV and 26 OFX files, 3031 rows each in total. Each CSV has exactly the rows of its OFX pair.
- CSV rows have four fields, no header, no byte order mark, no thousands separators, no multiline fields. Rows are newest first. Deposit and loan rows carry a running balance; card rows have an empty balance.
- 2132 CSV descriptions end with ` Value Date: DD/MM/YYYY`. The same suffix appears in the OFX `MEMO`, and `DTUSER` holds the same date. Strip the suffix into `valueOn`, keep the literal text in `raw`.
- OFX is 1.02 SGML with `ENCODING:USASCII` and `CHARSET:1252`. Leaf tags have no closing tag. `&amp;` appears in memos and must be decoded. `NAME` is never present; `MEMO` always is. `TRNTYPE` is only `DEBIT` or `CREDIT`.
- All `DTPOSTED` and `DTUSER` values are eight digits. `DTSTART`, `DTEND`, and `DTASOF` are fourteen digits with no offset, which OFX defines as GMT.
- The deposit accounts use `BANKMSGSRSV1` with `BANKACCTFROM` and `ACCTTYPE` `SAVINGS`, and every row has a `FITID`. The card uses `CREDITCARDMSGSRSV1` with `CCACCTFROM`. The loan uses `BANKMSGSRSV1` with `ACCTTYPE` `CREDITLINE`, opens its statement with `<CCSTMTRS>` and closes it with `</STMTRS>`. Card and loan `FITID` tags are empty on every row.
- Amounts and balances are already signed the way the glossary defines booked amounts: card and loan balances are negative, repayments are positive. Store them as exported. Reconciliation catches any file that breaks this.
- After decoding entities and stripping the value-date suffix, every CSV row has an OFX row with the same posted date, amount, and description. 39 groups of two or more identical rows exist within single files.
- 151 posted-date and amount and description keys appear in more than one spending-account file because export windows overlap on purpose.

## Worked example

Account S is a deposit account. File A is its OFX for 17 to 31 August. File B is the CSV for the same window. File C is the CSV for 25 August to 5 September.

1. **Upload A.** The envelope identifies the account by `BANKID` and `ACCTID`; no account exists, so the importer creates one with kind `deposit` and a placeholder label. 77 observations, 77 new postings. `LEDGERBAL` at `DTASOF` becomes the closing anchor. No opening anchor, so coverage is 17 to 31 August with `reconciled` false. Status `complete`.
2. **Upload B.** The CSV has no account identity, so the UI asks; the user picks S. 77 observations. Every row finds exactly one existing posting with the same posted date and amount, and the normalized descriptions agree. Two rows on 20 August are identical; the file has two and the account has two, so both match as a group. Running balances reconcile every adjacent pair, and the newest balance equals A's ledger anchor, so the coverage row for B is `reconciled`. 0 new postings, 77 matched. Status `complete`.
3. **Upload B again under another name.** The hash matches. No import is created. The response says `existing` and the UI links to the earlier import.
4. **Upload C.** 30 observations. 18 rows from 25 to 31 August match existing postings. 12 September rows are new. Coverage for C runs 25 August to 5 September. Status `complete`. The Transactions list now shows 89 postings for S.
5. **Upload A while B is still processing.** Publication takes the write lock, so the second file's matching sees the first file's committed postings or waits for them. No duplicates either way.
6. **A future export changes a description.** The parser produces a candidate that differs from the accepted posting an earlier observation of the same file supports. The importer creates a `source_conflict` review item and leaves the posting unchanged until the user chooses.

## Verification checklist

Run these before calling the stage done. [Verification](/technical/verification) has the test layout.

- Every CSV and every OFX in the corpus imports alone. Row counts match the file. Adjacent running balances reconcile in every deposit and loan CSV. Each OFX closing anchor equals the newest running balance of its CSV pair.
- The whole corpus imports in filename order and in reverse order to the same set of postings. Every CSV row matches its OFX pair's posting at step 3, and the deposit accounts also match at step 2. The CSV and OFX corpus produces zero review items; report any that appear with their reason.
- Two identical same-day rows in one file produce two postings. Reuploading that file produces no more.
- Renamed identical bytes are recognized. A file with one bad row fails visibly while a sibling completes, and retry succeeds after the parser fix.
- `publishImport` called twice with the same observations returns the same summary and writes nothing the second time. A failure injected before commit leaves no postings, no observations, no receipt.
- A `resolveReview` whose response is lost can be repeated with the same command ID and returns the first result. A stale `expectedVersion` changes nothing.
- Money and date decoding: exact minor units, negatives, leap days, no `number` conversion, `DATE` round-trips without timezone shift, offset-free `DTASOF` reads as GMT.
- Unauthenticated requests to the web Worker are rejected. Source download requires the Access session.
- Managed backups are enabled with a recorded retention. One restore into an isolated environment shows postings and review resolutions intact, and original files are retrievable from the independent copy.
- The four screens work on a phone-width viewport and by keyboard alone.

## Not in this stage

PDF, exports, source removal, any model call, financial events and categories, links between postings, spending analysis, planning, the analyst, findings. Offset relationships and effective-dated account changes arrive in stage 3.
